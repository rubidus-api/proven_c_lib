    Chapter 17: HTTP/2 - frames and header compression#

    Part V - Talking to the operating system. Prerequisites: Chapter 10 for what a request and a response are; Chapter 2 for the allocator the compression tables are made with. After this chapter you can say what HTTP/2 changes and what it does not, encode and decode header blocks, read and write frames, tell a well-formed request from one that must not be passed on, drive a connection - streams, windows, resets and goodbyes - over bytes you carry yourself, turn HTTP/2 - and HTTP/3 - on in the event-driven server of Chapter 15 without changing a handler, and say which of these this library does today.

    This chapter covers hpack.h and h2.h. Both are pure computation, available in a freestanding build: HPACK allocates one table for an encoder and one for a decoder, the frame functions allocate nothing, and a connection allocates what its configuration bounds.

    What is here, from the bottom up. Sections 2 to 4 are the codec: what travels on an HTTP/2 connection, read and written. Section 5 is the connection itself - which streams are open, how much may be sent, what to answer - as an object that is given bytes and gives bytes back. Sections 6 and 7 are that object at work: the event-driven server speaks HTTP/2 when asked to, beside HTTP/1.1 on the same port, and the event-driven client keeps an HTTP/2 connection for each origin that agrees to one. The blocking server and the blocking client of Chapter 11 speak HTTP/1.1 only: section 8 says exactly where the line is. Section 9 is the same server speaking HTTP/3, over QUIC on UDP, to the same handlers; section 10 is the client speaking it when a request asks.

    1. What HTTP/2 changes, in one page#

    HTTP/2 (RFC 9113) carries the same requests and responses as HTTP/1.1 - the same methods, status codes and header fields - in another shape. Three things are different:

    • Everything is a frame. Nine bytes of header - a length, a type, flags, a stream number - and a payload. There is no text to parse and no line to end: a message is HEADERS frames and DATA frames.
    • Many exchanges share one connection. Each request and its response are a stream with a number; frames of different streams are interleaved, so a slow response does not hold up the ones behind it. Each stream, and the connection as a whole, has a window: how many bytes of DATA the other side has said it will take.
    • Header fields are compressed, by a scheme made for them (HPACK, RFC 7541), because the same fields are sent again with every request.

    What HTTP/1.1 said in its first line is said by pseudo-header fields, whose names begin with a colon: :method, :scheme, :authority and :path for a request, :status for a response. There is no Host (it is :authority), no Connection, no Transfer-Encoding: framing does what they did.

    A connection begins with 24 fixed bytes from the client (PROVEN_H2_PREFACE), then a SETTINGS frame from each side.

    2. Header compression#

proven_err_t proven_hpack_encode(proven_hpack_encoder_t *encoder, const proven_http_header_t *headers, proven_size_t count,

proven_err_t proven_hpack_decode(proven_hpack_decoder_t *decoder, proven_mem_view_t block,
                                 proven_http_header_t *headers, proven_size_t header_cap,
                                 proven_mem_mut_t scratch, proven_size_t max_list_bytes, proven_size_t *count);

    HPACK sends a field in one of three ways: as a number that names an entry of a fixed table of 61 common fields (:method: GET is entry 2); as a number that names an entry of the dynamic table, which holds fields this connection sent before; or as a literal - which may be added to the dynamic table as it goes, and whose text may be Huffman-coded. A request that is 65 bytes the first time is 22 the second.

    The two ends must keep the same table. Every block is decoded, in the order it was sent, by the one decoder of its connection and direction. Skip a block, or decode one twice, and every block after it means something else. That is why a decoder that meets a malformed block refuses everything afterwards, and why HTTP/2 ends the connection over it.

    The table's size is yours to set, and it is a ceiling, not a cost: 4,096 bytes by default (PROVEN_HPACK_DEFAULT_TABLE_BYTES). The memory behind it grows as entries are added

    • a few hundred bytes for a peer that sends a few short fields - to about one and a half

    times the size when the table is full. An encoder made with 0 keeps no table and is stateless; a decoder made with 0 tells the peer to keep none.

    Example: a request sent twice, a secret kept out, and a limit#

    #include <stdio.h>
#include <string.h>

/*
 * HPACK: how HTTP/2 sends header fields.
 *
 * An encoder turns a list of fields into a block of bytes; the decoder at the other end turns
 * the block back into the list. Both keep a table of fields that went before, and the second
 * time a field is sent it is one byte. The two tables must stay the same - which is why a
 * connection has exactly one encoder and one decoder in each direction, used in order.
 */

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    proven_hpack_encoder_t *encoder = NULL;
    proven_hpack_decoder_t *decoder = NULL;
    /* 4096 bytes of table is the protocol's default; each side may agree on another size. */
    EXAMPLE_REQUIRE(proven_hpack_encoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &encoder) == PROVEN_OK &&
                    proven_hpack_decoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &decoder) == PROVEN_OK, "an encoder here, a decoder there");

    // ---- a request, twice ------------------------------------------------------------
    /* Names are lowercase in HTTP/2, and what HTTP/1 put in its first line is here as fields
     * whose names begin with a colon. */
    proven_http_header_t request[] = {
        { PROVEN_LIT(":method"), PROVEN_LIT("GET") },
        { PROVEN_LIT(":scheme"), PROVEN_LIT("https") },
        { PROVEN_LIT(":path"), PROVEN_LIT("/reports/2026/october") },
        { PROVEN_LIT(":authority"), PROVEN_LIT("www.example.com") },
        { PROVEN_LIT("user-agent"), PROVEN_LIT("example-client/1.0") },
        { PROVEN_LIT("authorization"), PROVEN_LIT("Bearer 5f2c1e9a7b3d") },
    };
    proven_byte_t block[512];
    EXAMPLE_REQUIRE(proven_hpack_encode_bound(request, 6) <= sizeof block, "the block will fit");
    proven_size_t first = 0;
    EXAMPLE_REQUIRE(proven_hpack_encode(encoder, request, 6, NULL, (proven_mem_mut_t){ block, sizeof block }, &first) == PROVEN_OK, "the request, encoded");

    /* The decoder gives the fields back as views: into the block, into the fixed table, or
     * into the scratch you lend it. */
    proven_http_header_t fields[16];
    proven_byte_t scratch[1024];
    proven_size_t count = 0;
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ block, first }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK && count == 6,
                    "and decoded");
    EXAMPLE_REQUIRE(proven_u8str_view_eq(fields[2].name, PROVEN_LIT(":path")) && proven_u8str_view_eq(fields[2].value, PROVEN_LIT("/reports/2026/october")), "field for field");

    /* The same request again costs a fraction: both sides remember. */
    proven_size_t second = 0;
    EXAMPLE_REQUIRE(proven_hpack_encode(encoder, request, 6, NULL, (proven_mem_mut_t){ block, sizeof block }, &second) == PROVEN_OK, "the same request again");
    printf("the first time: %u bytes; the second: %u\n", (unsigned)first, (unsigned)second);
    EXAMPLE_REQUIRE(second < first / 2, "less than half");
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ block, second }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK && count == 6 &&
                    proven_u8str_view_eq(fields[4].value, PROVEN_LIT("example-client/1.0")), "and the decoder still gives the whole list");

    // ---- what is not remembered --------------------------------------------------------
    /* A table is a compression context, and a secret in one can be guessed from the size of
     * later blocks. So the authorization value was never put in it - by either side: */
    proven_size_t entries = proven_hpack_decoder_table_count(decoder);
    bool secret_kept = false;
    for (proven_size_t i = 0; i < entries; ++i) {
        proven_u8str_view_t name, value;
        EXAMPLE_REQUIRE(proven_hpack_decoder_table_entry(decoder, i, &name, &value), "an entry of the table");
        if (proven_u8str_view_eq(name, PROVEN_LIT("authorization"))) secret_kept = true;
    }
    printf("the table holds %u entries, %u bytes by the protocol's count\n", (unsigned)entries, (unsigned)proven_hpack_decoder_table_bytes(decoder));
    EXAMPLE_REQUIRE(entries == 3 && !secret_kept, "the path, the authority and the user agent - not the secret");
    /* Any field can be given the same treatment. */
    proven_http_header_t more[] = { { PROVEN_LIT("x-api-key"), PROVEN_LIT("k-0123456789") } };
    bool sensitive[] = { true };
    bool marked[16] = { false };
    proven_size_t n = 0;
    /* The decoder can say which fields came marked - what something that passes them on needs. */
    EXAMPLE_REQUIRE(proven_hpack_encode(encoder, more, 1, sensitive, (proven_mem_mut_t){ block, sizeof block }, &n) == PROVEN_OK &&
                    proven_hpack_decode_marked(decoder, (proven_mem_view_t){ block, n }, fields, marked, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK &&
                    proven_hpack_decoder_table_count(decoder) == 3 && marked[0], "a field marked sensitive adds nothing to the table, and arrives marked");

    // ---- a limit, and what it is for ---------------------------------------------------
    /* A block is not the size of what it says. This one is five bytes and names the same
     * remembered field five times: */
    static const proven_byte_t repeat[] = { 0xbe, 0xbe, 0xbe, 0xbe, 0xbe };       /* "entry 62" - the newest in the table */
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ repeat, sizeof repeat }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK && count == 5,
                    "five bytes, five fields");
    /* So the limit is on the decoded list - names, values, and 32 a field - not on the block.
     * Over it, the fields are withheld, but the decoder has read the block to its end and is
     * still usable: refuse the one request, keep the connection. */
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ repeat, sizeof repeat }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 100, &count) == PROVEN_ERR_OUT_OF_BOUNDS && count == 0,
                    "a list limit of 100 bytes refuses it");
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ repeat, 1 }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 100, &count) == PROVEN_OK && count == 1, "and the next block is decoded as if nothing had happened");

    /* A block that is not HPACK at all is another matter: the tables can no longer be trusted
     * to match, and the decoder says so from then on. In HTTP/2 that ends the connection. */
    static const proven_byte_t nonsense[] = { 0x80 };                            /* "entry 0": there is none */
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ nonsense, 1 }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_ERR_INVALID_FORMAT &&
                    proven_hpack_decode(decoder, (proven_mem_view_t){ repeat, 1 }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_ERR_INVALID_FORMAT,
                    "a malformed block is refused, and so is everything after it");

    // ---- the table's size is negotiated -------------------------------------------------
    /* When the peer announces a smaller table, the encoder is told, and says at the start of
     * its next block that it followed. A decoder whose own limit was lowered insists on that. */
    proven_hpack_decoder_destroy(decoder);
    EXAMPLE_REQUIRE(proven_hpack_decoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &decoder) == PROVEN_OK, "a fresh decoder");
    proven_hpack_decoder_set_max_table_bytes(decoder, 0);          /* "this side will keep no table" ... */
    proven_hpack_encoder_set_peer_table_bytes(encoder, 0);         /* ... heard by the encoder */
    n = 0;
    EXAMPLE_REQUIRE(proven_hpack_encode(encoder, request, 6, NULL, (proven_mem_mut_t){ block, sizeof block }, &n) == PROVEN_OK && block[0] == 0x20, "the next block opens by saying: table size 0");
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ block, n }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK && count == 6 &&
                    proven_hpack_decoder_table_count(decoder) == 0, "and nothing is remembered on either side");

    // ---- Huffman coding, by itself -------------------------------------------------------
    /* Literal strings are sent in a code that gives common characters fewer bits. */
    proven_u8str_view_t text = PROVEN_LIT("www.example.com");
    proven_byte_t coded[32], back[32];
    proven_size_t coded_len = 0, back_len = 0;
    EXAMPLE_REQUIRE(proven_hpack_huffman_size(text) == 12 && proven_hpack_huffman_encode(text, (proven_mem_mut_t){ coded, sizeof coded }, &coded_len) == PROVEN_OK && coded_len == 12, "fifteen characters in twelve bytes");
    EXAMPLE_REQUIRE(proven_hpack_huffman_decode((proven_mem_view_t){ coded, coded_len }, (proven_mem_mut_t){ back, sizeof back }, &back_len) == PROVEN_OK && back_len == 15 && memcmp(back, "www.example.com", 15) == 0, "and back");

    proven_hpack_encoder_destroy(encoder);
    proven_hpack_decoder_destroy(decoder);
    return EXAMPLE_OK();
}

    Cautions, and what goes wrong#

    • A block is not the size of what it says. Five bytes can name a large remembered field five times; five thousand can name it five thousand times. Always give max_list_bytes: it bounds the decoded list - names, values and 32 bytes a field, as the RFC counts - and scratch of that size is always enough.
    • Over the limit is not the end of the connection; malformed is. OUT_OF_BOUNDS means the block was read to its end, the table is in step, and only this message is refused. INVALID_FORMAT means the tables may now differ, and the decoder repeats it for ever.
    • Views, three kinds. A decoded name or value points into the block, into the library's fixed table, or into your scratch. All three must outlive your use of the fields; copy what you keep.
    • Secrets stay out of the table. A table is a compression context, and what is in one can be guessed, byte by byte, from the size of later blocks that an attacker influences. The encoder never remembers the values of authorization and proxy-authorization and sends them marked so that no hop will; it does not remember cookie and set-cookie; and sensitive extends that to any field you name. Something that passes fields on - a proxy - learns which ones arrived marked from proven_hpack_decode_marked, and gives those marks to the encoder as its sensitive.
    • What is seldom the same twice stays out too. content-length, content-range, etag, age, if-none-match and if-modified-since are sent by their name's index and not remembered: each new value would take a place in the table from a field that does repeat. (A response head whose content-length differs every time: 26 bytes and 430,000 a second with the value remembered, 13 bytes and 1,020,000 without, on one machine, encoded and decoded.)
    • Names are lowercase before they reach the encoder. It encodes what it is given; the check that a list is fit to send is section 4's.
    • One encoder, one decoder, one direction, in order. Not per request, not per stream.

    3. Frames#

    proven_err_t proven_h2_frame_parse(proven_mem_view_t data, proven_h2_frame_t *out);
proven_err_t proven_h2_frame_check(const proven_h2_frame_t *frame, proven_u32 max_frame_size, proven_h2_error_t *code, bool *stream_error);

    A frame is nine bytes and a payload:

    FieldBitsMeaning
    Length24Bytes of payload. Every endpoint accepts 16,384; more only if it said so
    Type8One of ten; anything else is skipped
    Flags8Meaning depends on the type
    Stream31 (and one reserved bit)0 is the connection itself; a client opens odd streams

    proven_h2_frame_check applies, before the payload is looked at, the rule each type has:

    TypeStreamSizeCarries
    DATArequiredanyA piece of a body. May be padded. END_STREAM ends the sender's side
    HEADERSrequiredanyA header block, or its beginning. May be padded; may carry five bytes of priority, which are skipped
    CONTINUATIONrequiredanyMore of a header block, until END_HEADERS
    RST_STREAMrequired4An error code: this stream is over
    SETTINGSmust be 0a multiple of 6; 0 with ACKIdentifier and value pairs
    PINGmust be 08Eight bytes to be sent back with ACK
    GOAWAYmust be 0at least 8The last stream acted on, an error code, text for a human
    WINDOW_UPDATEeither4How many more bytes may be sent
    PRIORITYrequired5Deprecated; checked and ignored
    PUSH_PROMISErequiredanyServer push, which this library always declines

    An error has one of two sizes. A connection error ends the connection: send GOAWAY with the code, then close. A stream error ends one stream: send RST_STREAM and go on. The check reports the code and which it is.

    Example: a connection's first bytes, read as a server reads them#

    #include <stdio.h>
#include <string.h>

/*
 * HTTP/2 frames, and the header list inside them - read here from a buffer, as a server
 * reads the first bytes of a connection.
 *
 * Nothing in h2.h holds a connection together. It reads and writes frames, applies the rule
 * each frame type has, and checks that a decoded header list is a request. Which streams are
 * open and how much may be sent is the business of whatever uses these.
 */

/* What a client would send to open a connection and ask for one page. */
static proven_size_t client_bytes(proven_allocator_t heap, proven_byte_t *wire, proven_size_t cap) {
    proven_mem_mut_t out = { wire, cap };
    proven_size_t len = 0;
    memcpy(wire, PROVEN_H2_PREFACE, PROVEN_H2_PREFACE_SIZE);       /* 24 fixed bytes come first */
    len = PROVEN_H2_PREFACE_SIZE;

    /* Then the client's settings: here, "do not push" and a larger window. */
    proven_h2_setting_t settings[] = {
        { PROVEN_H2_SETTINGS_ENABLE_PUSH, 0 },
        { PROVEN_H2_SETTINGS_INITIAL_WINDOW_SIZE, 1048576 },
    };
    if (proven_h2_write_settings(out, &len, settings, 2) != PROVEN_OK) return 0;

    /* A request is a HEADERS frame on a new stream - a client's streams are odd numbers -
     * carrying an HPACK block. END_HEADERS: the block is whole. END_STREAM: no body follows. */
    proven_http_header_t request[] = {
        { PROVEN_LIT(":method"), PROVEN_LIT("GET") },
        { PROVEN_LIT(":scheme"), PROVEN_LIT("https") },
        { PROVEN_LIT(":path"), PROVEN_LIT("/") },
        { PROVEN_LIT(":authority"), PROVEN_LIT("www.example.com") },
        { PROVEN_LIT("accept"), PROVEN_LIT("text/html") },
    };
    proven_hpack_encoder_t *encoder = NULL;
    proven_byte_t block[256];
    proven_size_t block_len = 0;
    if (proven_hpack_encoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &encoder) != PROVEN_OK) return 0;
    proven_err_t err = proven_hpack_encode(encoder, request, 5, NULL, (proven_mem_mut_t){ block, sizeof block }, &block_len);
    proven_hpack_encoder_destroy(encoder);
    if (err != PROVEN_OK) return 0;
    proven_h2_frame_t headers = { .length = (proven_u32)block_len, .type = PROVEN_H2_HEADERS,
                                  .flags = PROVEN_H2_FLAG_END_HEADERS | PROVEN_H2_FLAG_END_STREAM, .stream_id = 1 };
    if (proven_h2_frame_write(out, &len, &headers) != PROVEN_OK) return 0;
    memcpy(wire + len, block, block_len);
    len += block_len;

    /* And, for the example's sake, one frame that breaks a rule: a PING must be eight bytes. */
    proven_h2_frame_t bad_ping = { .length = 4, .type = PROVEN_H2_PING };
    if (proven_h2_frame_write(out, &len, &bad_ping) != PROVEN_OK) return 0;
    memset(wire + len, 0, 4);
    return len + 4;
}

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    proven_byte_t wire[1024];
    proven_size_t size = client_bytes(heap, wire, sizeof wire);
    EXAMPLE_REQUIRE(size > 0, "the client's bytes");

    // ---- the server's side -------------------------------------------------------------
    EXAMPLE_REQUIRE(size >= PROVEN_H2_PREFACE_SIZE && memcmp(wire, PROVEN_H2_PREFACE, PROVEN_H2_PREFACE_SIZE) == 0, "the preface: this is HTTP/2");
    proven_size_t at = PROVEN_H2_PREFACE_SIZE;

    proven_hpack_decoder_t *decoder = NULL;
    EXAMPLE_REQUIRE(proven_hpack_decoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &decoder) == PROVEN_OK, "the connection's decoder");
    int frames = 0, requests = 0;
    proven_h2_error_t refused_with = PROVEN_H2_NO_ERROR;

    while (at < size) {
        /* Nine bytes of header say how long the frame is, what it is, and whose. */
        proven_h2_frame_t frame;
        proven_err_t err = proven_h2_frame_parse((proven_mem_view_t){ wire + at, size - at }, &frame);
        if (err == PROVEN_ERR_NEED_MORE) break;                    /* a real server would read more */
        EXAMPLE_REQUIRE(err == PROVEN_OK, "a frame header");

        /* Before the payload is looked at: is this frame allowed to be what it says? The size
         * limit is the one this side announced (the protocol's smallest, here). */
        proven_h2_error_t code;
        bool stream_error;
        if (proven_h2_frame_check(&frame, PROVEN_H2_MIN_MAX_FRAME_SIZE, &code, &stream_error) != PROVEN_OK) {
            /* A real server answers GOAWAY (or RST_STREAM when only the stream is at fault). */
            refused_with = code;
            EXAMPLE_REQUIRE(!stream_error, "a PING of the wrong size ends the connection");
            break;
        }
        proven_mem_view_t payload = { wire + at + PROVEN_H2_FRAME_HEADER_SIZE, frame.length };
        EXAMPLE_REQUIRE(PROVEN_H2_FRAME_HEADER_SIZE + frame.length <= size - at, "the whole frame is here");
        frames++;

        if (frame.type == PROVEN_H2_SETTINGS) {
            proven_size_t pos = 0;
            proven_h2_setting_t setting;
            while ((err = proven_h2_settings_next(payload, &pos, &setting, &code)) == PROVEN_OK) {
                if (setting.id == PROVEN_H2_SETTINGS_INITIAL_WINDOW_SIZE) printf("the client's window: %u bytes a stream\n", (unsigned)setting.value);
                /* A setting this side does not know is simply not acted on. */
            }
            EXAMPLE_REQUIRE(err == PROVEN_ERR_EOF, "every setting was in range");
        } else if (frame.type == PROVEN_H2_HEADERS) {
            /* The header block is what is left when padding and the old priority fields are
             * taken away. (With END_HEADERS unset, CONTINUATION frames would carry the rest.) */
            proven_mem_view_t block;
            EXAMPLE_REQUIRE(proven_h2_frame_content(&frame, payload, &block) == PROVEN_OK && (frame.flags & PROVEN_H2_FLAG_END_HEADERS) != 0, "a whole header block");
            proven_http_header_t fields[32];
            proven_byte_t scratch[2048];
            proven_size_t count = 0;
            EXAMPLE_REQUIRE(proven_hpack_decode(decoder, block, fields, 32, (proven_mem_mut_t){ scratch, sizeof scratch }, 16384, &count) == PROVEN_OK, "decoded");

            /* A list of fields is not yet a request. This is where a name in capitals, a line
             * break in a value, a missing :path or a "connection" header are caught. */
            proven_h2_request_head_t head;
            EXAMPLE_REQUIRE(proven_h2_request_head(fields, count, &head) == PROVEN_OK, "a well-formed request");
            printf("stream %u: %.*s %.*s for %.*s, %u more fields\n", (unsigned)frame.stream_id, (int)head.method.size, (const char *)head.method.ptr,
                   (int)head.path.size, (const char *)head.path.ptr, (int)head.authority.size, (const char *)head.authority.ptr, (unsigned)head.field_count);
            EXAMPLE_REQUIRE(proven_u8str_view_eq(head.path, PROVEN_LIT("/")) && head.field_count == 1 && proven_u8str_view_eq(head.fields[0].name, PROVEN_LIT("accept")), "its parts");
            requests++;
        }
        at += PROVEN_H2_FRAME_HEADER_SIZE + frame.length;
    }
    EXAMPLE_REQUIRE(frames == 2 && requests == 1 && refused_with == PROVEN_H2_FRAME_SIZE_ERROR, "two frames taken, one request, and the third frame refused with FRAME_SIZE_ERROR");
    proven_hpack_decoder_destroy(decoder);

    // ---- what the server writes back -----------------------------------------------------
    proven_byte_t reply[256];
    proven_mem_mut_t out = { reply, sizeof reply };
    proven_size_t len = 0;
    static const proven_byte_t opaque[8] = { 'p', 'r', 'o', 'v', 'e', 'n', '!', '!' };
    EXAMPLE_REQUIRE(proven_h2_write_settings(out, &len, NULL, 0) == PROVEN_OK &&       /* its own settings: all defaults */
                    proven_h2_write_settings_ack(out, &len) == PROVEN_OK &&            /* "yours are in force" */
                    proven_h2_write_window_update(out, &len, 0, 1 << 20) == PROVEN_OK &&   /* a megabyte more may be sent on the connection */
                    proven_h2_write_ping(out, &len, opaque, false) == PROVEN_OK &&     /* are you there? */
                    proven_h2_write_rst_stream(out, &len, 3, PROVEN_H2_REFUSED_STREAM) == PROVEN_OK &&   /* not that stream, not now */
                    proven_h2_write_goaway(out, &len, 1, PROVEN_H2_FRAME_SIZE_ERROR, proven_mem_view_from_u8(PROVEN_LIT("a PING is eight bytes"))) == PROVEN_OK,
                    "six frames a server might send");

    /* Read back, as the client would. */
    at = 0;
    int seen = 0;
    while (at < len) {
        proven_h2_frame_t frame;
        proven_h2_error_t code;
        bool stream_error;
        EXAMPLE_REQUIRE(proven_h2_frame_parse((proven_mem_view_t){ reply + at, len - at }, &frame) == PROVEN_OK &&
                        proven_h2_frame_check(&frame, PROVEN_H2_MIN_MAX_FRAME_SIZE, &code, &stream_error) == PROVEN_OK, "each passes its own rule");
        proven_mem_view_t payload = { reply + at + PROVEN_H2_FRAME_HEADER_SIZE, frame.length };
        proven_u32 a = 0, b = 0;
        proven_mem_view_t debug;
        if (frame.type == PROVEN_H2_WINDOW_UPDATE) EXAMPLE_REQUIRE(proven_h2_read_window_update(payload, &a) == PROVEN_OK && a == 1 << 20, "the increment");
        if (frame.type == PROVEN_H2_RST_STREAM) EXAMPLE_REQUIRE(proven_h2_read_rst_stream(payload, &a) == PROVEN_OK && a == PROVEN_H2_REFUSED_STREAM && frame.stream_id == 3, "the reset");
        if (frame.type == PROVEN_H2_GOAWAY) EXAMPLE_REQUIRE(proven_h2_read_goaway(payload, &a, &b, &debug) == PROVEN_OK && a == 1 && b == PROVEN_H2_FRAME_SIZE_ERROR && debug.size == 21, "the goodbye");
        seen++;
        at += PROVEN_H2_FRAME_HEADER_SIZE + frame.length;
    }
    EXAMPLE_REQUIRE(seen == 6, "six frames read back");

    // ---- responses and trailers ----------------------------------------------------------
    proven_http_header_t response[] = { { PROVEN_LIT(":status"), PROVEN_LIT("200") }, { PROVEN_LIT("content-type"), PROVEN_LIT("text/html") } };
    proven_u16 status = 0;
    const proven_http_header_t *rest = NULL;
    proven_size_t rest_count = 0;
    EXAMPLE_REQUIRE(proven_h2_response_head(response, 2, &status, &rest, &rest_count) == PROVEN_OK && status == 200 && rest_count == 1, "a response has one pseudo-header field: its status");
    proven_http_header_t smuggle[] = { { PROVEN_LIT(":status"), PROVEN_LIT("200") }, { PROVEN_LIT("x-note"), PROVEN_LIT("fine\r\ntransfer-encoding: chunked") } };
    EXAMPLE_REQUIRE(proven_h2_response_head(smuggle, 2, &status, &rest, &rest_count) == PROVEN_ERR_INVALID_FORMAT, "a value with a line break in it is no response at all");
    proven_http_header_t trailers[] = { { PROVEN_LIT("x-checksum"), PROVEN_LIT("9f86d081") } };
    EXAMPLE_REQUIRE(proven_h2_trailers_check(trailers, 1) == PROVEN_OK, "trailers are ordinary fields");
    return EXAMPLE_OK();
}

    Cautions, and what goes wrong#

    • Check before you read. proven_h2_frame_parse cannot fail on nine bytes; whether they describe a frame that may exist is the check's answer. A frame longer than the size you announced is a connection error whatever it claims to be.
    • Flow control counts the whole payload. proven_h2_frame_content tells you where the content of a padded DATA frame is; the window is charged for the padding too.
    • A header block may span frames, and nothing else may come between them: HEADERS without END_HEADERS is followed by CONTINUATION frames of the same stream until one has it. Bound what you assemble - twice your header list limit is enough for any honest block - or a peer can make you hold as much as it cares to send.
    • Unknown is not wrong. A frame type or a setting this library does not know passes the check, as the protocol requires; skip it.
    • Settings have ranges, and a value outside one is a connection error: ENABLE_PUSH and ENABLE_CONNECT_PROTOCOL are 0 or 1, the initial window at most 2^31-1, the frame size from 16,384 to 2^24-1. ENABLE_CONNECT_PROTOCOL, once 1, may not become 0.

    4. A header list as a message#

    A decoded header list is a list of byte strings. Whether it is a request is a separate question, and the answer matters most where HTTP/2 meets HTTP/1.1: a value with a line break in it, passed on as text, becomes two header lines - a request the receiving server never saw arrive. So a list is malformed, and must be refused rather than repaired or forwarded, when:

    proven_h2_request_head applies them and hands back the parts: method, scheme, authority, path, and the ordinary fields that follow - and protocol, for an extended CONNECT (RFC 8441): :protocol with CONNECT only, and then scheme, authority and path all present. Whether one is allowed is the connection's to say: a server whose configuration has enable_connect_protocol says SETTINGS_ENABLE_CONNECT_PROTOCOL and takes them; any other refuses such a stream with PROTOCOL_ERROR, and ends its side of one it took with END_STREAM rather than a reset - a tunnel ends from both sides. A malformed message is a stream error of type PROTOCOL_ERROR: answer 400 if a response can still be sent, reset the stream if not.

    5. A connection#

    proven_err_t proven_h2_conn_create(const proven_h2_config_t *config, proven_h2_conn_t **out);
void proven_h2_conn_destroy(proven_h2_conn_t *conn);

proven_err_t proven_h2_conn_feed(proven_h2_conn_t *conn, proven_mem_view_t in, proven_size_t *consumed, proven_h2_event_t *event);
proven_mem_view_t proven_h2_conn_pending_output(const proven_h2_conn_t *conn);
void proven_h2_conn_output_sent(proven_h2_conn_t *conn, proven_size_t n);

    proven_h2_conn_t is one HTTP/2 connection, for either end. It holds everything sections 2 to 4 left to you: the settings of both sides, the streams that are open, the windows in both directions, the two compression tables, and the answer the protocol requires to each frame. It does no I/O and reads no clock. The shape is the one the TLS engine of Chapter 14 has:

       bytes the peer sent  -->  proven_h2_conn_feed  -->  one event: a request, a piece of a body, a reset, ...
   your requests, responses and bodies  -->  proven_h2_conn_submit_* / _send_data
   proven_h2_conn_pending_output  -->  bytes for the peer  -->  proven_h2_conn_output_sent

    A socket, TLS, and every timeout are the caller's. That is what makes one object serve a blocking program, an event loop and a test with no network at all - the example below is two connections handing each other buffers, and section 6 is the same object behind a socket.

    Events#

    proven_h2_conn_feed uses bytes of in until it has one event to report, and says how many it used. Call it again with the rest; PROVEN_H2_EVENT_NONE means everything was used.

    EventMeansFields

    PROVEN_H2_EVENT_DATAA piece of a body, as a view into instream_id, data, end_stream, user
    PROVEN_H2_EVENT_TRAILERSTrailer fields: the peer's side of the stream is overstream_id, fields, user

    PROVEN_H2_EVENT_GOAWAYThe peer will take no new streamcode, last_stream_id, data (the text it sent with that: the first 256 bytes, for a log)
    PROVEN_H2_EVENT_CLOSEDThe connection is over, and every stream with it. Send what is pending, then closecode

    Three things about this table are worth a second look.

    A body is never copied. A DATA event points into the buffer you fed, so a body of any size passes through in pieces no larger than your reads. A frame that arrives over three reads is three events, and end_stream is on the last.

    The peer's fault is an event, not an error. proven_h2_conn_feed returns PROVEN_OK when the peer breaks the protocol: the connection has queued a GOAWAY frame with the code, and reports PROVEN_H2_EVENT_CLOSED. A fault of one stream is PROVEN_H2_EVENT_STREAM_RESET for that stream and nothing else. The one error a feed returns for what the peer did is PROVEN_ERR_INVALID_FORMAT, on a server whose client did not begin with the 24-byte preface: that is not HTTP/2, nothing is said to it, and it is reported at the first byte that differs - so the bytes are still yours to hand to an HTTP/1.1 parser.

    Some events need no input. A stream becomes writable when output is sent, not when something arrives. So after proven_h2_conn_output_sent, call proven_h2_conn_feed once more, with an empty view, and take what is due.

    Sending#

    proven_err_t proven_h2_conn_submit_request(proven_h2_conn_t *conn, const proven_http_header_t *headers, proven_size_t count,
                                           bool end_stream, proven_u32 *stream_id);

                                            bool end_stream);

proven_err_t proven_h2_conn_reset(proven_h2_conn_t *conn, proven_u32 stream_id, proven_h2_error_t code);

    A client opens a stream with a header list that begins with the four pseudo-header fields; a server answers a stream with one that begins with :status. Both are checked by the rules of section 4 before a byte is queued, so this library does not send what it would refuse.

    proven_h2_conn_send_data may take fewer bytes than you offer, possibly none, and that is not an error. What it takes is the least of three things: the stream's window, the connection's window, and the room left under max_buffered_output. Keep the rest and offer it again when PROVEN_H2_EVENT_STREAM_WRITABLE names the stream. end_stream takes effect when all of what you offered was taken.

    When several streams wait for the connection's window, they are told in turn. A stream that is told takes what the window has; when room comes back, the search for the next one to tell goes on from the stream after it. A long body therefore does not hold up the other streams of its connection. (Before v0.37.1 it could: the search began at the same stream every time.)

    Flow control, receiving#

    void proven_h2_conn_consumed(proven_h2_conn_t *conn, proven_u32 stream_id, proven_size_t n);

    The peer may send only as much as this side has said it will take: initial_window bytes a stream, and as many for the connection as a whole. Room comes back when you say the bytes were dealt with, with proven_h2_conn_consumed - not when they arrive. A handler that falls behind and stops calling it stops its peer, having buffered at most one window. That is HTTP/2's backpressure, and it works only if this call means what it says: call it when the bytes have gone where they were going, not when you were handed them.

    What nobody consumes, the connection gives back by itself: padding, data for a stream that was reset, and whatever a stream had not consumed when it ended.

    What a peer can make a connection hold or do#

    Every amount has a setting, and every setting a default:

    SettingDefaultAt the edge
    max_concurrent_streams100A stream beyond it is refused (REFUSED_STREAM) and never reported
    initial_window65,535DATA beyond a stream's window is FLOW_CONTROL_ERROR for the stream; beyond the connection's, for the connection
    max_frame_size16,384A larger frame is FRAME_SIZE_ERROR for the connection
    max_header_list_bytes16 KiBA larger list is PROTOCOL_ERROR for its stream; a header block of more than twice this ends the connection
    header_table_bytes4,096The HPACK table in each direction; with set_header_table and 0, none
    max_buffered_output64 KiBMore body is not taken, and submit calls answer PROVEN_ERR_BUSY, until some is sent. Counted apart: the answers the protocol owes a peer that does not read them, beyond which the connection ends
    max_reset_debt100Streams reset - by the peer, or for its fault - beyond the number that finished properly: one more ends the connection with ENHANCE_YOUR_CALM
    enable_connect_protocolfalseA server: take extended CONNECT (RFC 8441) and say so in its first settings. The event-driven server sets it from http2_websocket (Chapter 15)

    The last row is the answer to a client that opens streams and resets them at once, as fast as it can, to make a server start work it then throws away. No clock is involved: a reset adds one, a stream that ends as it should takes one off, and a peer that mostly finishes what it starts never comes near the limit.

    A connection that has only opened holds one block of at most 400 bytes. One that has carried requests and is idle again holds that, a record of how its last streams ended, and the two compression tables, which grow as they are used: under 3 KiB after a hundred small requests, about 12.5 KiB when both are full at their default size of 4,096 bytes, and under 1,280 bytes with none. While streams are open it also holds 48 bytes for each, and the buffers for reading one header list: five times max_header_list_bytes, which is 80 KiB at the default. That last one need not be each connection's: give the configuration a header_buffer of proven_h2_header_buffer_size bytes and every connection driven by one thread can read into the same memory - what is read there is what an event reports, and an event is good only until the next call. The server of section 6 does this.

    Settings changed after the opening#

    proven_err_t proven_h2_conn_set_max_streams(proven_h2_conn_t *conn, proven_u32 n);
proven_err_t proven_h2_conn_set_initial_window(proven_h2_conn_t *conn, proven_u32 n);

    Two of the settings can be changed while the connection runs (v0.79.0): how many streams the peer may have open at once, and the window each stream starts with. A server under load lowers them and raises them again later. Each call queues a SETTINGS frame; RFC 9113 says a setting holds once the peer acknowledges it, and the connection keeps to that:

    • The values at creation are the ceilings. What a connection may come to hold is sized by them when it is made, so a change can lower a number and raise it back, never above: PROVEN_ERR_INVALID_ARG.
    • Until the acknowledgement, the larger number holds. A peer may open streams, or send body bytes, under the number it had before it read the change; those are taken. After the acknowledgement a stream over the new number is refused with REFUSED_STREAM (a client may send it again), and DATA beyond a stream's window is that stream's FLOW_CONTROL_ERROR.
    • Nothing open is cut. Streams already open go on, however many there are. A window change moves every open stream's window by the difference (RFC 9113 section 6.9.2): a lowering can leave a stream with less than nothing, and it then waits until enough is consumed. A raise holds at once. The connection's own window is not a setting and does not change.
    • One change in flight. A call made while one waits for its acknowledgement is kept, and the latest values go out together when it comes - one frame, however many calls.
    • On a client, max_streams is also the most this side opens, and that holds at once.

    The example below lowers both on a server and shows the client keeping to the new number.

    Goodbye#

    proven_h2_conn_shutdown with PROVEN_H2_NO_ERROR queues a GOAWAY frame and lets the open streams finish: no new stream is taken or begun, and PROVEN_H2_EVENT_CLOSED follows when the last has ended. The peer's GOAWAY is handled the same way, and a client is told which of its streams the server did not act on - PROVEN_H2_EVENT_STREAM_RESET with PROVEN_H2_REFUSED_STREAM - because those are safe to send again on another connection.

    Example: both ends of a connection, with no socket between them#

    #include <stdio.h>
#include <string.h>

/*
 * An HTTP/2 connection, both ends of it, with no socket: what one end queues is handed to the
 * other as if it had crossed a wire.
 *
 * proven_h2_conn_t does no I/O. You feed it the bytes the peer sent and it reports one event
 * at a time; you ask it to send and it queues frames for you to collect. A real program puts
 * a socket (and TLS) where carry() is.
 */

typedef struct {
    proven_h2_conn_t *conn;
    const char *name;
    /* What this end has learned, for the checks at the bottom. */
    int requests, responses, trailers, resets, writable, pongs, goaways, closed;
    proven_size_t body_bytes;
    proven_u32 last_stream, reset_code, close_code;
    bool hold;                             /* do not say that DATA was consumed */
} ex_end_t;

/* Take every event the bytes in `in` hold. One call reports one event: call again with the
 * rest until there is no event and nothing left. */
static bool take_events(ex_end_t *e, proven_mem_view_t in) {
    proven_size_t pos = 0;
    for (;;) {
        proven_size_t used = 0;
        proven_h2_event_t ev;
        if (proven_h2_conn_feed(e->conn, (proven_mem_view_t){ in.ptr + pos, in.size - pos }, &used, &ev) != PROVEN_OK) return false;
        pos += used;
        switch (ev.kind) {
            case PROVEN_H2_EVENT_NONE:
                if (pos == in.size) return true;           /* everything was used: read more */
                break;
            case PROVEN_H2_EVENT_HEADERS:
                e->last_stream = ev.stream_id;
                if (ev.status == 0) {                      /* a server: a request, already checked and taken apart */
                    e->requests++;
                    printf("%s: stream %u asks %.*s %.*s\n", e->name, (unsigned)ev.stream_id, (int)ev.request.method.size, (const char *)ev.request.method.ptr,
                           (int)ev.request.path.size, (const char *)ev.request.path.ptr);
                } else {                                   /* a client: a response head */
                    e->responses++;
                    printf("%s: stream %u answers %u%s\n", e->name, (unsigned)ev.stream_id, (unsigned)ev.status, ev.user ? " (the stream we marked)" : "");
                }
                break;
            case PROVEN_H2_EVENT_DATA:
                /* ev.data points into `in`: nothing was copied. Saying it was consumed is
                 * what lets the peer send more. */
                e->body_bytes += ev.data.size;
                if (!e->hold) proven_h2_conn_consumed(e->conn, ev.stream_id, ev.data.size);
                break;
            case PROVEN_H2_EVENT_TRAILERS: e->trailers++; break;
            case PROVEN_H2_EVENT_STREAM_RESET: e->resets++; e->reset_code = ev.code; break;
            case PROVEN_H2_EVENT_STREAM_WRITABLE: e->writable++; break;
            case PROVEN_H2_EVENT_PONG: e->pongs++; break;
            case PROVEN_H2_EVENT_GOAWAY: e->goaways++; break;
            case PROVEN_H2_EVENT_CLOSED: e->closed++; e->close_code = ev.code; return true;
        }
    }
}

/* The wire: what `from` has queued goes to `to`. Then `from` is asked once more, with
 * nothing, for what sending made due - a stream that may go on. */
static bool carry(ex_end_t *from, ex_end_t *to) {
    static proven_byte_t wire[200000];
    proven_mem_view_t out = proven_h2_conn_pending_output(from->conn);
    if (out.size > sizeof wire) return false;
    if (out.size > 0) memcpy(wire, out.ptr, out.size);
    proven_size_t n = out.size;
    proven_h2_conn_output_sent(from->conn, n);             /* a socket would say how many it took */
    if (!to->closed && !take_events(to, (proven_mem_view_t){ wire, n })) return false;
    return from->closed || take_events(from, (proven_mem_view_t){ wire, 0 });
}

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    ex_end_t client = { .name = "client" }, server = { .name = "server" };

    /* Zero means the default for every limit. `server` is the one thing that must be said. */
    proven_h2_config_t ccfg = { .alloc = heap };
    proven_h2_config_t scfg = { .alloc = heap, .server = true, .max_concurrent_streams = 10 };
    EXAMPLE_REQUIRE(proven_h2_conn_create(&ccfg, &client.conn) == PROVEN_OK && proven_h2_conn_create(&scfg, &server.conn) == PROVEN_OK, "two ends");

    /* The opening is already queued: the client's preface and both ends' settings. */

     * peer (GOAWAY), reports that it is over, and takes nothing more. */

    EXAMPLE_REQUIRE(proven_h2_conn_pending_output(strict.conn).size > 0, "with a GOAWAY still to be sent before the socket is closed");

                    "HTTP/1.1 is PROVEN_ERR_INVALID_FORMAT with nothing taken: the bytes are yours to give to something else");

    proven_h2_conn_shutdown(server.conn, PROVEN_H2_NO_ERROR);          /* no new streams; open ones would finish first */

    proven_h2_conn_destroy(server.conn);

    Cautions, and what goes wrong#

    • After every call, send what is pending. The connection answers by itself - acknowledgements, window updates, resets, the last GOAWAY - and those answers are in proven_h2_conn_pending_output whether or not you asked for anything.
    • After sending, feed nothing. proven_h2_conn_feed with an empty view collects what sending made due. A driver that waits for the socket instead will wait for a peer that is itself waiting.
    • proven_h2_conn_send_data returning 0 is not the end of the world, nor of the stream. It is "not now". The exception is an empty data with end_stream: that always goes out, and 0 then means "ended".
    • Views die at the next call. The fields of an event, and the pending output, are good until the next call that takes the connection. Copy what you keep.
    • The pointer comes with the event. When a stream ends, proven_h2_conn_stream_user no longer finds it: the last event for the stream carries the pointer in user, and that is where to free what it points to.
    • PROVEN_H2_EVENT_CLOSED ends every stream without saying so one by one. Walk your own list of what was open.
    • A response that ends before its request tells the client to stop. The server's side sends RST_STREAM with NO_ERROR, as RFC 9113 provides, and the stream is over. A client sees PROVEN_H2_EVENT_STREAM_RESET with PROVEN_H2_NO_ERROR after the response: not a failure, and the event's end_stream is true. Some servers reset with NO_ERROR in place of ending the stream, after every byte the response's content-length declared; the length shows nothing is missing, and end_stream is true then too. One byte short, with no length (or a length that describes no body: HEAD, 204, 304), or with any other code, it is false: the response may be cut short.
    • A connection is for one thread at a time.
    • No clock means no timeouts. A peer that opens a connection and says nothing, or never opens a window, is the caller's to give up on.

    /* ... everything Chapter 15 describes ... */

    The event-driven server of Chapter 15 speaks HTTP/2 when its configuration says http2. Nothing else changes for a handler: the same four callbacks, the same proven_http_stream_* calls, the same request type. What was one exchange on a connection is now one stream of many, and the server does the translating:

    proven_http_stream_protocol answers 1 or 2 (3 for HTTP/3, section 9), for a log line; a handler seldom has another reason to ask.

    Which protocol a connection speaks#

    • Over TLS, the handshake says (ALPN). The TLS configuration must offer h2 - and http/1.1 after it, for clients that have nothing newer - when http2 is on, and must not offer h2 when it is off: the server refuses at creation a pair that could agree in the handshake to something it would then not speak. A connection that negotiated h2 on TLS older than 1.2, or on a 1.2 suite without forward secrecy and authenticated encryption - possible only with the legacy options of Chapter 14 switched on - is ended with INADEQUATE_SECURITY, as RFC 9113 requires.
    • 0-RTT, when the TLS configuration has early_data (chapter 14, section 6; v0.84.0), as for HTTP/1.1 and HTTP/3: a request whose HEADERS arrived in the client's early data reaches its handler before the handshake is over, with proven_http_stream_early true, and may be answered at once; only GET, HEAD and OPTIONS without a body get that far - anything else that arrives early is answered 425 on its stream by the server.
    • In the clear, the first bytes say. A client that knows it wants HTTP/2 begins with the 24-byte preface (curl's --http2-prior-knowledge); anything else is HTTP/1.1. The server decides at the first byte that differs, so POST, which shares the preface's first letter, is HTTP/1.1 at its second. Upgrade: h2c is not offered: RFC 9113 removed it.

    Both protocols are served on one port, by one handler, at the same time.

    max_concurrent_streams can be changed while the server runs (v0.79.0), from the loop's thread: 1 to the configured value, which stays the ceiling. Each HTTP/2 connection says the new number to its client (section 5's proven_h2_conn_set_max_streams), and a connection made later opens with it. Requests already running go on; until a client acknowledges, it may still begin requests under the number before. HTTP/3 has its own rule (section 9). To take no new requests at all, shut the server down instead: 0 is PROVEN_ERR_INVALID_ARG.

    proven_http_event_server_set_window (v0.82.0) does the same for request bodies: from the loop's thread, n becomes a ceiling on what a client may send ahead of the handler, on a stream and on a connection, HTTP/2 and HTTP/3, for the connections open and those to come. Room is given back only up to it - what the client may still send and what the server holds unread, together - and windows that grow (http2_window_bytes left 0) stop at it, growing again when it is raised. A configured window stays the most a protocol gives. What was granted stands: an HTTP/2 window said lower holds once the client acknowledges it, and HTTP/3 credit cannot be taken back, so a lower ceiling shows as what is outstanding is used up. Each HTTP/2 connection says min(n, its window) as its initial window (section 5's proven_h2_conn_set_initial_window). On an HTTP/3 connection open now a stream the client opens later may still use the window promised in the handshake; connections made later are promised at most n.

    proven_http_event_server_stop_listening is the graceful way to end: each HTTP/2 connection is sent GOAWAY, finishes the streams it has, and closes. proven_http_event_server_destroy ends everything at once, and every open stream's handler gets on_done(PROVEN_ERR_RESET).

    Example: one port, one handler, both protocols#

    #include <stdio.h>
#include <string.h>

/*
 * One server, one port, both protocols: the event-driven HTTP server with `http2` on.
 *
 * The handler below is an ordinary one - the same callbacks, the same stream calls - and does
 * not know which protocol a request came by unless it asks. An HTTP/1.1 client and an HTTP/2
 * client then talk to it on the same port. The HTTP/2 client here is the connection engine of
 * this chapter's section 5 with a socket put through it, to show what one is made of: forty
 * lines. (The library's own, which keeps connections and shares them, is section 7's.)
 */

typedef struct { proven_loop_t *loop; int served, over_http2; } ex_app_t;

static void on_request(void *ctx, proven_http_stream_t *stream, const proven_http_request_t *head) {
    ex_app_t *app = ctx;
    /* The request looks the same either way: a method, a target, fields - Host among them,
     * which HTTP/2 carries as `:authority` and the server hands on under its usual name. */
    /* With `early_data` in the TLS configuration, a request may come as early data (chapter 14,
     * section 6) and may be a copy an attacker replayed. This answer is safe to give
     * twice; a handler whose request is not answers 425 and the client sends it again later. */
    if (proven_http_stream_early(stream) && head->method != PROVEN_HTTP_GET) {
        (void)proven_http_stream_respond(stream, 425, NULL, 0, (proven_mem_view_t){ 0 });
        return;
    }
    const int protocol = proven_http_stream_protocol(stream);
    char text[96];
    int n = snprintf(text, sizeof text, "%.*s over HTTP/%d\n", (int)head->target.size, (const char *)head->target.ptr, protocol);
    proven_http_header_t fields[] = { { PROVEN_LIT("Content-Type"), PROVEN_LIT("text/plain") } };
    if (proven_http_stream_respond(stream, 200, fields, 1, (proven_mem_view_t){ (const proven_byte_t *)text, (proven_size_t)n }) != PROVEN_OK) return;
    if (protocol == 2) app->over_http2++;
}

static void on_done(void *ctx, proven_http_stream_t *stream, proven_err_t why) {
    (void)stream;
    if (why == PROVEN_OK) ((ex_app_t *)ctx)->served++;
}

static void run(void *arg) { (void)proven_loop_run(((ex_app_t *)arg)->loop); }

/* An HTTP/2 client in miniature: the engine, a socket, and a loop that moves bytes between
 * them until every stream it asked for has ended. Returns how many were answered 200. */
static int ask_three(proven_u16 port, char answers[3][64]) {
    proven_net_conn_t sock;
    if (proven_net_connect(proven_net_addr_loopback(PROVEN_NET_FAMILY_IPV4, port), proven_net_deadline_in(5000), &sock) != PROVEN_OK) return -1;

    /* The engine reads header lists into memory it allocates while streams are open - or into
     * memory of yours, which several connections on one thread may share. */
    static proven_u64 header_room[16384];
    proven_h2_config_t config = { .alloc = proven_heap_allocator(), .header_buffer = { (proven_byte_t *)header_room, sizeof header_room } };
    proven_h2_conn_t *conn = NULL;
    if (proven_h2_header_buffer_size(0) > sizeof header_room || proven_h2_conn_create(&config, &conn) != PROVEN_OK) { (void)proven_net_close(&sock); return -1; }

    /* Three requests at once, on the one connection: streams 1, 3 and 5. */
    static const char *const paths[3] = { "/first", "/second", "/third" };
    for (int i = 0; i < 3; i++) {
        proven_http_header_t request[] = {
            { PROVEN_LIT(":method"), PROVEN_LIT("GET") }, { PROVEN_LIT(":scheme"), PROVEN_LIT("http") },
            { PROVEN_LIT(":authority"), PROVEN_LIT("localhost") }, { PROVEN_LIT(":path"), proven_u8str_view_from_cstr(paths[i]) },
        };
        proven_u32 stream = 0;
        if (proven_h2_conn_submit_request(conn, request, 4, true, &stream) != PROVEN_OK) { proven_h2_conn_destroy(conn); (void)proven_net_close(&sock); return -1; }
    }

    int ended = 0, ok = 0;
    static proven_byte_t in[16384];
    while (ended < 3) {
        /* Whatever the engine has queued - the preface and settings, the requests, later its
         * acknowledgements - goes to the socket first. */
        proven_mem_view_t out = proven_h2_conn_pending_output(conn);
        if (out.size > 0) {
            if (proven_net_write_all(&sock, out, proven_net_deadline_in(5000)).err != PROVEN_OK) break;
            proven_h2_conn_output_sent(conn, out.size);
        }
        proven_result_size_t got = proven_net_read(&sock, (proven_mem_mut_t){ in, sizeof in }, proven_net_deadline_in(5000));
        if (got.err != PROVEN_OK) break;
        proven_size_t pos = 0;
        for (;;) {
            proven_size_t used = 0;
            proven_h2_event_t ev;
            if (proven_h2_conn_feed(conn, (proven_mem_view_t){ in + pos, got.value - pos }, &used, &ev) != PROVEN_OK) { ended = 3; break; }
            pos += used;
            const proven_u32 k = ev.stream_id ? (ev.stream_id - 1) / 2 : 0;     /* stream 1, 3, 5 -> 0, 1, 2 */
            if (ev.kind == PROVEN_H2_EVENT_HEADERS && ev.status == 200 && k < 3) ok++;
            if (ev.kind == PROVEN_H2_EVENT_DATA && k < 3) {
                snprintf(answers[k], 64, "%.*s", (int)(ev.data.size < 63 ? ev.data.size : 63), (const char *)ev.data.ptr);
                proven_h2_conn_consumed(conn, ev.stream_id, ev.data.size);
            }
            if ((ev.kind == PROVEN_H2_EVENT_DATA || ev.kind == PROVEN_H2_EVENT_HEADERS) && ev.end_stream) ended++;
            if (ev.kind == PROVEN_H2_EVENT_STREAM_RESET || ev.kind == PROVEN_H2_EVENT_CLOSED) { ended = 3; break; }
            if (ev.kind == PROVEN_H2_EVENT_NONE && pos == got.value) break;
        }
    }
    proven_h2_conn_destroy(conn);
    (void)proven_net_close(&sock);
    return ok;
}

    Cautions, and what goes wrong#

    • A handler that keeps its place across on_writable is safe, as it was. on_writable is never called from inside a call the handler itself made - a write that called back into the same handler would send the same bytes twice. This is the server's promise for both protocols; on HTTP/2 it took a defect to find (section 8).
    • max_buffered_output is per connection, not per stream. One slow client with a hundred streams holds what one HTTP/1.1 client would, not a hundred times it.
    • A client that does not read is not read from. A response's head is always queued - the server has nowhere else to keep it - so what bounds a client that asks and never reads is that, while twice max_buffered_output waits for it, the server takes nothing more from that connection: further requests stay in the socket, as a pipelined request does on HTTP/1.1 while a response is owed. The most a connection then holds as output is twice max_buffered_output and one head for each stream that was open - at most max_concurrent_streams of them, each the size its handler made it. A client that uploads without reading its other responses therefore stops being read, and resumes when it reads.
    • An idle HTTP/2 connection is larger than an HTTP/1.1 one, by what it has been sent. HTTP/1.1's is 480 bytes. HTTP/2's is 2,360 bytes after one small request, and grows with the header fields its client has made it remember, to about 12.8 KiB when both compression tables are full: ten thousand idle connections are between 22 and 128 MiB. http2_header_table_bytes lowers the ceiling and http2_no_header_table removes it (under 2 KiB, always; on Windows x64, whose loop socket holds an OVERLAPPED, 2,048 bytes), at the price of sending every field in full every time. The buffer for reading header lists - 80 KiB - is one for the whole server, not one each. A request in progress adds about 210 bytes: 160 in the server, 48 in the connection.
    • A handler that answers before the request has ended is done with it. The server tells the client to stop sending (section 5), and what was already on its way is dropped unread - including a frame that would have been an error. If the body matters, answer when it has arrived.
    • WebSocket needs HTTP/1.1. An upgrade is refused on an HTTP/2 stream (PROVEN_ERR_UNSUPPORTED): a browser that wants a WebSocket opens an HTTP/1.1 connection for it, which the same port accepts.
    • Trailers are not passed on, in either direction, as they are not on HTTP/1.1: a request's trailers end its body and are dropped.

    7. HTTP/2 in the event-driven client#

    typedef struct {
    /* ... everything Chapter 15 describes ... */
    bool http2;
    bool http2_cleartext;
    proven_u32 idle_timeout_ms;
    proven_size_t max_waiting_requests;
} proven_http_event_client_config_t;

int proven_http_event_request_protocol(const proven_http_event_request_t *request);

    The event-driven client of Chapter 15 is, for HTTP/1.1, one connection to a request. With http2 it keeps a connection for each origin that agrees to HTTP/2 and puts every request to that origin on it: a hundred requests to one server are one handshake, not a hundred. The callbacks and the proven_http_event_request_* calls are the same; so is what start promises - everything the options point to is copied or used before it returns, and on_done comes exactly once, never from inside start.

    • Over TLS, http2 and a TLS configuration that offers h2 (and http/1.1 after it): the handshake with each origin decides. An origin that chooses HTTP/1.1 is remembered as such and served one connection to a request, as before. (The last 64 such origins are remembered, at about 600 bytes each; one that has been forgotten costs a handshake to learn again.) With early_data in the TLS configuration and a session made over h2, a new connection begins HTTP/2 inside its first flight: the preface, the settings and one request that is GET, HEAD or OPTIONS without a body go as early data (chapter 14, section 6; v0.84.0), the rest after the handshake. What the server refused goes again, as it was; a 425 sends the request once more on the same connection, now that it is up.
    • In the clear, http2_cleartext: every http request of that client is HTTP/2 by prior knowledge. There is no way to ask a server in the clear, so say this only of servers you know; a client that talks to both kinds in the clear is two clients. Said of a server that does not speak it, it ends every request with PROVEN_ERR_UNSUPPORTED: the connection was made, and it ended - on bytes that were not HTTP/2, or with none at all - before the server's settings, which are the first sign that a server in the clear is an HTTP/2 server. Nothing is sent ahead of them, so no such request was acted on; but starting it again would end the same way, which is why the answer is not PROVEN_ERR_AGAIN. (It was, until v0.35.0.) A server that was only restarting at that moment gets the same answer: if you know that it speaks HTTP/2, start the request again.

    A request may wait, where an HTTP/1.1 request never did: for the connection, while it is being made; for the server's first word, which says how many streams it allows - nothing is sent ahead of that, so nothing is refused for it; and for a free stream, when the server's limit is reached. A waiting request holds a copy of what it was started with. At most max_waiting_requests (1,000) wait for one connection; the next start is PROVEN_ERR_BUSY. And, with max_connections set and every connection in use, a request to an origin that has no connection waits for the client to have room for one - on no connection, as many again at most, and for connect_timeout_ms at most (Chapter 15).

    What on_done says is what it said, with two more answers. PROVEN_ERR_AGAIN, for a request that an HTTP/2 server did not act on - it said goodbye first, or refused the stream, or the connection was lost before the request was sent. Such a request may be started again, whatever its method; the client does not do so by itself unless retry_unsent says how many times it may (below). PROVEN_ERR_UNSUPPORTED, for a request to a server in the clear that turned out not to speak HTTP/2 (http2_cleartext, above): not acted on either, and not worth starting again. PROVEN_ERR_RESET still means "it may have been acted on" - but a server that resets a stream with NO_ERROR once every byte of the response's declared content-length has arrived has answered in full, and that is PROVEN_OK, with the whole body (section 5 says which resets count). Over TLS there is no PROVEN_ERR_UNSUPPORTED: the handshake settles the protocol, and a server that agrees to HTTP/1.1 is spoken to in HTTP/1.1.

    Example: three requests, one connection#

    #include <stdio.h>
#include <string.h>

/*
 * The event-driven client speaking HTTP/2: three requests, one connection.
 *
 * Client and server sit on one loop here, driven by hand, so the example needs no thread. The
 * client's callbacks are the ones an HTTP/1.1 program has; what differs is underneath - the
 * client keeps a connection for the origin and puts every request to it on that connection.
 */

typedef struct { int answered, over_http2; char text[3][32]; bool done[3]; } ex_seen_t;
typedef struct { ex_seen_t *seen; int which; } ex_call_t;

static void serve(void *ctx, proven_http_stream_t *stream, const proven_http_request_t *head) {
    (void)ctx;
    (void)proven_http_stream_respond(stream, 200, NULL, 0, (proven_mem_view_t){ head->target.ptr, head->target.size });     /* its own path, back */
}

static void on_response(void *ctx, proven_http_event_request_t *request, const proven_http_response_t *head) {
    ex_call_t *call = ctx;
    /* 2 here; 1 for a request that is still waiting for its connection, or whose server
     * turned out to speak only HTTP/1.1. */
    if (head->status == 200 && proven_http_event_request_protocol(request) == 2) call->seen->over_http2++;
}

static void on_body(void *ctx, proven_http_event_request_t *request, proven_mem_view_t piece, bool last) {
    (void)request; (void)last;
    ex_call_t *call = ctx;
    snprintf(call->seen->text[call->which], sizeof call->seen->text[0], "%.*s", (int)piece.size, (const char *)piece.ptr);
}

static void on_done(void *ctx, proven_http_event_request_t *request, proven_err_t why) {
    (void)request;
    ex_call_t *call = ctx;
    call->seen->done[call->which] = true;
    if (why == PROVEN_OK) call->seen->answered++;
}

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    proven_loop_t *loop = NULL;
    EXAMPLE_REQUIRE(proven_loop_create(heap, &loop) == PROVEN_OK, "a loop");

    /* A server that speaks both protocols (section 6). */
    proven_http_event_server_config_t server_config = { .on = { .on_request = serve }, .http2 = true };
    proven_http_event_server_t *server = NULL;
    proven_net_addr_t at;
    EXAMPLE_REQUIRE(proven_http_event_server_create(loop, &server_config, &server) == PROVEN_OK &&
                    proven_http_event_server_listen(server, proven_net_addr_loopback(PROVEN_NET_FAMILY_IPV4, 0), &at) == PROVEN_OK, "a server");

    /* In the clear there is no handshake to ask in, so the client is told: every `http`
     * request of this client is HTTP/2. Over TLS it is `http2` instead, with a TLS
     * configuration that offers "h2", and the handshake decides for each origin. */
    proven_http_event_client_config_t client_config = { .alloc = heap, .http2_cleartext = true };
    proven_http_event_client_t *client = NULL;
    EXAMPLE_REQUIRE(proven_http_event_client_create(loop, &client_config, &client) == PROVEN_OK, "a client");

    ex_seen_t seen = { 0 };
    ex_call_t calls[3] = { { &seen, 0 }, { &seen, 1 }, { &seen, 2 } };
    static const char *const paths[3] = { "/first", "/second", "/third" };
    for (int i = 0; i < 3; i++) {
        char url[64];
        snprintf(url, sizeof url, "http://127.0.0.1:%u%s", (unsigned)at.port, paths[i]);
        proven_http_event_request_options_t request = {
            .url = proven_u8str_view_from_cstr(url),
            .on = { .on_response = on_response, .on_body = on_body, .on_done = on_done }, .ctx = &calls[i],
        };
        /* Started at once, before there is a connection: the first makes it, the others wait
         * for it, and all three go out together when the server has said what it allows. */
        EXAMPLE_REQUIRE(proven_http_event_client_start(client, &request, NULL) == PROVEN_OK, "a request is started");
    }
    EXAMPLE_REQUIRE(proven_http_event_client_requests(client) == 3, "three are under way");

    proven_net_deadline_t until = proven_net_deadline_in(5000);
    while (!(seen.done[0] && seen.done[1] && seen.done[2]) && proven_time_monotonic_now() < until)
        EXAMPLE_REQUIRE(proven_loop_poll(loop, proven_net_deadline_in(10)) == PROVEN_OK, "a round of the loop");

    for (int i = 0; i < 3; i++) printf("%s\n", seen.text[i]);
    EXAMPLE_REQUIRE(seen.answered == 3 && seen.over_http2 == 3, "all three were answered, over HTTP/2");
    EXAMPLE_REQUIRE(strcmp(seen.text[0], "/first") == 0 && strcmp(seen.text[1], "/second") == 0 && strcmp(seen.text[2], "/third") == 0, "each with its own answer");
    EXAMPLE_REQUIRE(proven_http_event_server_connections(server) == 1, "and the server saw one connection, not three");

    proven_http_event_client_destroy(client);
    proven_http_event_server_destroy(server);
    proven_loop_destroy(loop);
    return EXAMPLE_OK();
}

    Cautions, and what goes wrong#

    • A request's object does not change under you. One that was started while its origin was unknown, and whose origin turned out to speak HTTP/1.1, is still the pointer start gave you; proven_http_event_request_protocol then answers 1.
    • A request that waits can time out before it is sent: connect_timeout_ms covers the connection it is waiting for. One that waits for a free stream has no clock of its own - it is the requests ahead of it that are being timed.
    • Pause holds at most one window, as on the server: the client stops telling the server that it has consumed, and the server stops sending.

    • PROVEN_ERR_AGAIN is not retried for you, unless you ask. retry_unsent is a number: how many times the client itself puts to the server again a request that would end that way - one behind a goodbye, one whose stream was refused, one waiting on a connection that was lost. It goes on the same connection when one stream was refused and the connection goes on, and otherwise on another for the same origin, which is made if there is none; requests that move together keep their order; you are told nothing of the try that failed, and on_done comes once, for the last. Zero, the default, is none: the caller decides. What the setting does not cover, and what it costs:

      • Not a request whose body is written in pieces - the client does not have the pieces to send again - and not after on_response: you have seen an answer begin.
      • Not PROVEN_ERR_UNSUPPORTED, which would end the same way again, nor PROVEN_ERR_RESET, which the server may have acted on, nor a time limit.
      • At once, with no delay. A server that refuses a stream because it is busy is asked again in the same moment; a small number is a few moments. A program that wants to wait between tries leaves the setting at zero and starts the request again itself.
      • The time limits are each try's: a request may take connect_timeout_ms or response_timeout_ms once for every try it has.
      • A body held in memory stays in memory until the response begins, not only until it has been sent.
      • A try that fails for another reason ends the request with that reason. If the new connection cannot be made, on_done says PROVEN_ERR_REFUSED, not PROVEN_ERR_AGAIN.
    • One connection is one point of failure. When it ends, every request on it ends with it - PROVEN_ERR_AGAIN for those not yet sent, PROVEN_ERR_RESET for the others (and PROVEN_ERR_UNSUPPORTED for all of them when, in the clear, it never was HTTP/2).

    8. What is accepted, what is not here, and how this was tested#

    What the decoder accepts is HPACK as RFC 7541 defines it. Any number of table size updates at the start of a block (the RFC promises at most two); integers of up to five continuation bytes; a literal's Huffman padding of up to seven one bits and nothing else.

    What the encoder writes is valid HPACK that makes the common choices: a table reference where there is one, Huffman coding where it is shorter (not where it is the same length), new fields added to the table unless they are secrets or larger than it.

    What a connection accepts is RFC 9113, with these choices where the RFC leaves one: the deprecated priority fields are ignored, except that a stream said to depend on itself is an error of that stream, as RFC 7540 had it; a frame for a stream that this side reset is dropped without comment for as long as the reset is among the last max_concurrent_streams endings it remembers; a header list over the limit is an error of its stream, not of the connection; content-length that disagrees with the body is an error of the stream; a response to HEAD, and one with status 204 or 304, may announce a length it does not carry.

    Not here:

    • HTTP/2 in the blocking server and the blocking client of Chapter 11: one thread to a connection suits one exchange at a time, which is HTTP/1.1.
    • A retry with a delay, or of anything but what the server did not act on: the event-driven client reports such a request (PROVEN_ERR_AGAIN) and, when retry_unsent is set, puts it again at once, so many times. Waiting between tries, and trying again what may have been acted on, are its caller's.
    • Trailers in the event-driven server, for either protocol.
    • Extended CONNECT (RFC 8441, WebSocket over HTTP/2) and the SETTINGS it needs.
    • Server push: PUSH_PROMISE is recognised so that it can be refused.
    • Priorities (RFC 7540's scheme, which RFC 9113 deprecated): skipped.
    • Upgrade: h2c, which RFC 9113 removed. (HTTP/3 is sections 9 and 10.)
    • The never-indexed mark on a decoded field: a proxy would pass it on; nothing here does.

    How this was tested. The static table and the Huffman code are not typed in: a private program reads them from the published text of RFC 7541, and stops unless there are 61 entries and 257 codes that are prefix-free and fill the code space exactly; the registered test checks the same of the table it is linked with. That test then replays all sixteen examples of the RFC's Appendix C through the decoder, comparing the dynamic table with the RFC's after each; has the encoder reproduce, byte for byte, the examples whose choices it shares; refuses thirteen kinds of malformed block; holds each limit; and decodes every beginning and every single-bit change of the RFC's blocks. A second test tries each frame type's rule on both sides of its edge and thirty-one malformed requests. Outside the registered tests: this decoder read 47,142 blocks that fourteen other implementations produced for the same header lists (nghttp2, Go, Node, Python, Haskell and Swift encoders, including sequences in which the table size changes); Node's HTTP/2 server, which is nghttp2, decoded every block this encoder wrote for 1,290 requests on shared connections; and five million damaged blocks were decoded under tools that report any read or write outside a buffer, with none reported.

    The connection has a registered test of its own. Two connections are wired together in memory and carry bodies of nine sizes through three window sizes, a byte at a time and in bulk, fifty streams at once, and a head of 40,000 bytes that leaves as three frames. A hundred and one scripted conversations each break one rule of RFC 9113, or stand just inside it, and the connection is held to the verdict the RFC names - ignored, an error of the stream with its code, an error of the connection with its code - once with the bytes in one piece and once a byte at a time. Each bound of section 5 is driven to its edge from both sides. A recorded conversation is replayed 12,214 times to a fresh connection in each role - cut short at every point near its start and at intervals after, or with one bit changed; and every allocation of a conversation is made to fail once. Outside the registered tests, through a private program that moves a socket through the connection: Node's HTTP/2 client and server (nghttp2) and curl exchanged requests, bodies up to 5 MB, heads of 20,000 bytes, trailers, interim responses, cancellations and settings changes with it in both roles, under twelve combinations of settings - 7,896 checks, none failed; and 5,000,230 random frames over 140,108 connections, with an application acting at random, broke none of the connection's invariants under the same tools.

    The server of section 6 has its own registered test: the handlers of an HTTP/1.1 server, unchanged, answering a client made of this library's connection over real sockets - in the clear, over TLS 1.3 and over TLS 1.2 - with bodies both ways, sixty streams at once, compression, pause, resets from either side, a client that closes its sending side and is still answered, limits, each timeout, goodbye, and HTTP/1.1 clients on the same port throughout. Outside the registered tests, a private program serves both protocols on one port to Node's http2, http and https clients and to curl in five modes: 7,392 checks, none failed in the end. One did at first: two large responses side by side to Node over TLS stalled, because the server called on_writable from inside the handler's own write and the handler, re-entered, lost its place. This library's own client had not provoked it. The registered test now holds the handler to "never re-entered", with two streams racing.

    h2spec, the conformance suite for HTTP/2 servers (version 2.6.0, 146 cases), was run against that server: 146 of 146 over TLS, and 145 of 146 in the clear. The one is "an invalid connection preface must end the connection": in the clear, bytes that are not the preface are not HTTP/2 here but HTTP/1.1, and are answered as such. Its first run found two things: a handler had no way to tell that a body with no announced length was coming (it now sees Transfer-Encoding: chunked), and a stream that depends on itself was not refused.

    The client of section 7 has a registered test against the server of section 6 on one loop - in the clear and over TLS: forty requests on one connection, bodies both ways, compression, pause, abort, the server's limit on streams, each timeout, an idle connection let go, and an origin that turns out to speak only HTTP/1.1, whose waiting requests are served as HTTP/1.1 by the objects their caller already held. Outside the registered tests, a private program ran the client against Node's HTTP/2 servers over TLS and in the clear under four sets of server settings, and against an HTTPS server with no HTTP/2: 1,156 checks, none failed in the end. Fifteen did at first: against a server that allows four streams, a burst of requests on a new connection went out before the server had said so, and the surplus came back refused. The client now sends nothing ahead of the server's settings.

    What the registered tests did not find, once more. When the server was first made to hold its output for the length of a read (the table below is what that bought), a burst of whole-body responses filled the connection's output and the responses that began after them were reset for want of room. Every registered test passed. Node's client, in the private checks, had 945 of 7,392 fail. The hold now ends when a quarter of max_buffered_output is queued, a whole body leaves the room that heads need, and a registered test sends a hundred requests in one write to a server whose bound is smaller than their heads; the private checks were then run again in full - 7,896, 7,392 and 1,156 against Node and curl, h2spec as before - and none failed.

    Speed, measured once, with no socket: two connections in memory on one core of a 3.5 GHz x86-64 processor, GCC -O2. A request head of twelve fields (299 bytes as literals) is Huffman-decoded 680,000 times a second, 204 MB/s; 385,000 requests a second are sent, decoded, answered with a head and read back, a hundred in flight; and bodies cross at 2.4 GB/s. These are the protocol's costs alone - a socket, TLS and a handler all cost more.

    Speed over a socket, measured once: the load of Chapter 15, section 14, made again for HTTP/2 against the same server on the same machine - a load program that is not part of the test suite, client and server in two processes over the loopback interface, in the clear, one loop, a handler that answers two bytes, ten seconds a row. Every connection makes one request and is left open; then some of them keep a number of requests in flight. The HTTP/1.1 rows were made the same day against the same server process, for comparison.

A connection finds a stream in one step by a map from its number, which holds two slots for every place in the stream table; a stream that arrives to find its slot taken - by one open far longer than its neighbours - is found by walking the table, and a peer that arranges that on purpose makes the connection walk its table as it did before there was a map, and do nothing worse.

    9. HTTP/3 in the event-driven server#

    typedef struct {
    /* ... everything Chapter 15 describes, and section 6's fields ... */
    bool http3;
    bool http3_retry;
    proven_size_t http3_window_bytes;
} proven_http_event_server_config_t;

    HTTP/3 (RFC 9114) is HTTP over QUIC (RFC 9000): a transport on UDP with its own streams, flow control, loss recovery and congestion control, and TLS 1.3 inside it rather than under it. Its header compression is QPACK (RFC 9204), HPACK's successor. What it gives over HTTP/2 is that a lost packet holds up only its own stream, and that the transport and TLS handshake take one round trip together. All of it is this library's own code.

    With http3 on, the server of section 6 speaks it too. Handlers still do not change: section 6's table holds for HTTP/3 as written for HTTP/2, with QUIC's flow control where it says the client's windows, and proven_http_stream_protocol answers 3. What is different is underneath:

    • Each listen opens a UDP socket as well, on the same address and port as its TCP listener; a listen whose UDP socket cannot be had fails, and the TCP listener is closed again. At port 0 a UDP port already in use under the number TCP was given is not a failure: another number is tried, up to 17 in all. HTTP/3 is over TLS only: the TLS configuration must offer h3 (beside h2 and http/1.1), and must not when http3 is off. Over QUIC the server agrees h3 alone, whatever else the list offers over TCP and in whatever order (RFC 9114 section 3.1); a QUIC client that does not offer it ends with no_application_protocol. Before version 0.73.2 the server took its own first choice that the client offered, so this library's client and server agreed h2 over QUIC and spoke HTTP/3 under it.
    • How a client finds it. HTTP/1.1 and HTTP/2 responses carry Alt-Svc: h3=":PORT" - the port the connection came in on - unless the handler wrote an Alt-Svc of its own, which is sent instead. A browser, or curl --alt-svc, tries HTTP/3 on its next request; curl --http3-only asks for it at once.
    • One socket, many connections. QUIC connections are told apart by their connection IDs, not by sockets: a datagram goes to the connection whose ID it carries, a client's first packet makes one, and a short packet for an ID nobody holds is answered with a stateless reset.
    • What bounds a write is QUIC's send buffer - 256 KiB a stream and 1 MiB a connection of data sent and not yet acknowledged, or, within what the client has granted, twice the congestion window, up to 16 MiB and 24 MiB - not max_buffered_output. A refused write is told on_writable as on the other two.
    • A paused request stops being read, and QUIC's flow control stops the client at http3_window_bytes: by default 256 KiB a stream and 1 MiB a connection to begin with, grown - doubling while bodies are read as fast as they come - up to 16 MiB and 24 MiB; a body that is not read stops the growth, so a paused one holds no more than the window it had (v0.71.0). The send buffers grow with what the path carries (twice the congestion window), within what the peer has granted, up to the same caps.

    Goodbye is two GOAWAYs a round trip apart (RFC 9114 section 5.2): the first names the largest request a client may still send, so that one already on its way is answered and not refused; the second names the first request not acted on, and the connection closes with H3_NO_ERROR when what it took is answered. proven_http_event_server_stop_listening does this; the UDP socket stays open while a connection uses it, and listening again on the same port takes it up. proven_http_event_server_shutdown and _destroy end HTTP/3 connections as they end HTTP/2 ones.

    Cautions, and what goes wrong#

    • UDP reaches the server before any handshake. Anyone can send a client's first packet from any address, and without http3_retry each one makes a connection - about 40 KiB while its handshake waits, measured with a thousand from addresses that never answered - until head_timeout_ms lets it go. Such an address is never sent more than three times what it sent (RFC 9000 section 8), so the server cannot be used to flood someone else, but a flood can hold max_connections of them. http3_retry keeps nothing for an address until it has shown that it receives, at the price of a round trip for every connection.
    • The key for Retry tokens and stateless resets is drawn when the server is made. A restarted server cannot reset a client's old connection; that client waits out its idle timeout.
    • Timers fire at their time (within about a millisecond on POSIX, at the system timer's interval on Windows; v0.70.0): a quiet connection's QUIC timer - a probe, a delayed acknowledgement - no longer waits for the next 16 ms boundary; a busy one does its work in each round.
    • How fast HTTP/3 is depends on the platform. On Linux the datagrams of a round go to the kernel together - up to 45 of 1,452 bytes in one call (UDP_SEGMENT), and a receive may hand several back (UDP_GRO); on Windows the same, through USO and URO (UDP_SEND_MSG_SIZE, UDP_RECV_MAX_COALESCED_SIZE; v0.74.0); everywhere else each datagram is one system call. Each is encrypted and protected on its own either way. On the Windows 11 test VM, this server to this client in one process over loopback, 256 MiB: 2,545 Mbit/s over HTTP/3 against 1,021 one call a datagram, and 1,919 over HTTP/2 (x86-64; i686 1,807, 845 and 1,627). One 100 MiB download from this server to curl on Linux loopback ran at 369 MiB/s over HTTP/3, 382 over HTTP/2 and 499 over HTTP/1.1, all over TLS (v0.68.0; 219 at v0.67.0, one call a datagram; 174 at v0.65.0).
    • Datagrams start at 1,200 bytes and grow by probing (RFC 9000 section 14.3), up to 1,452 where the path and the peer carry them: one probe after the handshake on a path that carries 1,452, none once found. A path that stops carrying the size is noticed by its losses or its probe timeouts, and the size goes back to 1,200 and is found again. Nothing is configured. Every datagram carries the don't-fragment bit and nothing is fragmented on this side (Linux IP_PMTUDISC_PROBE, Windows IP_DONTFRAGMENT; v0.69.0), so a probe that passes passed whole.
    • 0-RTT, when the TLS configuration has early_data (chapter 14, section 6; v0.73.0). A client that resumes may send its first requests in its first packet, and the server answers them in its first reply: one round trip instead of two. A request that arrives that way is handed to the handler before the handshake is complete, and proven_http_stream_early is true for it: it may be a copy an attacker replayed. Only GET, HEAD and OPTIONS without a body reach a handler early; the server answers anything else that arrives early with 425 (Too Early) itself, and a handler that must not act on a copy answers 425 too - the client sends the request again once the handshake is over. Off by default.
    • A client's next connection skips the address check. After each handshake the server gives the client a token (NEW_TOKEN, RFC 9000 section 8.1.3) bound to its IP address and good for a day; a connection that brings one back is validated at once - no limit of three times what it sent, no Retry under http3_retry - so a 0-RTT answer larger than about 3.6 KB is not held back a round trip. A token that does not check is taken as none.
    • Not over HTTP/3: WebSocket (proven_ws_event_accept refuses the stream), trailers, server push, migration of this side's own (a client's new address is validated), QUIC versions other than 1. proven_http_event_server_adopt takes TCP connections only, so several loops cannot share one UDP port.
    • The event-driven client speaks HTTP/3 when a request asks (section 10); it never follows this server's Alt-Svc on its own.

    How this was tested. A registered test runs the server against a client made of this library's QUIC and HTTP/3 engines over UDP on loopback - every route of the HTTP/2 tests that is not WebSocket, the limits, each timeout, the goodbyes, Retry. Outside the registered tests: curl --http3-only (OpenSSL's QUIC) and aioquic's client against the server, every response checked byte for byte; h3spec 0.1.14, 76 of its 77 cases passed - the one not is a repeated unknown setting, which RFC 9114 lets a server take; a thousand client first packets from addresses that never answered, each sent at most three times what it sent, all let go after head_timeout_ms, and none kept with http3_retry.

    10. HTTP/3 in the event-driven client#

    typedef struct {
    /* ... everything Chapter 15 describes, and section 7's fields ... */
    bool http3;
    proven_size_t http3_window_bytes;
} proven_http_event_client_config_t;

typedef struct {
    /* ... */
    bool http3;            /* this request over HTTP/3 */
} proven_http_event_request_options_t;

    HTTP/2 is chosen by the TLS handshake; HTTP/3 cannot be - it is another transport, on UDP, and there is nothing to ask before the first packet. So the caller chooses: a client with http3 sends over HTTP/3 the requests whose options say http3, each with an https URL, and every other request as before. It never follows a server's Alt-Svc on its own. The callbacks and the request calls are the same for all three protocols; proven_http_event_request_protocol says 3, from the start.

    What happens underneath is section 7's, on QUIC: one connection kept for each origin (scheme, host, port, address), on a UDP socket of its own, shared by its requests; a request beyond the server's limit on streams waits on it; an idle one is told goodbye after idle_timeout_ms and closed; max_connections counts it with the TCP ones; retry_unsent sends again a request the server refused unprocessed (H3_REQUEST_REJECTED, or behind its GOAWAY); decompress decodes as over the others. A write is bounded by QUIC's send buffer - 256 KiB a stream, 1 MiB a connection, or, within what the server has granted, twice the congestion window, up to 16 MiB and 24 MiB - and a paused response stops being read, so the server stops at the window it had; read as fast as it comes, the window grows to 16 MiB a stream and 24 MiB a connection unless http3_window_bytes fixes it (v0.71.0).

    There is no fallback. A request asked over HTTP/3 whose server does not answer over UDP ends with PROVEN_ERR_TIMEOUT when connect_timeout_ms has passed - an unconnected UDP socket hears no refusal - one whose server refuses h3 with PROVEN_ERR_UNSUPPORTED, and one whose server is not trusted with PROVEN_ERR_UNTRUSTED. Over QUIC the client offers h3 alone, whatever else its TLS configuration offers over TCP, and takes nothing else (since version 0.73.2). No TCP connection is tried: a caller that wants one starts the request again without http3.

    Cautions, and what goes wrong#

    • Ask only servers known to speak it. Nothing here learns which do; a server's Alt-Svc says so, and reading it is the caller's to do.
    • How fast it is depends on the platform, as for the server: on Linux a round's datagrams go to the kernel together and a receive may hand several back; elsewhere one system call each. One 100 MiB download from this library's server to this client on Linux loopback ran at 393 MiB/s over HTTP/3 and 340 over HTTP/2 (v0.68.0; 233 over HTTP/3 at v0.67.0, 171 at v0.65.0). Datagrams grow from 1,200 to 1,452 bytes by probing, as the server's do.
    • A TLS session is kept per origin (chapter 15; v0.72.0): a new connection resumes it, and keeps the server's NEW_TOKEN token for the next one, which then skips the address check.
    • 0-RTT with early_data in the TLS configuration (chapter 14, section 6; v0.73.0). On a new connection whose session allows it, requests that are GET, HEAD or OPTIONS without a body go in the first packet and are answered one round trip sooner; any other request waits for the handshake. A request refused as early data, or answered 425, is sent again once after the handshake and only its second answer is delivered. Off by default.
    • Not here: connection migration of this side's own, WebSocket over HTTP/3.

    How this was tested. A registered test runs this client against this library's server over UDP on loopback - every case of section 7's test that the server can answer, the client's refusals, no fallback, an untrusted server, the timeouts. Outside the registered tests: aioquic's server (downloads to 50 MB byte for byte, uploads, trailers, an interim response passed over, 400 requests) and two public servers, cloudflare-quic.com and www.google.com.
