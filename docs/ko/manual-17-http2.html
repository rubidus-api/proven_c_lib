    17장: HTTP/2 - 프레임과 헤더 압축#

    5부 — 운영체제와 대화하기. 선행 조건: 요청과 응답이 무엇인지는 10장, 압축 테이블을 만들 때 쓰는 할당자(allocator) - 예제에서는 힙(heap) 할당자 - 는 2장. 이 장을 마치면 HTTP/2가 무엇을 바꾸고 무엇을 바꾸지 않는지 말할 수 있고, 헤더 블록을 인코딩하고 디코딩하며, 프레임을 읽고 쓰고, 잘 만들어진 요청과 전달해서는 안 되는 요청을 가려내고, 직접 실어 나르는 바이트 위에서 연결 하나 - 스트림, 윈도, 리셋, 작별 - 를 몰 수 있고, 처리기를 바꾸지 않고 15장의 이벤트 구동 서버에서 HTTP/2를 - 그리고 HTTP/3을 - 켤 수 있다. 그리고 이 가운데 이 라이브러리가 지금 하는 것이 어디까지인지 말할 수 있다.

    이 장은 hpack.h와 h2.h를 다룬다. 둘 다 순수한 계산이고 프리스탠딩(freestanding) 빌드에서 쓸 수 있다: HPACK은 인코더에 테이블 하나, 디코더에 테이블 하나를 할당하고, 프레임 함수는 아무것도 할당하지 않으며, 연결은 설정이 정한 한도 안에서 할당한다. 입력과 출력은 여러분의 메모리를 가리키는 뷰(view)로 주고받는다.

    여기 있는 것을, 아래에서 위로. 2절부터 4절까지는 코덱이다: HTTP/2 연결 위를 오가는 것을 읽고 쓴다. 5절은 연결 그 자체다 - 어떤 스트림이 열려 있는지, 얼마나 보낼 수 있는지, 무엇에 무엇으로 답하는지 - 바이트를 받고 바이트를 돌려주는 객체로서. 6절과 7절은 그 객체가 일하는 모습이다: 이벤트 구동 서버는 요청받으면 같은 포트에서 HTTP/1.1과 나란히 HTTP/2로 말하고, 이벤트 구동 클라이언트는 합의한 오리진마다 HTTP/2 연결 하나를 간직한다. 11장의 블로킹 서버와 블로킹 클라이언트는 HTTP/1.1로만 말한다. 그 선이 정확히 어디인지는 8절에 있다. 9절은 같은 서버가 UDP 위 QUIC으로, 같은 처리기에게 HTTP/3을 말하는 모습이고, 10절은 요청이 청할 때 클라이언트가 그것을 말하는 모습이다.

    1. HTTP/2가 바꾸는 것, 한 쪽으로#

    HTTP/2(RFC 9113)는 HTTP/1.1과 같은 요청과 응답 - 같은 메서드, 상태 코드, 헤더 필드 - 을 다른 모양으로 실어 나른다. 세 가지가 다르다:

    • 모든 것이 프레임이다. 헤더 아홉 바이트 - 길이, 종류, 플래그, 스트림 번호 - 와 페이로드. 파싱할 텍스트도 끝낼 줄도 없다: 메시지는 HEADERS 프레임과 DATA 프레임이다.
    • 여러 교환이 한 연결을 나눠 쓴다. 요청 하나와 그 응답이 번호가 붙은 *스트림*이다. 서로 다른 스트림의 프레임이 섞여 오가므로, 느린 응답이 뒤의 것들을 붙잡지 않는다. 스트림마다, 그리고 연결 전체에 *윈도*가 있다: 상대가 받겠다고 말한 DATA 바이트 수다.
    • 헤더 필드는 압축된다. 헤더를 위해 만든 방식(HPACK, RFC 7541)으로. 같은 필드가 요청마다 다시 전송되기 때문이다.

    HTTP/1.1이 첫 줄에서 말하던 것은 이름이 콜론으로 시작하는 *유사 헤더 필드*가 말한다: 요청에는 :method, :scheme, :authority, :path, 응답에는 :status. Host는 없고(:authority가 그것이다) Connection도 Transfer-Encoding도 없다: 그것들이 하던 일은 프레이밍이 한다.

    연결은 클라이언트가 보내는 고정된 24바이트(PROVEN_H2_PREFACE)로 시작하고, 이어서 양쪽이 SETTINGS 프레임을 하나씩 보낸다.

    2. 헤더 압축#

    proven_err_t proven_hpack_encoder_create(proven_allocator_t alloc, proven_size_t max_table_bytes, proven_hpack_encoder_t **out);
proven_err_t proven_hpack_encode(proven_hpack_encoder_t *encoder, const proven_http_header_t *headers, proven_size_t count,
                                 const bool *sensitive, proven_mem_mut_t out, proven_size_t *len);

proven_err_t proven_hpack_decoder_create(proven_allocator_t alloc, proven_size_t max_table_bytes, proven_hpack_decoder_t **out);
proven_err_t proven_hpack_decode(proven_hpack_decoder_t *decoder, proven_mem_view_t block,
                                 proven_http_header_t *headers, proven_size_t header_cap,
                                 proven_mem_mut_t scratch, proven_size_t max_list_bytes, proven_size_t *count);

    HPACK은 필드를 세 가지 방법 가운데 하나로 보낸다: 흔한 필드 61개가 담긴 고정 테이블의 항목을 가리키는 번호로(:method: GET은 2번 항목이다), 이 연결이 전에 보낸 필드를 담은 *동적 테이블*의 항목을 가리키는 번호로, 또는 리터럴로 - 리터럴은 보내면서 동적 테이블에 넣을 수 있고, 그 글자는 허프만 코딩할 수 있다. 처음에 65바이트인 요청이 두 번째에는 22바이트다.

    양쪽은 같은 테이블을 유지해야 한다. 모든 블록은 보낸 순서대로, 그 연결 그 방향의 디코더 하나가 디코딩한다. 블록 하나를 건너뛰거나 두 번 디코딩하면 그 뒤의 모든 블록이 다른 뜻이 된다. 잘못된 블록을 만난 디코더가 그 뒤의 것을 모두 거부하는 까닭, 그리고 HTTP/2가 그 일로 연결을 끝내는 까닭이 이것이다.

    테이블 크기는 여러분이 정하며, 그것은 비용이 아니라 상한이다: 기본 4,096바이트 (PROVEN_HPACK_DEFAULT_TABLE_BYTES). 그 뒤의 메모리는 항목이 추가되는 만큼 자란다 - 짧은 필드 몇 개를 보내는 상대라면 수백 바이트 - 테이블이 가득 차면 크기의 한 배 반쯤이 된다. 0으로 만든 인코더는 테이블을 두지 않아 상태가 없고, 0으로 만든 디코더는 상대에게 테이블을 두지 말라고 알린다.

    예제: 두 번 보낸 요청, 테이블에 넣지 않은 비밀, 그리고 한도#

    #include <stdio.h>
#include <string.h>

/*
 * HPACK: HTTP/2가 헤더 필드를 보내는 방식.
 *
 * 인코더는 필드 목록을 바이트 블록으로 바꾸고, 반대편의 디코더는 블록을 다시 목록으로 바꾼다.
 * 양쪽 모두 앞서 지나간 필드의 테이블을 유지하며, 같은 필드를 두 번째로 보낼 때는 한 바이트다.
 * 두 테이블은 같은 상태여야 한다 - 그래서 연결에는 방향마다 인코더 하나와 디코더 하나가 있고,
 * 순서대로 쓴다.
 */

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    proven_hpack_encoder_t *encoder = NULL;
    proven_hpack_decoder_t *decoder = NULL;
    /* 테이블 4096바이트가 프로토콜의 기본값이다. 양쪽이 다른 크기에 합의할 수 있다. */
    EXAMPLE_REQUIRE(proven_hpack_encoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &encoder) == PROVEN_OK &&
                    proven_hpack_decoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &decoder) == PROVEN_OK, "an encoder here, a decoder there");

    // ---- 요청 하나를 두 번 ---------------------------------------------------------
    /* HTTP/2에서 이름은 소문자이고, HTTP/1이 첫 줄에 적던 것은 여기서 이름이 콜론으로
     * 시작하는 필드가 된다. */
    proven_http_header_t request[] = {
        { PROVEN_LIT(":method"), PROVEN_LIT("GET") },
        { PROVEN_LIT(":scheme"), PROVEN_LIT("https") },
        { PROVEN_LIT(":path"), PROVEN_LIT("/reports/2026/october") },
        { PROVEN_LIT(":authority"), PROVEN_LIT("www.example.com") },
        { PROVEN_LIT("user-agent"), PROVEN_LIT("example-client/1.0") },
        { PROVEN_LIT("authorization"), PROVEN_LIT("Bearer 5f2c1e9a7b3d") },
    };
    proven_byte_t block[512];
    EXAMPLE_REQUIRE(proven_hpack_encode_bound(request, 6) <= sizeof block, "the block will fit");
    proven_size_t first = 0;
    EXAMPLE_REQUIRE(proven_hpack_encode(encoder, request, 6, NULL, (proven_mem_mut_t){ block, sizeof block }, &first) == PROVEN_OK, "the request, encoded");

    /* 디코더는 필드를 뷰로 돌려준다: 블록 안, 고정 테이블 안, 또는 빌려준 스크래치 안을
     * 가리킨다. */
    proven_http_header_t fields[16];
    proven_byte_t scratch[1024];
    proven_size_t count = 0;
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ block, first }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK && count == 6,
                    "and decoded");
    EXAMPLE_REQUIRE(proven_u8str_view_eq(fields[2].name, PROVEN_LIT(":path")) && proven_u8str_view_eq(fields[2].value, PROVEN_LIT("/reports/2026/october")), "field for field");

    /* 같은 요청을 다시 보내면 비용은 일부분이다: 양쪽이 기억하고 있다. */
    proven_size_t second = 0;
    EXAMPLE_REQUIRE(proven_hpack_encode(encoder, request, 6, NULL, (proven_mem_mut_t){ block, sizeof block }, &second) == PROVEN_OK, "the same request again");
    printf("the first time: %u bytes; the second: %u\n", (unsigned)first, (unsigned)second);
    EXAMPLE_REQUIRE(second < first / 2, "less than half");
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ block, second }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK && count == 6 &&
                    proven_u8str_view_eq(fields[4].value, PROVEN_LIT("example-client/1.0")), "and the decoder still gives the whole list");

    // ---- 기억하지 않는 것 ----------------------------------------------------------
    /* 테이블은 압축 문맥이고, 그 안의 비밀은 뒤따르는 블록의 크기로 추측될 수 있다.
     * 그래서 authorization 값은 테이블에 들어간 적이 없다 - 어느 쪽에서도: */
    proven_size_t entries = proven_hpack_decoder_table_count(decoder);
    bool secret_kept = false;
    for (proven_size_t i = 0; i < entries; ++i) {
        proven_u8str_view_t name, value;
        EXAMPLE_REQUIRE(proven_hpack_decoder_table_entry(decoder, i, &name, &value), "an entry of the table");
        if (proven_u8str_view_eq(name, PROVEN_LIT("authorization"))) secret_kept = true;
    }
    printf("the table holds %u entries, %u bytes by the protocol's count\n", (unsigned)entries, (unsigned)proven_hpack_decoder_table_bytes(decoder));
    EXAMPLE_REQUIRE(entries == 3 && !secret_kept, "the path, the authority and the user agent - not the secret");
    /* 어떤 필드든 같은 취급을 받게 할 수 있다. */
    proven_http_header_t more[] = { { PROVEN_LIT("x-api-key"), PROVEN_LIT("k-0123456789") } };
    bool sensitive[] = { true };
    bool marked[16] = { false };
    proven_size_t n = 0;
    /* 디코더는 어느 필드가 표시와 함께 왔는지 알려 줄 수 있다 - 필드를 넘기는 쪽에 필요한 것. */
    EXAMPLE_REQUIRE(proven_hpack_encode(encoder, more, 1, sensitive, (proven_mem_mut_t){ block, sizeof block }, &n) == PROVEN_OK &&
                    proven_hpack_decode_marked(decoder, (proven_mem_view_t){ block, n }, fields, marked, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK &&
                    proven_hpack_decoder_table_count(decoder) == 3 && marked[0], "a field marked sensitive adds nothing to the table, and arrives marked");

    // ---- 한도, 그리고 그것의 쓸모 --------------------------------------------------
    /* 블록의 크기는 그것이 말하는 내용의 크기가 아니다. 이 블록은 다섯 바이트이고, 기억된
     * 같은 필드를 다섯 번 가리킨다: */
    static const proven_byte_t repeat[] = { 0xbe, 0xbe, 0xbe, 0xbe, 0xbe };       /* "62번 항목" - 테이블에서 가장 새것 */
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ repeat, sizeof repeat }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK && count == 5,
                    "five bytes, five fields");
    /* 그래서 한도는 블록이 아니라 풀린 목록 - 이름, 값, 그리고 필드마다 32 - 에 걸린다.
     * 넘으면 필드는 내주지 않지만, 디코더는 블록을 끝까지 읽었고 여전히 쓸 수 있다:
     * 그 요청 하나만 거절하고 연결은 유지한다. */
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ repeat, sizeof repeat }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 100, &count) == PROVEN_ERR_OUT_OF_BOUNDS && count == 0,
                    "a list limit of 100 bytes refuses it");
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ repeat, 1 }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 100, &count) == PROVEN_OK && count == 1, "and the next block is decoded as if nothing had happened");

    /* 아예 HPACK이 아닌 블록은 다른 문제다: 두 테이블이 일치한다고 더는 믿을 수 없고,
     * 디코더는 그때부터 그렇게 말한다. HTTP/2에서는 연결이 끝난다. */
    static const proven_byte_t nonsense[] = { 0x80 };                            /* "0번 항목": 그런 것은 없다 */
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ nonsense, 1 }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_ERR_INVALID_FORMAT &&
                    proven_hpack_decode(decoder, (proven_mem_view_t){ repeat, 1 }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_ERR_INVALID_FORMAT,
                    "a malformed block is refused, and so is everything after it");

    // ---- 테이블 크기는 협상된다 ---------------------------------------------------
    /* 상대가 더 작은 테이블을 알리면 인코더에게 전하고, 인코더는 다음 블록의 맨 앞에서
     * 따랐다고 말한다. 자기 한도가 낮아진 디코더는 그 말을 요구한다. */
    proven_hpack_decoder_destroy(decoder);
    EXAMPLE_REQUIRE(proven_hpack_decoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &decoder) == PROVEN_OK, "a fresh decoder");
    proven_hpack_decoder_set_max_table_bytes(decoder, 0);          /* "이쪽은 테이블을 두지 않겠다" ... */
    proven_hpack_encoder_set_peer_table_bytes(encoder, 0);         /* ... 인코더가 그것을 들었다 */
    n = 0;
    EXAMPLE_REQUIRE(proven_hpack_encode(encoder, request, 6, NULL, (proven_mem_mut_t){ block, sizeof block }, &n) == PROVEN_OK && block[0] == 0x20, "the next block opens by saying: table size 0");
    EXAMPLE_REQUIRE(proven_hpack_decode(decoder, (proven_mem_view_t){ block, n }, fields, 16, (proven_mem_mut_t){ scratch, sizeof scratch }, 4096, &count) == PROVEN_OK && count == 6 &&
                    proven_hpack_decoder_table_count(decoder) == 0, "and nothing is remembered on either side");

    // ---- 허프만 코딩만 따로 ------------------------------------------------------
    /* 리터럴 문자열은 흔한 문자에 더 적은 비트를 주는 코드로 보낸다. */
    proven_u8str_view_t text = PROVEN_LIT("www.example.com");
    proven_byte_t coded[32], back[32];
    proven_size_t coded_len = 0, back_len = 0;
    EXAMPLE_REQUIRE(proven_hpack_huffman_size(text) == 12 && proven_hpack_huffman_encode(text, (proven_mem_mut_t){ coded, sizeof coded }, &coded_len) == PROVEN_OK && coded_len == 12, "fifteen characters in twelve bytes");
    EXAMPLE_REQUIRE(proven_hpack_huffman_decode((proven_mem_view_t){ coded, coded_len }, (proven_mem_mut_t){ back, sizeof back }, &back_len) == PROVEN_OK && back_len == 15 && memcmp(back, "www.example.com", 15) == 0, "and back");

    proven_hpack_encoder_destroy(encoder);
    proven_hpack_decoder_destroy(decoder);
    return EXAMPLE_OK();
}

    주의사항, 그리고 무엇이 잘못되는가#

    • 블록의 크기는 그것이 말하는 내용의 크기가 아니다. 다섯 바이트가 기억된 큰 필드를 다섯 번 가리킬 수 있고, 오천 바이트는 오천 번 가리킬 수 있다. max_list_bytes를 늘 줄 것: 풀린 목록 - RFC가 세는 대로 이름, 값, 그리고 필드마다 32바이트 - 을 묶고, 그 크기의 scratch면 언제나 충분하다.
    • 한도 초과는 연결의 끝이 아니고, 잘못된 형식은 끝이다. OUT_OF_BOUNDS는 블록을 끝까지 읽었고 테이블이 맞아 있으며 이 메시지만 거절한다는 뜻이다. INVALID_FORMAT은 두 테이블이 달라졌을 수 있다는 뜻이고, 디코더는 그 뒤로 계속 같은 답을 한다.
    • 뷰, 세 가지. 디코딩된 이름이나 값은 블록 안, 라이브러리의 고정 테이블 안, 또는 여러분이 빌려준 임시 작업용(scratch) 버퍼 - 아래에서는 스크래치 - 안을 가리킨다. 셋 모두 필드를 쓰는 동안 살아 있어야 한다. 간직할 것은 복사한다.
    • 비밀은 테이블에 넣지 않는다. 테이블은 압축 문맥이고, 그 안의 것은 공격자가 영향을 주는 뒤따르는 블록의 크기로 한 바이트씩 추측될 수 있다. 인코더는 authorization과 proxy-authorization의 값을 기억하지 않고, 어느 중간 지점도 기억하지 않도록 표시해서 보낸다. cookie와 set-cookie도 기억하지 않는다. sensitive는 여러분이 지목한 필드까지 그렇게 다룬다. 필드를 받아서 넘기는 쪽 - 프록시 - 은 어느 필드가 그 표시와 함께 왔는지 proven_hpack_decode_marked로 알아내어, 그 표시를 인코더의 sensitive로 넘긴다.
    • 두 번 같기 어려운 것도 넣지 않는다. content-length, content-range, etag, age, if-none-match, if-modified-since는 이름의 인덱스로 보내고 기억하지 않는다. 새 값마다 테이블에서 되풀이되는 필드의 자리를 빼앗기 때문이다. (content-length가 매번 다른 응답 헤드: 값을 기억하면 26바이트에 초당 430,000개, 기억하지 않으면 13바이트에 초당 1,020,000개 - 한 기계에서, 인코딩과 디코딩.)
    • 이름은 인코더에 닿기 전에 소문자여야 한다. 인코더는 받은 대로 인코딩한다. 목록이 보내도 되는 것인지 검사하는 일은 4절의 것이다.
    • 인코더 하나, 디코더 하나, 방향 하나, 순서대로. 요청마다가 아니고 스트림마다가 아니다.

    3. 프레임#

    proven_err_t proven_h2_frame_parse(proven_mem_view_t data, proven_h2_frame_t *out);
proven_err_t proven_h2_frame_check(const proven_h2_frame_t *frame, proven_u32 max_frame_size, proven_h2_error_t *code, bool *stream_error);
proven_err_t proven_h2_frame_write(proven_mem_mut_t out, proven_size_t *len, const proven_h2_frame_t *frame);

    프레임은 아홉 바이트와 페이로드다:

    필드비트뜻
    길이24페이로드의 바이트 수. 모든 끝점은 16,384를 받는다. 더 큰 것은 그렇게 말한 경우에만
    종류8열 가지 가운데 하나. 그 밖의 것은 건너뛴다
    플래그8뜻은 종류에 따라 다르다
    스트림31(그리고 예약 비트 하나)0은 연결 자체. 클라이언트는 홀수 스트림을 연다

    proven_h2_frame_check는 페이로드를 보기 전에 종류마다 있는 규칙을 적용한다:

    종류스트림크기싣는 것
    DATA필요아무 크기본문의 한 조각. 패딩될 수 있다. END_STREAM은 보낸 쪽을 끝낸다
    HEADERS필요아무 크기헤더 블록, 또는 그 시작. 패딩될 수 있고, 우선순위 다섯 바이트를 실을 수 있는데 그것은 건너뛴다
    CONTINUATION필요아무 크기END_HEADERS가 나올 때까지 헤더 블록의 나머지
    RST_STREAM필요4오류 코드: 이 스트림은 끝났다
    SETTINGS0이어야 한다6의 배수. ACK면 0식별자와 값의 쌍
    PING0이어야 한다8ACK와 함께 돌려보낼 여덟 바이트
    GOAWAY0이어야 한다8 이상처리한 마지막 스트림, 오류 코드, 사람이 읽을 글
    WINDOW_UPDATE어느 쪽이든4몇 바이트를 더 보내도 되는가
    PRIORITY필요5폐기된 것. 검사하고 무시한다
    PUSH_PROMISE필요아무 크기서버 푸시. 이 라이브러리는 언제나 사양한다

    오류에는 두 가지 크기가 있다. *연결 오류*는 연결을 끝낸다: 코드를 실은 GOAWAY를 보내고 닫는다. *스트림 오류*는 스트림 하나를 끝낸다: RST_STREAM을 보내고 계속한다. 검사는 코드와 어느 쪽인지를 알려 준다.

    예제: 서버가 읽듯이 읽은, 연결의 첫 바이트들#

    #include <stdio.h>
#include <string.h>

/*
 * HTTP/2 프레임과 그 안의 헤더 목록 - 서버가 연결의 첫 바이트들을 읽듯이, 여기서는 버퍼에서
 * 읽는다.
 *
 * h2.h에는 연결을 하나로 묶어 주는 것이 없다. 프레임을 읽고 쓰고, 프레임 종류마다 있는 규칙을
 * 적용하고, 풀린 헤더 목록이 요청인지 검사한다. 어떤 스트림이 열려 있고 얼마나 보낼 수 있는지는
 * 이것들을 쓰는 쪽의 일이다.
 */

/* 클라이언트가 연결을 열고 페이지 하나를 요청할 때 보낼 바이트. */
static proven_size_t client_bytes(proven_allocator_t heap, proven_byte_t *wire, proven_size_t cap) {
    proven_mem_mut_t out = { wire, cap };
    proven_size_t len = 0;
    memcpy(wire, PROVEN_H2_PREFACE, PROVEN_H2_PREFACE_SIZE);       /* 고정된 24바이트가 먼저 온다 */
    len = PROVEN_H2_PREFACE_SIZE;

    /* 다음은 클라이언트의 설정: 여기서는 "푸시하지 말 것"과 더 큰 윈도. */
    proven_h2_setting_t settings[] = {
        { PROVEN_H2_SETTINGS_ENABLE_PUSH, 0 },
        { PROVEN_H2_SETTINGS_INITIAL_WINDOW_SIZE, 1048576 },
    };
    if (proven_h2_write_settings(out, &len, settings, 2) != PROVEN_OK) return 0;

    /* 요청은 새 스트림 - 클라이언트의 스트림은 홀수 - 위의 HEADERS 프레임이고, HPACK
     * 블록을 싣는다. END_HEADERS: 블록이 온전하다. END_STREAM: 본문이 뒤따르지 않는다. */
    proven_http_header_t request[] = {
        { PROVEN_LIT(":method"), PROVEN_LIT("GET") },
        { PROVEN_LIT(":scheme"), PROVEN_LIT("https") },
        { PROVEN_LIT(":path"), PROVEN_LIT("/") },
        { PROVEN_LIT(":authority"), PROVEN_LIT("www.example.com") },
        { PROVEN_LIT("accept"), PROVEN_LIT("text/html") },
    };
    proven_hpack_encoder_t *encoder = NULL;
    proven_byte_t block[256];
    proven_size_t block_len = 0;
    if (proven_hpack_encoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &encoder) != PROVEN_OK) return 0;
    proven_err_t err = proven_hpack_encode(encoder, request, 5, NULL, (proven_mem_mut_t){ block, sizeof block }, &block_len);
    proven_hpack_encoder_destroy(encoder);
    if (err != PROVEN_OK) return 0;
    proven_h2_frame_t headers = { .length = (proven_u32)block_len, .type = PROVEN_H2_HEADERS,
                                  .flags = PROVEN_H2_FLAG_END_HEADERS | PROVEN_H2_FLAG_END_STREAM, .stream_id = 1 };
    if (proven_h2_frame_write(out, &len, &headers) != PROVEN_OK) return 0;
    memcpy(wire + len, block, block_len);
    len += block_len;

    /* 그리고 예제를 위해, 규칙을 어기는 프레임 하나: PING은 여덟 바이트여야 한다. */
    proven_h2_frame_t bad_ping = { .length = 4, .type = PROVEN_H2_PING };
    if (proven_h2_frame_write(out, &len, &bad_ping) != PROVEN_OK) return 0;
    memset(wire + len, 0, 4);
    return len + 4;
}

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    proven_byte_t wire[1024];
    proven_size_t size = client_bytes(heap, wire, sizeof wire);
    EXAMPLE_REQUIRE(size > 0, "the client's bytes");

    // ---- 서버 쪽 -------------------------------------------------------------------
    EXAMPLE_REQUIRE(size >= PROVEN_H2_PREFACE_SIZE && memcmp(wire, PROVEN_H2_PREFACE, PROVEN_H2_PREFACE_SIZE) == 0, "the preface: this is HTTP/2");
    proven_size_t at = PROVEN_H2_PREFACE_SIZE;

    proven_hpack_decoder_t *decoder = NULL;
    EXAMPLE_REQUIRE(proven_hpack_decoder_create(heap, PROVEN_HPACK_DEFAULT_TABLE_BYTES, &decoder) == PROVEN_OK, "the connection's decoder");
    int frames = 0, requests = 0;
    proven_h2_error_t refused_with = PROVEN_H2_NO_ERROR;

    while (at < size) {
        /* 헤더 아홉 바이트가 프레임의 길이, 종류, 그리고 어느 스트림의 것인지를 말한다. */
        proven_h2_frame_t frame;
        proven_err_t err = proven_h2_frame_parse((proven_mem_view_t){ wire + at, size - at }, &frame);
        if (err == PROVEN_ERR_NEED_MORE) break;                    /* 실제 서버라면 더 읽을 것이다 */
        EXAMPLE_REQUIRE(err == PROVEN_OK, "a frame header");

        /* 페이로드를 보기 전에: 이 프레임은 자기가 말하는 그것이어도 되는가? 크기 한도는
         * 이쪽이 알린 값이다(여기서는 프로토콜의 최솟값). */
        proven_h2_error_t code;
        bool stream_error;
        if (proven_h2_frame_check(&frame, PROVEN_H2_MIN_MAX_FRAME_SIZE, &code, &stream_error) != PROVEN_OK) {
            /* 실제 서버는 GOAWAY로 답한다(스트림만 잘못됐으면 RST_STREAM). */
            refused_with = code;
            EXAMPLE_REQUIRE(!stream_error, "a PING of the wrong size ends the connection");
            break;
        }
        proven_mem_view_t payload = { wire + at + PROVEN_H2_FRAME_HEADER_SIZE, frame.length };
        EXAMPLE_REQUIRE(PROVEN_H2_FRAME_HEADER_SIZE + frame.length <= size - at, "the whole frame is here");
        frames++;

        if (frame.type == PROVEN_H2_SETTINGS) {
            proven_size_t pos = 0;
            proven_h2_setting_t setting;
            while ((err = proven_h2_settings_next(payload, &pos, &setting, &code)) == PROVEN_OK) {
                if (setting.id == PROVEN_H2_SETTINGS_INITIAL_WINDOW_SIZE) printf("the client's window: %u bytes a stream\n", (unsigned)setting.value);
                /* 이쪽이 모르는 설정은 그저 따르지 않는다. */
            }
            EXAMPLE_REQUIRE(err == PROVEN_ERR_EOF, "every setting was in range");
        } else if (frame.type == PROVEN_H2_HEADERS) {
            /* 헤더 블록은 패딩과 옛 우선순위 필드를 걷어 낸 나머지다. (END_HEADERS가 꺼져
             * 있으면 CONTINUATION 프레임들이 나머지를 싣는다.) */
            proven_mem_view_t block;
            EXAMPLE_REQUIRE(proven_h2_frame_content(&frame, payload, &block) == PROVEN_OK && (frame.flags & PROVEN_H2_FLAG_END_HEADERS) != 0, "a whole header block");
            proven_http_header_t fields[32];
            proven_byte_t scratch[2048];
            proven_size_t count = 0;
            EXAMPLE_REQUIRE(proven_hpack_decode(decoder, block, fields, 32, (proven_mem_mut_t){ scratch, sizeof scratch }, 16384, &count) == PROVEN_OK, "decoded");

            /* 필드 목록이 아직 요청인 것은 아니다. 대문자가 든 이름, 값 안의 줄바꿈, 빠진
             * :path, "connection" 헤더가 여기서 걸린다. */
            proven_h2_request_head_t head;
            EXAMPLE_REQUIRE(proven_h2_request_head(fields, count, &head) == PROVEN_OK, "a well-formed request");
            printf("stream %u: %.*s %.*s for %.*s, %u more fields\n", (unsigned)frame.stream_id, (int)head.method.size, (const char *)head.method.ptr,
                   (int)head.path.size, (const char *)head.path.ptr, (int)head.authority.size, (const char *)head.authority.ptr, (unsigned)head.field_count);
            EXAMPLE_REQUIRE(proven_u8str_view_eq(head.path, PROVEN_LIT("/")) && head.field_count == 1 && proven_u8str_view_eq(head.fields[0].name, PROVEN_LIT("accept")), "its parts");
            requests++;
        }
        at += PROVEN_H2_FRAME_HEADER_SIZE + frame.length;
    }
    EXAMPLE_REQUIRE(frames == 2 && requests == 1 && refused_with == PROVEN_H2_FRAME_SIZE_ERROR, "two frames taken, one request, and the third frame refused with FRAME_SIZE_ERROR");
    proven_hpack_decoder_destroy(decoder);

    // ---- 서버가 써 보내는 것 -------------------------------------------------------
    proven_byte_t reply[256];
    proven_mem_mut_t out = { reply, sizeof reply };
    proven_size_t len = 0;
    static const proven_byte_t opaque[8] = { 'p', 'r', 'o', 'v', 'e', 'n', '!', '!' };
    EXAMPLE_REQUIRE(proven_h2_write_settings(out, &len, NULL, 0) == PROVEN_OK &&       /* 자기 설정: 모두 기본값 */
                    proven_h2_write_settings_ack(out, &len) == PROVEN_OK &&            /* "그쪽 설정이 적용되었다" */
                    proven_h2_write_window_update(out, &len, 0, 1 << 20) == PROVEN_OK &&   /* 연결에 1메가바이트를 더 보내도 된다 */
                    proven_h2_write_ping(out, &len, opaque, false) == PROVEN_OK &&     /* 거기 있는가? */
                    proven_h2_write_rst_stream(out, &len, 3, PROVEN_H2_REFUSED_STREAM) == PROVEN_OK &&   /* 그 스트림은 지금은 안 된다 */
                    proven_h2_write_goaway(out, &len, 1, PROVEN_H2_FRAME_SIZE_ERROR, proven_mem_view_from_u8(PROVEN_LIT("a PING is eight bytes"))) == PROVEN_OK,
                    "six frames a server might send");

    /* 클라이언트가 하듯이 다시 읽는다. */
    at = 0;
    int seen = 0;
    while (at < len) {
        proven_h2_frame_t frame;
        proven_h2_error_t code;
        bool stream_error;
        EXAMPLE_REQUIRE(proven_h2_frame_parse((proven_mem_view_t){ reply + at, len - at }, &frame) == PROVEN_OK &&
                        proven_h2_frame_check(&frame, PROVEN_H2_MIN_MAX_FRAME_SIZE, &code, &stream_error) == PROVEN_OK, "each passes its own rule");
        proven_mem_view_t payload = { reply + at + PROVEN_H2_FRAME_HEADER_SIZE, frame.length };
        proven_u32 a = 0, b = 0;
        proven_mem_view_t debug;
        if (frame.type == PROVEN_H2_WINDOW_UPDATE) EXAMPLE_REQUIRE(proven_h2_read_window_update(payload, &a) == PROVEN_OK && a == 1 << 20, "the increment");
        if (frame.type == PROVEN_H2_RST_STREAM) EXAMPLE_REQUIRE(proven_h2_read_rst_stream(payload, &a) == PROVEN_OK && a == PROVEN_H2_REFUSED_STREAM && frame.stream_id == 3, "the reset");
        if (frame.type == PROVEN_H2_GOAWAY) EXAMPLE_REQUIRE(proven_h2_read_goaway(payload, &a, &b, &debug) == PROVEN_OK && a == 1 && b == PROVEN_H2_FRAME_SIZE_ERROR && debug.size == 21, "the goodbye");
        seen++;
        at += PROVEN_H2_FRAME_HEADER_SIZE + frame.length;
    }
    EXAMPLE_REQUIRE(seen == 6, "six frames read back");

    // ---- 응답과 트레일러 -----------------------------------------------------------
    proven_http_header_t response[] = { { PROVEN_LIT(":status"), PROVEN_LIT("200") }, { PROVEN_LIT("content-type"), PROVEN_LIT("text/html") } };
    proven_u16 status = 0;
    const proven_http_header_t *rest = NULL;
    proven_size_t rest_count = 0;
    EXAMPLE_REQUIRE(proven_h2_response_head(response, 2, &status, &rest, &rest_count) == PROVEN_OK && status == 200 && rest_count == 1, "a response has one pseudo-header field: its status");
    proven_http_header_t smuggle[] = { { PROVEN_LIT(":status"), PROVEN_LIT("200") }, { PROVEN_LIT("x-note"), PROVEN_LIT("fine\r\ntransfer-encoding: chunked") } };
    EXAMPLE_REQUIRE(proven_h2_response_head(smuggle, 2, &status, &rest, &rest_count) == PROVEN_ERR_INVALID_FORMAT, "a value with a line break in it is no response at all");
    proven_http_header_t trailers[] = { { PROVEN_LIT("x-checksum"), PROVEN_LIT("9f86d081") } };
    EXAMPLE_REQUIRE(proven_h2_trailers_check(trailers, 1) == PROVEN_OK, "trailers are ordinary fields");
    return EXAMPLE_OK();
}

    주의사항, 그리고 무엇이 잘못되는가#

    • 읽기 전에 검사한다. proven_h2_frame_parse는 아홉 바이트에서 실패할 수 없다. 그 바이트들이 있어도 되는 프레임을 말하는지는 검사가 답한다. 여러분이 알린 크기보다 긴 프레임은 무엇이라고 주장하든 연결 오류다.
    • 흐름 제어는 페이로드 전체를 센다. proven_h2_frame_content는 패딩된 DATA 프레임의 내용이 어디 있는지 알려 준다. 윈도에서는 패딩까지 차감된다.
    • 헤더 블록은 여러 프레임에 걸칠 수 있고, 그 사이에 다른 것은 올 수 없다: END_HEADERS가 없는 HEADERS 뒤에는 같은 스트림의 CONTINUATION 프레임이, 그 플래그가 나올 때까지 이어진다. 모으는 양에 한도를 둘 것 - 헤더 목록 한도의 두 배면 정직한 블록에는 충분하다 - 그러지 않으면 상대가 보내고 싶은 만큼을 쥐게 된다.
    • 모르는 것은 틀린 것이 아니다. 이 라이브러리가 모르는 프레임 종류나 설정은, 프로토콜이 요구하는 대로 검사를 통과한다. 건너뛴다.
    • 설정에는 범위가 있고, 벗어난 값은 연결 오류다: ENABLE_PUSH와 ENABLE_CONNECT_PROTOCOL은 0 또는 1, 초기 윈도는 많아야 2^31-1, 프레임 크기는 16,384에서 2^24-1까지. ENABLE_CONNECT_PROTOCOL은 한 번 1이 되면 0이 될 수 없다.

    4. 메시지로서의 헤더 목록#

    디코딩된 헤더 목록은 바이트 문자열의 목록이다. 그것이 요청인가는 별개의 질문이고, 그 답은 HTTP/2가 HTTP/1.1과 만나는 곳에서 가장 중요하다: 줄바꿈이 든 값이 텍스트로 전달되면 헤더 두 줄이 된다 - 받는 서버가 도착하는 것을 본 적 없는 요청이다. 그래서 다음과 같은 목록은 *잘못된 형식*이며, 고치거나 전달하지 말고 거절해야 한다:

    규칙까닭
    필드 이름에 대문자, 공백, 제어 바이트, 0x7e보다 큰 바이트가 있거나, 맨 앞이 아닌 곳에 콜론이 있다이름은 소문자 토큰이다. 콜론은 유사 헤더 필드를 시작할 뿐이다
    값에 NUL, CR, LF가 있거나, 값이 공백이나 탭으로 시작하거나 끝난다이것들은 HTTP/1.1의 구분자다
    유사 헤더 필드가 보통 필드 뒤에 오거나, 두 번 나오거나, 아무도 정의하지 않은 것이다그것들은 메시지의 첫 줄이다: 한 번, 맨 먼저
    요청에 :method, :scheme, :path가 없다. http나 https인데 :path가 비었다. 요청에 :status가 있다첫 줄은 온전해야 한다. (CONNECT에는 :method와 :authority만 있다)
    응답에 :status가 없거나 세 자리 숫자가 아니다위와 같다
    connection, proxy-connection, keep-alive, transfer-encoding, upgrade가 있다. te가 trailers가 아닌 것을 말한다이것들은 HTTP/1.1 연결을 기술한다. 여기서는 남의 연결을 기술하려는 시도다
    트레일러에 유사 헤더 필드가 있다트레일러는 보통 필드다

    proven_h2_request_head는 이 규칙들을 적용하고 부분들을 돌려준다: 메서드, 스킴, authority, 경로, 그리고 뒤따르는 보통 필드들 - 그리고 확장 CONNECT(RFC 8441)이면 protocol: :protocol은 CONNECT에만, 그리고 그때는 스킴, authority, 경로가 모두 있어야 한다. 그것이 허락되는지는 연결이 정한다: 설정에 enable_connect_protocol이 있는 서버는 SETTINGS_ENABLE_CONNECT_PROTOCOL을 말하고 그것을 받는다. 다른 서버는 그런 스트림을 PROTOCOL_ERROR로 거절하고, 받아들인 것의 자기 쪽은 리셋이 아니라 END_STREAM으로 끝낸다 - 터널은 양쪽에서 끝난다. 잘못된 형식의 메시지는 PROTOCOL_ERROR 종류의 스트림 오류다: 응답을 아직 보낼 수 있으면 400으로 답하고, 아니면 스트림을 리셋한다.

    5. 연결#

    proven_err_t proven_h2_conn_create(const proven_h2_config_t *config, proven_h2_conn_t **out);
void proven_h2_conn_destroy(proven_h2_conn_t *conn);

proven_err_t proven_h2_conn_feed(proven_h2_conn_t *conn, proven_mem_view_t in, proven_size_t *consumed, proven_h2_event_t *event);

void proven_h2_conn_output_sent(proven_h2_conn_t *conn, proven_size_t n);

    proven_h2_conn_t는 어느 쪽 끝이든 될 수 있는 HTTP/2 연결 하나다. 2절부터 4절까지가 여러분에게 남겨 두었던 것을 모두 쥐고 있다: 양쪽의 설정, 열려 있는 스트림, 양방향의 윈도, 압축 테이블 둘, 그리고 프레임마다 프로토콜이 요구하는 답. 입출력을 하지 않고 시계도 읽지 않는다. 모양은 14장의 TLS 엔진과 같다:

       상대가 보낸 바이트  -->  proven_h2_conn_feed  -->  사건 하나: 요청, 본문의 한 조각, 리셋, ...
   여러분의 요청, 응답, 본문  -->  proven_h2_conn_submit_* / _send_data
   proven_h2_conn_pending_output  -->  상대에게 갈 바이트  -->  proven_h2_conn_output_sent

    소켓, TLS, 모든 타임아웃은 호출자의 것이다. 그래서 객체 하나가 블로킹 프로그램에도, 이벤트 루프에도, 네트워크가 전혀 없는 시험에도 쓰인다 - 아래 예제는 서로 버퍼를 건네는 연결 둘이고, 6절은 소켓 뒤에 놓인 같은 객체다.

    사건#

    proven_h2_conn_feed는 알릴 사건이 하나 생길 때까지 in의 바이트를 쓰고, 몇 바이트를 썼는지 알려 준다. 나머지를 가지고 다시 호출한다. PROVEN_H2_EVENT_NONE은 모두 썼다는 뜻이다.

    사건뜻필드
    PROVEN_H2_EVENT_HEADERS서버: 요청이 시작되었다. 이미 4절의 규칙으로 검사되고 나뉘어 있다. 클라이언트: 응답의 머리(status가 200 미만이면 중간 응답이고, 더 온다)stream_id, request 또는 status와 fields, end_stream, user
    PROVEN_H2_EVENT_DATA본문의 한 조각. in 안을 가리키는 뷰다stream_id, data, end_stream, user
    PROVEN_H2_EVENT_TRAILERS트레일러 필드: 상대 쪽의 스트림은 끝났다stream_id, fields, user
    PROVEN_H2_EVENT_STREAM_RESET스트림이 끝나기 전에 끝났다: 상대가 리셋했거나, 그 스트림에서 규칙을 어겼거나, 처리하지 않은 채 작별했다stream_id, code, user; 클라이언트에서는 그래도 응답이 완전할 때 end_stream(아래); 상대의 헤더 목록이 max_header_list_bytes를 넘어 이쪽이 리셋했을 때 too_large
    PROVEN_H2_EVENT_STREAM_WRITABLE잘렸던 전송을 이어 갈 수 있다stream_id, user
    PROVEN_H2_EVENT_PONGproven_h2_conn_ping의 답data: 그 여덟 바이트
    PROVEN_H2_EVENT_GOAWAY상대가 새 스트림을 받지 않는다code, last_stream_id, data (함께 보낸 텍스트: 처음 256바이트, 로그용)
    PROVEN_H2_EVENT_CLOSED연결이 끝났고, 모든 스트림도 함께 끝났다. 남은 출력을 보내고 닫는다code

    이 표에서 세 가지는 다시 볼 만하다.

    본문은 복사되지 않는다. DATA 사건은 여러분이 넣어 준 버퍼 안을 가리키므로, 어떤 크기의 본문이든 여러분의 읽기 한 번보다 크지 않은 조각으로 지나간다. 세 번의 읽기에 걸쳐 도착한 프레임은 사건 셋이고, end_stream은 마지막 것에 붙는다.

    상대의 잘못은 오류가 아니라 사건이다. 상대가 프로토콜을 어겨도 proven_h2_conn_feed는 PROVEN_OK를 돌려준다: 연결은 코드를 담은 GOAWAY 프레임을 쌓아 두고 PROVEN_H2_EVENT_CLOSED를 알린다. 스트림 하나의 잘못은 그 스트림의 PROVEN_H2_EVENT_STREAM_RESET일 뿐이다. 상대가 한 일 때문에 feed가 돌려주는 오류는 하나, PROVEN_ERR_INVALID_FORMAT이다: 서버인데 클라이언트가 24바이트 서문으로 시작하지 않았을 때. 그것은 HTTP/2가 아니다. 상대에게 아무 말도 하지 않으며, 달라지는 첫 바이트에서 알린다 - 그래서 그 바이트들은 여전히 여러분의 것이고 HTTP/1.1 파서에 넘길 수 있다.

    입력이 필요 없는 사건이 있다. 스트림이 다시 쓸 수 있게 되는 것은 무언가 도착했을 때가 아니라 출력이 나갔을 때다. 그러니 proven_h2_conn_output_sent 뒤에는 proven_h2_conn_feed를 빈 뷰로 한 번 더 불러 생긴 사건을 받는다.

    클라이언트는 의사 헤더 필드 넷으로 시작하는 헤더 목록으로 스트림을 열고, 서버는 :status로 시작하는 목록으로 스트림에 답한다. 둘 다 한 바이트라도 쌓이기 전에 4절의 규칙으로 검사되므로, 이 라이브러리는 자기가 거부할 것을 보내지 않는다.

    proven_h2_conn_send_data는 내민 것보다 적게 가져갈 수 있고 전혀 가져가지 않을 수도 있으며, 그것은 오류가 아니다. 가져가는 양은 세 가지 가운데 가장 작은 것이다: 스트림의 윈도, 연결의 윈도, max_buffered_output 아래에 남은 자리. 나머지는 쥐고 있다가 PROVEN_H2_EVENT_STREAM_WRITABLE이 그 스트림을 가리키면 다시 내민다. end_stream은 내민 것이 모두 받아들여졌을 때 효력이 생긴다.

    여러 스트림이 연결의 윈도를 기다리고 있으면 차례대로 알린다. 알림을 받은 스트림은 윈도에 있는 만큼을 가져가고, 자리가 다시 생기면 그 다음 스트림부터 찾는다. 그래서 긴 본문 하나가 같은 연결의 다른 스트림을 붙잡아 두지 않는다. (v0.37.1 전에는 그럴 수 있었다: 찾기가 매번 같은 스트림에서 시작했다.)

    받는 쪽의 흐름 제어#

    void proven_h2_conn_consumed(proven_h2_conn_t *conn, proven_u32 stream_id, proven_size_t n);

    상대는 이쪽이 받겠다고 한 만큼만 보낼 수 있다: 스트림마다 initial_window 바이트, 연결 전체로도 그만큼. 자리는 바이트가 도착했을 때가 아니라 처리했다고 말할 때 돌아온다 - proven_h2_conn_consumed로. 뒤처져서 이 호출을 멈춘 처리기는 많아야 윈도 하나만큼을 버퍼에 둔 채 상대를 멈춘다. 이것이 HTTP/2의 역압(backpressure)이고, 이 호출이 말 그대로일 때만 통한다: 바이트를 건네받았을 때가 아니라 가야 할 곳으로 보냈을 때 부른다.

    아무도 소비하지 않는 것은 연결이 스스로 돌려준다: 패딩, 리셋된 스트림으로 온 데이터, 그리고 스트림이 끝날 때 아직 소비되지 않았던 것.

    상대가 연결에 쥐게 하거나 하게 할 수 있는 것#

    모든 양에는 설정이 있고, 모든 설정에는 기본값이 있다:

    설정기본값경계에서
    max_concurrent_streams100넘는 스트림은 거절되고(REFUSED_STREAM) 알려지지 않는다
    initial_window65,535스트림의 윈도를 넘는 DATA는 그 스트림의 FLOW_CONTROL_ERROR, 연결의 윈도를 넘으면 연결의 오류
    max_frame_size16,384더 큰 프레임은 연결의 FRAME_SIZE_ERROR
    max_header_list_bytes16 KiB더 큰 목록은 그 스트림의 PROTOCOL_ERROR. 이 값의 두 배를 넘는 헤더 블록은 연결을 끝낸다

    max_buffered_output64 KiB얼마가 나갈 때까지 본문을 더 받지 않고 submit 호출은 PROVEN_ERR_BUSY로 답한다. 따로 센다: 읽지 않는 상대에게 프로토콜이 빚진 답이 이만큼을 넘으면 연결이 끝난다
    max_reset_debt100리셋된 스트림 - 상대가 했거나 상대의 잘못 때문에 - 이 제대로 끝난 스트림보다 이만큼 많은 뒤: 하나 더 오면 ENHANCE_YOUR_CALM으로 연결이 끝난다
    enable_connect_protocolfalse서버: 확장 CONNECT(RFC 8441)를 받고 첫 설정에서 그렇다고 말한다. 이벤트 구동 서버는 http2_websocket(15장)으로 이것을 정한다

    마지막 줄은, 서버가 일을 시작하게 해 놓고 버리게 하려고 스트림을 열자마자 리셋하기를 되도록 빨리 되풀이하는 클라이언트에 대한 답이다. 시계는 쓰지 않는다: 리셋 하나가 하나를 더하고, 제대로 끝난 스트림 하나가 하나를 덜며, 시작한 것을 대체로 끝내는 상대는 한도 근처에도 가지 않는다.

    막 열린 연결은 많아야 400바이트인 블록 하나를 쥔다. 요청을 실어 나른 뒤 다시 한가해진 연결은 그것과, 마지막 스트림들이 어떻게 끝났는지의 기록과, 압축 테이블 둘을 쥔다. 테이블은 쓰이는 만큼 자란다: 작은 요청 백 개 뒤에 3 KiB 미만, 둘 다 기본 크기 4,096바이트로 가득 찼을 때 약 12.5 KiB, 테이블 없이는 1,280바이트 미만. 스트림이 열려 있는 동안에는 스트림마다 48바이트와, 헤더 목록 하나를 읽는 데 쓰는 버퍼 - max_header_list_bytes의 다섯 배, 기본값에서 80 KiB - 를 더 쥔다. 이 마지막 것은 연결마다 가질 필요가 없다: 설정에 proven_h2_header_buffer_size 바이트짜리 header_buffer를 주면 한 스레드가 모는 모든 연결이 같은 메모리에 읽을 수 있다 - 거기 읽힌 것이 곧 사건이 알리는 것이고, 사건은 다음 호출까지만 유효하다. 6절의 서버가 이렇게 한다.

    연결 뒤에 바꾸는 설정#

    proven_err_t proven_h2_conn_set_max_streams(proven_h2_conn_t *conn, proven_u32 n);
proven_err_t proven_h2_conn_set_initial_window(proven_h2_conn_t *conn, proven_u32 n);

    설정 가운데 둘은 연결이 도는 동안 바꿀 수 있다(v0.79.0). 하나는 상대가 한꺼번에 열 수 있는 스트림 수이고, 다른 하나는 스트림마다 처음 주는 창이다. 바쁜 서버는 둘을 줄였다가 나중에 다시 올린다. 호출할 때마다 SETTINGS 프레임이 하나 쌓인다. RFC 9113에 따르면 설정은 상대가 확인한 뒤부터 유효하고, 연결도 그대로 따른다.

    • 만들 때 준 값이 상한이다. 연결이 쥘 수 있는 메모리는 만들 때 그 값으로 정해진다. 그래서 값을 낮췄다가 다시 올릴 수는 있어도 넘을 수는 없다. 넘으면 PROVEN_ERR_INVALID_ARG이다.
    • 확인 전에는 큰 쪽이 유효하다. 상대는 변경을 읽기 전의 값으로 스트림을 열거나 본문을 보낼 수 있고, 연결은 그것을 받는다. 확인 뒤에는 새 수를 넘는 스트림을 REFUSED_STREAM으로 거절하고(클라이언트는 다시 보낼 수 있다), 스트림 창을 넘는 DATA는 그 스트림의 FLOW_CONTROL_ERROR이다.

    • 열린 것은 자르지 않는다. 이미 열린 스트림은 몇 개든 계속된다.

      • 창을 바꾸면 열린 스트림마다 창이 그 차이만큼 움직인다(RFC 9113 6.9.2).
      • 낮추면 어떤 스트림은 남은 창이 0보다 작아질 수 있다. 그 스트림은 충분히 소비될 때까지 기다린다.
      • 올리면 바로 유효하다.
      • 연결 전체의 창은 설정이 아니어서 바뀌지 않는다.
    • 진행 중인 변경은 하나다. 확인을 기다리는 동안 들어온 호출은 기억해 두었다가, 확인이 오면 마지막 값들을 프레임 하나로 보낸다. 몇 번을 불러도 프레임은 하나다.
    • 클라이언트에서는 max_streams가 이쪽이 여는 스트림 수의 상한도 되고, 그 상한은 바로 유효하다.

    아래 예제는 서버에서 둘을 낮추고, 클라이언트가 새 수를 지키는 것을 보인다.

    작별#

    void proven_h2_conn_shutdown(proven_h2_conn_t *conn, proven_h2_error_t code);
proven_err_t proven_h2_conn_ping(proven_h2_conn_t *conn, const proven_byte_t opaque[8]);
bool proven_h2_conn_is_closed(const proven_h2_conn_t *conn);

    PROVEN_H2_NO_ERROR로 부른 proven_h2_conn_shutdown은 GOAWAY 프레임을 쌓아 두고 열려 있는 스트림이 끝나게 둔다: 새 스트림은 받지도 시작하지도 않으며, 마지막 스트림이 끝나면 PROVEN_H2_EVENT_CLOSED가 따라온다. 상대의 GOAWAY도 같은 방식으로 처리되며, 클라이언트는 서버가 처리하지 않은 스트림이 어느 것인지 듣는다 - PROVEN_H2_REFUSED_STREAM이 담긴 PROVEN_H2_EVENT_STREAM_RESET - 그것들은 다른 연결에서 다시 보내도 안전하기 때문이다.

    예제: 사이에 소켓이 없는, 연결의 양쪽 끝#

    #include <stdio.h>
#include <string.h>

/*
 * 소켓 없이 양쪽 끝을 모두 가진 HTTP/2 연결: 한쪽이 쌓아 둔 것을 마치 선을 건너온 것처럼
 * 다른 쪽에 넘겨준다.
 *
 * proven_h2_conn_t는 입출력을 하지 않는다. 상대가 보낸 바이트를 넣어 주면 사건을 한 번에
 * 하나씩 알려 주고, 보내 달라고 하면 프레임을 쌓아 두어 가져가게 한다. 실제 프로그램은
 * carry()가 있는 자리에 소켓(과 TLS)을 둔다.
 */

typedef struct {
    proven_h2_conn_t *conn;
    const char *name;
    /* 이쪽 끝이 알게 된 것. 아래의 검사에 쓴다. */
    int requests, responses, trailers, resets, writable, pongs, goaways, closed;
    proven_size_t body_bytes;
    proven_u32 last_stream, reset_code, close_code;
    bool hold;                             /* DATA를 소비했다고 알리지 않는다 */
} ex_end_t;

/* `in`의 바이트에 든 사건을 모두 받는다. 한 번 호출에 사건 하나다: 사건도 없고 남은 것도 없을
 * 때까지 나머지를 가지고 다시 호출한다. */
static bool take_events(ex_end_t *e, proven_mem_view_t in) {
    proven_size_t pos = 0;
    for (;;) {
        proven_size_t used = 0;
        proven_h2_event_t ev;
        if (proven_h2_conn_feed(e->conn, (proven_mem_view_t){ in.ptr + pos, in.size - pos }, &used, &ev) != PROVEN_OK) return false;
        pos += used;
        switch (ev.kind) {
            case PROVEN_H2_EVENT_NONE:
                if (pos == in.size) return true;           /* 다 썼다: 더 읽어 온다 */
                break;
            case PROVEN_H2_EVENT_HEADERS:
                e->last_stream = ev.stream_id;
                if (ev.status == 0) {                      /* 서버: 이미 검사되고 나뉜 요청 */
                    e->requests++;
                    printf("%s: stream %u asks %.*s %.*s\n", e->name, (unsigned)ev.stream_id, (int)ev.request.method.size, (const char *)ev.request.method.ptr,
                           (int)ev.request.path.size, (const char *)ev.request.path.ptr);
                } else {                                   /* 클라이언트: 응답의 머리 */
                    e->responses++;
                    printf("%s: stream %u answers %u%s\n", e->name, (unsigned)ev.stream_id, (unsigned)ev.status, ev.user ? " (the stream we marked)" : "");
                }
                break;
            case PROVEN_H2_EVENT_DATA:
                /* ev.data는 `in` 안을 가리킨다: 복사된 것이 없다. 소비했다고 알려야 상대가
                 * 더 보낼 수 있다. */
                e->body_bytes += ev.data.size;
                if (!e->hold) proven_h2_conn_consumed(e->conn, ev.stream_id, ev.data.size);
                break;
            case PROVEN_H2_EVENT_TRAILERS: e->trailers++; break;
            case PROVEN_H2_EVENT_STREAM_RESET: e->resets++; e->reset_code = ev.code; break;
            case PROVEN_H2_EVENT_STREAM_WRITABLE: e->writable++; break;
            case PROVEN_H2_EVENT_PONG: e->pongs++; break;
            case PROVEN_H2_EVENT_GOAWAY: e->goaways++; break;
            case PROVEN_H2_EVENT_CLOSED: e->closed++; e->close_code = ev.code; return true;
        }
    }
}

/* 선: `from`이 쌓아 둔 것이 `to`로 간다. 그런 다음 `from`에게 빈 입력으로 한 번 더 묻는다 -
 * 보낸 덕분에 생긴 사건, 곧 다시 보낼 수 있게 된 스트림이 있는지. */
static bool carry(ex_end_t *from, ex_end_t *to) {
    static proven_byte_t wire[200000];
    proven_mem_view_t out = proven_h2_conn_pending_output(from->conn);
    if (out.size > sizeof wire) return false;
    if (out.size > 0) memcpy(wire, out.ptr, out.size);
    proven_size_t n = out.size;
    proven_h2_conn_output_sent(from->conn, n);             /* 소켓이라면 몇 바이트를 받았는지 알려 줄 것이다 */
    if (!to->closed && !take_events(to, (proven_mem_view_t){ wire, n })) return false;
    return from->closed || take_events(from, (proven_mem_view_t){ wire, 0 });
}

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    ex_end_t client = { .name = "client" }, server = { .name = "server" };

    /* 0은 모든 한계에서 기본값을 뜻한다. 꼭 말해야 하는 것은 `server` 하나다. */
    proven_h2_config_t ccfg = { .alloc = heap };
    proven_h2_config_t scfg = { .alloc = heap, .server = true, .max_concurrent_streams = 10 };
    EXAMPLE_REQUIRE(proven_h2_conn_create(&ccfg, &client.conn) == PROVEN_OK && proven_h2_conn_create(&scfg, &server.conn) == PROVEN_OK, "two ends");

    /* 여는 말은 이미 쌓여 있다: 클라이언트의 서문과 양쪽의 설정. */
    EXAMPLE_REQUIRE(carry(&client, &server) && carry(&server, &client) && carry(&client, &server), "settings cross and are acknowledged");
    /* 첫 요청 전에 이것을 기다리는 클라이언트는 서버가 받는 것보다 많은 스트림을 요청하는 일이 없다. */
    EXAMPLE_REQUIRE(proven_h2_conn_has_peer_settings(client.conn) && proven_h2_conn_has_peer_settings(server.conn), "each end has the other's settings");

    // ---- 본문이 있는 요청과 그 응답 ----------------------------------------------------------
    proven_http_header_t request[] = {
        { PROVEN_LIT(":method"), PROVEN_LIT("POST") }, { PROVEN_LIT(":scheme"), PROVEN_LIT("https") },
        { PROVEN_LIT(":authority"), PROVEN_LIT("www.example.com") }, { PROVEN_LIT(":path"), PROVEN_LIT("/upload") },
        { PROVEN_LIT("content-type"), PROVEN_LIT("text/plain") },
    };
    proven_u32 stream = 0;
    int mark = 0;
    EXAMPLE_REQUIRE(proven_h2_conn_submit_request(client.conn, request, 5, false, &stream) == PROVEN_OK && stream == 1, "a client's first stream is 1");
    proven_h2_conn_stream_set_user(client.conn, stream, &mark);       /* 이 스트림의 사건에 실려 온다 */
    EXAMPLE_REQUIRE(proven_h2_conn_stream_user(client.conn, stream) == &mark, "and it can be asked for");
    proven_result_size_t sent = proven_h2_conn_send_data(client.conn, stream, proven_mem_view_from_u8(PROVEN_LIT("hello, ")), false);
    EXAMPLE_REQUIRE(sent.err == PROVEN_OK && sent.value == 7, "seven bytes of body");
    sent = proven_h2_conn_send_data(client.conn, stream, proven_mem_view_from_u8(PROVEN_LIT("world")), true);     /* true: 본문의 끝 */
    EXAMPLE_REQUIRE(sent.err == PROVEN_OK && sent.value == 5 && carry(&client, &server), "and five more, the last");
    EXAMPLE_REQUIRE(server.requests == 1 && server.body_bytes == 12 && proven_h2_conn_stream_count(server.conn) == 1, "the server has the request and its twelve bytes");

    proven_http_header_t response[] = { { PROVEN_LIT(":status"), PROVEN_LIT("200") }, { PROVEN_LIT("content-type"), PROVEN_LIT("text/plain") } };
    proven_http_header_t trailers[] = { { PROVEN_LIT("x-checksum"), PROVEN_LIT("9f86d081") } };
    EXAMPLE_REQUIRE(proven_h2_conn_submit_response(server.conn, stream, response, 2, false) == PROVEN_OK, "a response head");
    sent = proven_h2_conn_send_data(server.conn, stream, proven_mem_view_from_u8(PROVEN_LIT("thanks")), false);
    EXAMPLE_REQUIRE(sent.err == PROVEN_OK && sent.value == 6 && proven_h2_conn_send_trailers(server.conn, stream, trailers, 1) == PROVEN_OK, "a body, and trailers to end it");
    EXAMPLE_REQUIRE(carry(&server, &client), "back to the client");
    EXAMPLE_REQUIRE(client.responses == 1 && client.body_bytes == 6 && client.trailers == 1, "the client has all three parts");
    EXAMPLE_REQUIRE(proven_h2_conn_stream_count(client.conn) == 0 && proven_h2_conn_stream_count(server.conn) == 0, "and the stream is over at both ends");

    // ---- 흐름 제어: 뒤처진 수신자는 송신자를 멈춘다 -------------------------------------------
    static proven_byte_t big[100000];
    server.hold = true;                                    /* 서버의 처리기가 바쁘다: 아무것도 소비하지 않는다 */
    server.body_bytes = 0;
    /* 어느 중간 지점도 기억하면 안 되는 필드는 바로 다음 목록 하나에 대해 표시한다: 여기서는 마지막 필드를, 키인 셈 치고. */
    static const bool keep_out[5] = { false, false, false, false, true };
    proven_h2_conn_next_sensitive(client.conn, keep_out);
    EXAMPLE_REQUIRE(proven_h2_conn_submit_request(client.conn, request, 5, false, &stream) == PROVEN_OK && stream == 3 && carry(&client, &server), "a second request");
    sent = proven_h2_conn_send_data(client.conn, stream, (proven_mem_view_t){ big, sizeof big }, true);
    const proven_size_t taken = sent.value;
    printf("client: offered %u bytes, %u were taken\n", (unsigned)sizeof big, (unsigned)taken);
    /* 연결의 창은 기본 65,535바이트이고, 첫 요청의 12바이트는 아직 돌려받지 못했다: 창은
     * 바이트마다가 아니라 묶어서 다시 열린다. */
    EXAMPLE_REQUIRE(sent.err == PROVEN_OK && taken == 65535 - 12, "what the windows allow and no more: taking less than was offered is not an error");
    EXAMPLE_REQUIRE(proven_h2_conn_send_room(client.conn, stream) == 0 && carry(&client, &server) && carry(&server, &client) && client.writable == 0, "nothing more may go until the server says so");
    proven_h2_conn_consumed(server.conn, stream, taken);   /* 처리기가 따라잡았다 */
    server.hold = false;
    EXAMPLE_REQUIRE(carry(&server, &client) && client.writable == 1, "and now the client is told: PROVEN_H2_EVENT_STREAM_WRITABLE");
    sent = proven_h2_conn_send_data(client.conn, stream, (proven_mem_view_t){ big + taken, sizeof big - taken }, true);
    EXAMPLE_REQUIRE(sent.err == PROVEN_OK && sent.value == sizeof big - taken && carry(&client, &server) && server.body_bytes == sizeof big, "the rest follows");

    /* 서버는 이 요청에 답하는 대신 포기한다. */
    EXAMPLE_REQUIRE(proven_h2_conn_reset(server.conn, stream, PROVEN_H2_CANCEL) == PROVEN_OK && carry(&server, &client), "a reset");
    EXAMPLE_REQUIRE(client.resets == 1 && client.reset_code == PROVEN_H2_CANCEL && proven_h2_conn_stream_count(client.conn) == 0, "which the client hears of, with the code");

    // ---- 거기 누구 있는가? ------------------------------------------------------------------
    static const proven_byte_t opaque[8] = { 'p', 'r', 'o', 'v', 'e', 'n', '!', '!' };
    EXAMPLE_REQUIRE(proven_h2_conn_ping(client.conn, opaque) == PROVEN_OK && carry(&client, &server) && carry(&server, &client) && client.pongs == 1, "a ping is answered by the connection itself");

    // ---- 연결 뒤에 바꾸는 설정 ----------------------------------------------------------------
    /* 바쁜 서버가 동시 스트림 수와 창을 줄인다. SETTINGS 프레임 하나이고, 클라이언트가 확인한
     * 뒤부터 유효하다. 만들 때 준 값이 상한이고, 이미 열린 스트림은 건드리지 않는다. */
    EXAMPLE_REQUIRE(proven_h2_conn_set_max_streams(server.conn, 1) == PROVEN_OK && proven_h2_conn_set_initial_window(server.conn, 16384) == PROVEN_OK, "the server lowers both");
    EXAMPLE_REQUIRE(carry(&server, &client) && carry(&client, &server), "the change crosses, and is acknowledged");
    EXAMPLE_REQUIRE(proven_h2_conn_submit_request(client.conn, request, 5, true, &stream) == PROVEN_OK && carry(&client, &server), "one request");
    proven_u32 second = 0;
    EXAMPLE_REQUIRE(proven_h2_conn_submit_request(client.conn, request, 5, true, &second) == PROVEN_ERR_BUSY, "and not a second at the same time: the client holds itself to the new number");
    EXAMPLE_REQUIRE(proven_h2_conn_set_max_streams(server.conn, 11) == PROVEN_ERR_INVALID_ARG, "above the number given at creation: refused");
    EXAMPLE_REQUIRE(proven_h2_conn_reset(server.conn, stream, PROVEN_H2_CANCEL) == PROVEN_OK && carry(&server, &client), "the server lets that one go");

    // ---- 규칙을 어기는 상대 ------------------------------------------------------------------
    /* 아무것도 더하지 않는 WINDOW_UPDATE는 프로토콜 오류다. 연결은 상대에게 그렇게 말하고
     * (GOAWAY), 끝났다고 알리고, 더는 아무것도 받지 않는다. */
    ex_end_t strict = { .name = "strict" };
    EXAMPLE_REQUIRE(proven_h2_conn_create(&scfg, &strict.conn) == PROVEN_OK, "another server");
    proven_byte_t bad[128];
    proven_size_t len = PROVEN_H2_PREFACE_SIZE;
    memcpy(bad, PROVEN_H2_PREFACE, PROVEN_H2_PREFACE_SIZE);
    EXAMPLE_REQUIRE(proven_h2_write_settings((proven_mem_mut_t){ bad, sizeof bad }, &len, NULL, 0) == PROVEN_OK, "a client that opens properly");
    static const proven_byte_t zero_increment[13] = { 0, 0, 4, PROVEN_H2_WINDOW_UPDATE, 0, 0, 0, 0, 0, 0, 0, 0, 0 };
    memcpy(bad + len, zero_increment, sizeof zero_increment);
    len += sizeof zero_increment;

    주의사항, 그리고 무엇이 잘못되는가#

    • 호출할 때마다, 쌓인 것을 보낸다. 연결은 스스로 답한다 - 승인, 윈도 갱신, 리셋, 마지막 GOAWAY - 그리고 그 답은 여러분이 무엇을 요청했든 아니든 proven_h2_conn_pending_output에 있다.
    • 보낸 뒤에는, 빈 입력을 넣는다. 빈 뷰로 부른 proven_h2_conn_feed가 전송 덕분에 생긴 사건을 거둔다. 그러지 않고 소켓을 기다리는 드라이버는 자기를 기다리고 있는 상대를 기다리게 된다.
    • proven_h2_conn_send_data가 0을 돌려주는 것은 세상의 끝도, 스트림의 끝도 아니다. "지금은 아니다"다. 예외는 end_stream과 함께 준 빈 data다: 그것은 언제나 나가고, 그때의 0은 "끝났다"는 뜻이다.
    • 뷰는 다음 호출에서 죽는다. 사건의 필드와 쌓인 출력은 연결을 받는 다음 호출까지만 유효하다. 간직할 것은 복사한다.
    • 포인터는 사건과 함께 온다. 스트림이 끝나면 proven_h2_conn_stream_user는 더는 그것을 찾지 못한다: 그 스트림의 마지막 사건이 user에 포인터를 싣고 오며, 가리키는 것을 해제할 곳은 거기다.
    • PROVEN_H2_EVENT_CLOSED는 모든 스트림을 하나하나 말하지 않고 끝낸다. 열려 있던 것의 목록은 여러분의 것을 따라간다.
    • 요청보다 먼저 끝난 응답은 클라이언트에게 그만 보내라고 말한다. 서버 쪽은 RFC 9113이 정한 대로 NO_ERROR를 담은 RST_STREAM을 보내고 스트림은 끝난다. 클라이언트는 응답 뒤에 PROVEN_H2_NO_ERROR가 담긴 PROVEN_H2_EVENT_STREAM_RESET을 본다: 실패가 아니고, 이벤트의 end_stream이 참이다. 어떤 서버는 스트림을 끝내는 대신 NO_ERROR로 리셋한다, 응답의 content-length가 선언한 바이트를 모두 보낸 뒤에. 길이가 빠진 것이 없음을 보여 주므로 그때도 end_stream이 참이다. 한 바이트라도 모자라거나, 길이가 없거나(본문이 없는 길이 - HEAD, 204, 304 - 도 마찬가지), 다른 코드라면 거짓이다: 응답이 잘렸을 수 있다.
    • 연결 하나는 한 번에 한 스레드의 것이다.
    • 시계가 없으니 타임아웃도 없다. 연결을 열고 아무 말도 하지 않는 상대, 윈도를 끝내 열지 않는 상대를 포기하는 것은 호출자의 일이다.

    6. 이벤트 구동 서버의 HTTP/2#

    typedef struct {
    /* ... 15장이 설명하는 모든 것 ... */
    bool http2;
    proven_size_t max_concurrent_streams;
    proven_size_t http2_window_bytes;
} proven_http_event_server_config_t;

    15장의 이벤트 구동 서버는 설정이 http2라고 하면 HTTP/2로 말한다. 처리기에게는 그 밖에 달라지는 것이 없다: 같은 콜백 넷, 같은 proven_http_stream_* 호출, 같은 요청 타입. 연결 위의 교환 하나였던 것이 이제 여러 스트림 가운데 하나이고, 옮겨 주는 일은 서버가 한다:

    처리기가 하는 일HTTP/2에서는
    head->method, head->target, 필드를 읽는다의사 헤더 필드와 목록. 이미 4절의 규칙으로 검사되었다. Host가 있다 - 클라이언트가 host 필드를 보내지 않았으면 :authority로 만든다. version_minor는 1이다
    Content-Length나 Transfer-Encoding으로 본문이 따라옴을 안다똑같다: HTTP/2는 둘 다 없이 본문을 보낼 수 있고, 그런 요청에는 Transfer-Encoding: chunked를 붙여 준다. 뜻은 그대로다 - 길이를 알리지 않은 본문
    proven_http_stream_respond, _begin, _write, _end응답 머리, 클라이언트의 윈도와 출력 한계가 허락하는 만큼의 DATA 프레임, 스트림의 끝. 필드 이름은 소문자로 나간다. Keep-Alive, Proxy-Connection, Upgrade는 보내지 않는다
    _write에서 거절당하고 on_writable을 기다린다HTTP/1.1과 꼭 같다 - 이유도 같은 둘인데 처리기는 둘을 구별할 수 없다: 서버가 max_buffered_output만큼 쥐고 있거나, 클라이언트가 자리를 내주지 않는다
    proven_http_stream_pauseHTTP/1.1처럼, 재개할 때까지 on_body가 없다. 이미 도착한 것은 쥐고 있다가 - 많아야 윈도 하나, 클라이언트는 그것이 소비되었다는 말을 듣지 못해 더 보낼 수 없으므로 - 재개할 때 한 조각으로 전달한다
    proven_http_stream_compress그대로다: 압축기는 프레이밍 위에 있다
    proven_http_stream_abort스트림이 리셋된다. 연결과 그 밖의 스트림은 계속된다
    on_done(why)를 받는다전과 같이 on_request마다 한 번: 응답 전체가 넘겨졌으면 PROVEN_OK, 클라이언트가 스트림을 리셋했거나 연결이 끝났으면 PROVEN_ERR_RESET, PROVEN_ERR_TIMEOUT, 한도를 넘는 본문은 PROVEN_ERR_OUT_OF_BOUNDS

    proven_http_stream_protocol은 로그 한 줄을 위해 1이나 2(HTTP/3이면 3, 9절)를 답한다. 처리기가 물을 다른 이유는 드물다.

    연결이 어느 프로토콜로 말하는가#

    • TLS에서는 핸드셰이크가 말한다(ALPN). http2가 켜져 있으면 TLS 설정이 h2를 - 그리고 더 새로운 것이 없는 클라이언트를 위해 그 뒤에 http/1.1을 - 내놓아야 하고, 꺼져 있으면 h2를 내놓아서는 안 된다: 핸드셰이크에서 합의하고는 말하지 않을 수 있는 조합을 서버는 생성 때 거부한다. 1.2보다 오래된 TLS에서, 또는 순방향 비밀성과 인증된 암호화가 없는 1.2 스위트에서 h2를 협상한 연결 - 14장의 구형 옵션을 켰을 때만 가능하다 - 은 RFC 9113이 요구하는 대로 INADEQUATE_SECURITY로 끝낸다.
    • TLS 설정에 early_data가 있으면 0-RTT(14장 6절, v0.84.0). HTTP/1.1, HTTP/3과 같다: HEADERS가 클라이언트의 조기 데이터로 온 요청은 핸드셰이크가 끝나기 전에 핸들러에게 가고, proven_http_stream_early가 참이며, 바로 답할 수 있다. 본문 없는 GET, HEAD, OPTIONS만 거기까지 간다 - 그 밖의 것이 조기에 오면 서버가 그 스트림에 425로 답한다.
    • 평문에서는 첫 바이트들이 말한다. HTTP/2를 원한다는 것을 아는 클라이언트는 24바이트 서문으로 시작한다(curl의 --http2-prior-knowledge). 그 밖의 것은 HTTP/1.1이다. 서버는 달라지는 첫 바이트에서 정하므로, 서문과 첫 글자가 같은 POST는 둘째 바이트에서 HTTP/1.1이 된다. Upgrade: h2c는 제공하지 않는다: RFC 9113이 없앴다.

    두 프로토콜은 한 포트에서, 한 처리기로, 동시에 서비스된다.

    max_connections전과 같이 연결 수: HTTP/2 연결은 스트림을 몇 개 나르든 하나다
    max_concurrent_streams (0: 100)한 연결에서 진행 중인 요청 수. 클라이언트에게 그 수를 알리고, 넘는 스트림은 거절한다

    max_head_bytes, max_headersHPACK이 세는 방식의 요청 헤더 목록 크기. max_headers보다 필드가 많으면 431
    max_body_bytes요청마다: 본문이 아직 도착하는 중에 413을 보내며, 그것이 클라이언트에게 그만 보내라고 말한다
    max_buffered_output읽지 않는 클라이언트를 위해 연결이 쥐는 양. 그 연결의 모든 스트림을 합쳐서
    head_timeout_ms연결의 첫 바이트부터 첫 요청까지
    body_timeout_ms본문을 기다리는 요청 하나의 침묵: 그 스트림이 리셋되고, 연결과 다른 스트림은 계속된다
    http2_header_table_bytes (0: 4,096), http2_no_header_table방향마다의 헤더 압축 테이블: 한가한 연결이 쥐게 될 수 있는 양과, 되풀이되는 필드를 보내는 비용 사이의 선택
    write_timeout_ms쥐고 있는 출력이 하나도 받아들여지지 않음: 연결이 끝난다
    idle_timeout_ms열린 스트림이 없음: 서버가 작별하고(GOAWAY) 닫는다

    max_concurrent_streams는 서버가 도는 동안 바꿀 수 있다(v0.79.0).

    • 루프의 스레드에서 부르고, 값은 1부터 설정값까지다. 설정값이 상한으로 남는다.
    • HTTP/2 연결마다 클라이언트에게 새 수를 알린다(5절의 proven_h2_conn_set_max_streams). 나중에 생기는 연결은 새 수로 시작한다.
    • 진행 중인 요청은 계속된다. 클라이언트가 확인하기 전에는 이전 수 안에서 요청을 더 시작할 수 있다.
    • HTTP/3에는 따로 규칙이 있다(9절).
    • 새 요청을 아예 받지 않으려면 서버를 종료한다. 0은 PROVEN_ERR_INVALID_ARG이다.

    proven_http_event_server_set_window(v0.82.0)는 요청 본문에 같은 일을 한다.

    • 루프의 스레드에서 부르면 n이, 클라이언트가 처리기보다 앞서 보낼 수 있는 양의 천장이 된다. 스트림당, 연결당, HTTP/2와 HTTP/3, 열린 연결과 앞으로 올 연결에.
    • 돌려주는 room은 그 천장까지다 - 클라이언트가 아직 보낼 수 있는 양과 서버가 읽지 않고 쥔 양을 합쳐서. 자라는 창(http2_window_bytes를 0으로 둔 경우)은 거기서 멈추고, 올리면 다시 자란다. 설정한 창은 그대로 프로토콜이 주는 최대다.
    • 이미 준 것은 남는다: 더 낮게 알린 HTTP/2 창은 클라이언트가 확인한 뒤에 효력이 있고, HTTP/3 credit은 되돌릴 수 없다. 그래서 낮춘 천장은 남은 것이 쓰이면서 드러난다.
    • HTTP/2 연결마다 min(n, 그 연결의 창)을 초기 창으로 알린다(5절의 proven_h2_conn_set_initial_window). 지금 열린 HTTP/3 연결에서 클라이언트가 나중에 여는 스트림은 핸드셰이크에서 약속한 창을 여전히 쓸 수 있고, 나중에 생기는 연결에는 많아야 n을 약속한다.

    proven_http_event_server_stop_listening이 우아하게 끝내는 길이다: HTTP/2 연결마다 GOAWAY를 보내고, 가진 스트림을 끝내고, 닫는다. proven_http_event_server_destroy는 모든 것을 즉시 끝내고, 열려 있던 스트림의 처리기는 모두 on_done(PROVEN_ERR_RESET)을 받는다.

    예제: 포트 하나, 처리기 하나, 프로토콜 둘#

    #include <stdio.h>
#include <string.h>

/*
 * 서버 하나, 포트 하나, 프로토콜 둘: `http2`를 켠 이벤트 구동 HTTP 서버.
 *
 * 아래 처리기는 평범한 처리기다 - 같은 콜백, 같은 스트림 호출 - 묻지 않는 한 요청이 어느
 * 프로토콜로 왔는지 모른다. 그런 다음 HTTP/1.1 클라이언트와 HTTP/2 클라이언트가 같은 포트로
 * 말을 건다. 여기의 HTTP/2 클라이언트는 이 장 5절의 연결 엔진에 소켓을 통과시킨 것으로, 그것이
 * 무엇으로 이루어지는지 보여 준다: 마흔 줄이다. (연결을 간직하고 함께 쓰는 라이브러리 자체의
 * 클라이언트는 7절에 있다.)
 */

typedef struct { proven_loop_t *loop; int served, over_http2; } ex_app_t;

static void on_request(void *ctx, proven_http_stream_t *stream, const proven_http_request_t *head) {
    ex_app_t *app = ctx;
    /* 요청은 어느 쪽이든 같아 보인다: 메서드, 대상, 필드 - 그 가운데 Host도 있다. HTTP/2는
     * 그것을 `:authority`로 싣고, 서버는 익숙한 이름으로 넘겨준다. */
    /* TLS 설정에 `early_data`가 있으면 요청은 조기 데이터로 올 수 있고(14장 6절),
     * 공격자가 재전송한 사본일 수 있다. 이 답은 두 번 해도 괜찮다. 그렇지 않은 요청이라면 425로
     * 답하고, 클라이언트는 나중에 다시 보낸다. */
    if (proven_http_stream_early(stream) && head->method != PROVEN_HTTP_GET) {
        (void)proven_http_stream_respond(stream, 425, NULL, 0, (proven_mem_view_t){ 0 });
        return;
    }
    const int protocol = proven_http_stream_protocol(stream);
    char text[96];
    int n = snprintf(text, sizeof text, "%.*s over HTTP/%d\n", (int)head->target.size, (const char *)head->target.ptr, protocol);
    proven_http_header_t fields[] = { { PROVEN_LIT("Content-Type"), PROVEN_LIT("text/plain") } };
    if (proven_http_stream_respond(stream, 200, fields, 1, (proven_mem_view_t){ (const proven_byte_t *)text, (proven_size_t)n }) != PROVEN_OK) return;
    if (protocol == 2) app->over_http2++;
}

static void on_done(void *ctx, proven_http_stream_t *stream, proven_err_t why) {
    (void)stream;
    if (why == PROVEN_OK) ((ex_app_t *)ctx)->served++;
}

static void run(void *arg) { (void)proven_loop_run(((ex_app_t *)arg)->loop); }

/* 작은 HTTP/2 클라이언트: 엔진, 소켓, 그리고 요청한 스트림이 모두 끝날 때까지 둘 사이로
 * 바이트를 옮기는 루프. 200으로 답을 받은 수를 돌려준다. */
static int ask_three(proven_u16 port, char answers[3][64]) {
    proven_net_conn_t sock;
    if (proven_net_connect(proven_net_addr_loopback(PROVEN_NET_FAMILY_IPV4, port), proven_net_deadline_in(5000), &sock) != PROVEN_OK) return -1;

    /* 엔진은 스트림이 열려 있는 동안 자기가 할당한 메모리에 헤더 목록을 읽는다 - 또는 여러분의
     * 메모리에. 한 스레드의 여러 연결이 그것을 함께 쓸 수 있다. */
    static proven_u64 header_room[16384];
    proven_h2_config_t config = { .alloc = proven_heap_allocator(), .header_buffer = { (proven_byte_t *)header_room, sizeof header_room } };
    proven_h2_conn_t *conn = NULL;
    if (proven_h2_header_buffer_size(0) > sizeof header_room || proven_h2_conn_create(&config, &conn) != PROVEN_OK) { (void)proven_net_close(&sock); return -1; }

    /* 한 연결에서 요청 셋을 한꺼번에: 스트림 1, 3, 5. */
    static const char *const paths[3] = { "/first", "/second", "/third" };
    for (int i = 0; i < 3; i++) {
        proven_http_header_t request[] = {
            { PROVEN_LIT(":method"), PROVEN_LIT("GET") }, { PROVEN_LIT(":scheme"), PROVEN_LIT("http") },
            { PROVEN_LIT(":authority"), PROVEN_LIT("localhost") }, { PROVEN_LIT(":path"), proven_u8str_view_from_cstr(paths[i]) },
        };
        proven_u32 stream = 0;
        if (proven_h2_conn_submit_request(conn, request, 4, true, &stream) != PROVEN_OK) { proven_h2_conn_destroy(conn); (void)proven_net_close(&sock); return -1; }
    }

    int ended = 0, ok = 0;
    static proven_byte_t in[16384];
    while (ended < 3) {
        /* 엔진이 쌓아 둔 것 - 서문과 설정, 요청, 나중에는 승인 - 이 먼저 소켓으로 간다. */
        proven_mem_view_t out = proven_h2_conn_pending_output(conn);
        if (out.size > 0) {
            if (proven_net_write_all(&sock, out, proven_net_deadline_in(5000)).err != PROVEN_OK) break;
            proven_h2_conn_output_sent(conn, out.size);
        }
        proven_result_size_t got = proven_net_read(&sock, (proven_mem_mut_t){ in, sizeof in }, proven_net_deadline_in(5000));
        if (got.err != PROVEN_OK) break;
        proven_size_t pos = 0;
        for (;;) {
            proven_size_t used = 0;
            proven_h2_event_t ev;
            if (proven_h2_conn_feed(conn, (proven_mem_view_t){ in + pos, got.value - pos }, &used, &ev) != PROVEN_OK) { ended = 3; break; }
            pos += used;
            const proven_u32 k = ev.stream_id ? (ev.stream_id - 1) / 2 : 0;     /* 스트림 1, 3, 5 -> 0, 1, 2 */
            if (ev.kind == PROVEN_H2_EVENT_HEADERS && ev.status == 200 && k < 3) ok++;
            if (ev.kind == PROVEN_H2_EVENT_DATA && k < 3) {
                snprintf(answers[k], 64, "%.*s", (int)(ev.data.size < 63 ? ev.data.size : 63), (const char *)ev.data.ptr);
                proven_h2_conn_consumed(conn, ev.stream_id, ev.data.size);
            }
            if ((ev.kind == PROVEN_H2_EVENT_DATA || ev.kind == PROVEN_H2_EVENT_HEADERS) && ev.end_stream) ended++;
            if (ev.kind == PROVEN_H2_EVENT_STREAM_RESET || ev.kind == PROVEN_H2_EVENT_CLOSED) { ended = 3; break; }
            if (ev.kind == PROVEN_H2_EVENT_NONE && pos == got.value) break;
        }
    }
    proven_h2_conn_destroy(conn);
    (void)proven_net_close(&sock);
    return ok;
}

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    ex_app_t app = { 0 };
    EXAMPLE_REQUIRE(proven_loop_create(heap, &app.loop) == PROVEN_OK, "a loop");

    /* `http2`가 전부다. 평문에서는 HTTP/2 서문으로 시작하는 클라이언트가 HTTP/2이고 나머지는
     * 모두 HTTP/1.1이다. TLS에서는 핸드셰이크가 정하며(ALPN), 그때는 TLS 설정이 "h2"를
     * 내놓아야 한다. */
    proven_http_event_server_config_t config = { .on = { .on_request = on_request, .on_done = on_done }, .ctx = &app, .http2 = true };
    proven_http_event_server_t *server = NULL;
    proven_net_addr_t at;
    EXAMPLE_REQUIRE(proven_http_event_server_create(app.loop, &config, &server) == PROVEN_OK &&
                    proven_http_event_server_listen(server, proven_net_addr_loopback(PROVEN_NET_FAMILY_IPV4, 0), &at) == PROVEN_OK, "a server that speaks both");
    /* 바쁜 서버는 연결마다 동시에 받는 요청 수를 줄였다가, 나중에 설정값(여기서는 기본값 100)까지
     * 다시 올릴 수 있다. 루프의 스레드에서, 또는 여기처럼 루프가 돌기 전에 부른다. */
    EXAMPLE_REQUIRE(proven_http_event_server_set_max_streams(server, 8) == PROVEN_OK && proven_http_event_server_set_max_streams(server, 0) == PROVEN_ERR_INVALID_ARG,
                    "eight requests at once from now on, and never none");
    /* 핸들러보다 앞서 클라이언트를 위해 쥐는 요청 본문도 줄일 수 있다: 지금부터 스트림당, 연결당
     * 최대 64 KiB - 주는 것의 천장이고, 이미 준 것을 거두지는 않는다. */
    EXAMPLE_REQUIRE(proven_http_event_server_set_window(server, 64 * 1024) == PROVEN_OK, "64 KiB of body at most ahead of the handler");
    proven_job_sys_t *threads = NULL;
    proven_job_group_t running;
    proven_job_group_init(&running);
    EXAMPLE_REQUIRE(proven_job_system_init(heap, 1, 4, &threads) == PROVEN_OK &&
                    proven_job_group_submit(threads, &running, run, &app) == PROVEN_OK, "the loop runs on another thread");

    // ---- HTTP/1.1 클라이언트 ------------------------------------------------------------------
    char url[64];
    snprintf(url, sizeof url, "http://127.0.0.1:%u/hello", (unsigned)at.port);
    proven_http_client_config_t client_config = { .alloc = heap, .max_idle_connections = 1 };
    proven_http_client_t *client = NULL;
    proven_http_client_response_t resp;
    proven_u8str_t body = { 0 };
    EXAMPLE_REQUIRE(proven_http_client_create(&client_config, &client) == PROVEN_OK &&
                    proven_http_client_get(client, proven_u8str_view_from_cstr(url), &resp) == PROVEN_OK && resp.status == 200 &&
                    proven_http_client_read_all(&resp, heap, &body, 4096) == PROVEN_OK, "the blocking client of chapter 11 is answered");
    printf("HTTP/1.1 client: %.*s", (int)proven_u8str_as_view(&body).size, (const char *)proven_u8str_as_view(&body).ptr);
    EXAMPLE_REQUIRE(proven_u8str_view_eq(proven_u8str_as_view(&body), PROVEN_LIT("/hello over HTTP/1\n")), "over HTTP/1.1");
    proven_u8str_destroy(heap, &body);
    proven_http_client_finish(&resp);
    proven_http_client_destroy(client);

    // ---- 같은 포트의 HTTP/2 클라이언트 ---------------------------------------------------------
    char answers[3][64] = { "", "", "" };
    EXAMPLE_REQUIRE(ask_three(at.port, answers) == 3, "three requests on one HTTP/2 connection are each answered");
    for (int i = 0; i < 3; i++) printf("HTTP/2 client:   %s", answers[i]);
    EXAMPLE_REQUIRE(strcmp(answers[0], "/first over HTTP/2\n") == 0 && strcmp(answers[1], "/second over HTTP/2\n") == 0 && strcmp(answers[2], "/third over HTTP/2\n") == 0,
                    "by the same handler, which was told the protocol was 2");

    // ---- 끝 ------------------------------------------------------------------------------------
    /* 루프를 멈춘 다음 처리기가 센 것을 보고 서버를 해체한다: 그때는 다른 무엇도 둘을 건드리지
     * 않는다. */
    proven_loop_stop(app.loop);
    proven_job_group_wait(threads, &running);
    EXAMPLE_REQUIRE(app.served == 4 && app.over_http2 == 3, "four exchanges ended with on_done(PROVEN_OK), three of them over HTTP/2");
    proven_http_event_server_destroy(server);
    proven_loop_destroy(app.loop);
    proven_job_system_close(threads);
    proven_job_system_destroy(threads);
    return EXAMPLE_OK();
}

    주의사항, 그리고 무엇이 잘못되는가#

    • on_writable을 넘어 자기 위치를 기억하는 처리기는 전과 같이 안전하다. on_writable은 처리기가 직접 한 호출 안에서는 결코 불리지 않는다 - 같은 처리기로 되돌아 들어오는 쓰기는 같은 바이트를 두 번 보내게 된다. 이것은 두 프로토콜 모두에 대한 서버의 약속이며, HTTP/2에서는 결함 하나를 겪고서야 찾았다 (8절).
    • 읽지 않는 클라이언트에게서는 읽지 않는다. 응답의 헤드는 언제나 큐에 넣는다 - 서버에는 그것을 달리 둘 곳이 없다. 그래서 묻기만 하고 읽지 않는 클라이언트를 제한하는 것은 이것이다: max_buffered_output의 두 배가 그 클라이언트를 기다리는 동안 서버는 그 연결에서 더 받지 않는다. 뒤따르는 요청은 소켓에 남는다. HTTP/1.1에서 응답이 밀려 있는 동안 파이프라인된 요청이 남는 것과 같다. 그때 연결이 출력으로 쥐는 최대는 max_buffered_output의 두 배와, 열려 있던 스트림마다 헤드 하나다 - 많아야 max_concurrent_streams개이고, 각각 처리기가 만든 크기다. 따라서 다른 응답을 읽지 않으면서 업로드하는 클라이언트는 읽히지 않게 되고, 읽으면 다시 읽힌다.
    • max_buffered_output은 스트림이 아니라 연결마다다. 스트림 백 개를 가진 느린 클라이언트 하나는 HTTP/1.1 클라이언트 하나만큼을 쥐게 하지, 그 백 배가 아니다.
    • 한가한 HTTP/2 연결은 HTTP/1.1 연결보다 크다. 받은 것만큼. HTTP/1.1은 480바이트다. HTTP/2는 작은 요청 하나 뒤에 2,360바이트이고, 클라이언트가 기억하게 한 헤더 필드만큼 자라 두 압축 테이블이 가득 차면 약 12.8 KiB가 된다: 한가한 연결 만 개는 22에서 128 MiB 사이다. http2_header_table_bytes는 그 상한을 낮추고 http2_no_header_table은 없앤다(언제나 2 KiB 미만). 대가는 모든 필드를 매번 온전히 보내는 것이다. 헤더 목록을 읽는 버퍼 - 80 KiB - 는 연결마다가 아니라 서버 전체에 하나다. 진행 중인 요청 하나는 약 210바이트를 더한다: 서버에 160, 연결에 48.
    • 요청이 끝나기 전에 답한 처리기는 그 요청과 끝난 것이다. 서버는 클라이언트에게 그만 보내라고 말하고(5절), 이미 오던 것은 읽지 않고 버린다 - 오류였을 프레임까지도. 본문이 중요하다면 본문이 도착한 뒤에 답한다.
    • WebSocket에는 HTTP/1.1이 필요하다. HTTP/2 스트림에서의 업그레이드는 거부된다 (PROVEN_ERR_UNSUPPORTED): WebSocket을 원하는 브라우저는 그것을 위해 HTTP/1.1 연결을 열고, 같은 포트가 그것을 받는다.
    • 트레일러는 전달되지 않는다. 어느 방향이든, HTTP/1.1에서도 그렇듯이: 요청의 트레일러는 본문을 끝내고 버려진다.

    7. 이벤트 구동 클라이언트의 HTTP/2#

    typedef struct {
    /* ... 15장이 설명하는 모든 것 ... */
    bool http2;
    bool http2_cleartext;
    proven_u32 idle_timeout_ms;
    proven_size_t max_waiting_requests;
} proven_http_event_client_config_t;

int proven_http_event_request_protocol(const proven_http_event_request_t *request);

    15장의 이벤트 구동 클라이언트는 HTTP/1.1에서 요청 하나에 연결 하나다. http2를 켜면 HTTP/2에 합의한 오리진마다 연결 하나를 간직하고, 그 오리진으로 가는 모든 요청을 거기에 올린다: 한 서버로 가는 요청 백 개가 핸드셰이크 백 번이 아니라 한 번이다. 콜백과 proven_http_event_request_* 호출은 같다. start가 약속하는 것도 같다 - 옵션이 가리키는 것은 모두 반환 전에 복사되거나 쓰이고, on_done은 정확히 한 번, start 안에서는 결코 오지 않는다.

    • TLS에서는 http2와, h2를 (그리고 그 뒤에 http/1.1을) 내놓는 TLS 설정: 오리진마다 핸드셰이크가 정한다. HTTP/1.1을 고른 오리진은 그렇게 기억되고, 전처럼 요청 하나에 연결 하나로 서비스된다. (그런 오리진은 마지막 64개까지, 하나에 약 600바이트로 기억한다. 잊힌 오리진은 핸드셰이크 한 번을 들여 다시 알아낸다.) TLS 설정에 early_data가 있고 세션이 h2로 만들어졌으면, 새 연결은 첫 비행 안에서 HTTP/2를 시작한다: 서문, 설정, 그리고 본문 없는 GET, HEAD, OPTIONS 요청 하나가 조기 데이터로 가고(14장 6절, v0.84.0) 나머지는 핸드셰이크 뒤에 간다. 서버가 거절한 것은 그대로 다시 가고, 425를 받으면 이제 열린 같은 연결에서 요청을 한 번 더 보낸다.
    • 평문에서는 http2_cleartext: 그 클라이언트의 모든 http 요청이 사전 지식 방식의 HTTP/2다. 평문에서는 서버에 물어볼 방법이 없으니, 아는 서버에 대해서만 이렇게 말한다. 평문으로 두 종류와 모두 말하는 클라이언트는 클라이언트 둘이다. HTTP/2를 말하지 않는 서버에 대해 이렇게 말하면 모든 요청이 PROVEN_ERR_UNSUPPORTED로 끝난다: 연결은 맺어졌고, 서버의 설정이 오기 전에 - HTTP/2가 아닌 바이트를 받고, 또는 아무것도 받지 못하고 - 끝났다. 평문에서는 서버의 설정이 그 서버가 HTTP/2 서버라는 첫 신호다. 설정보다 앞서 보내는 것은 없으므로 그런 요청은 처리된 적이 없다. 그러나 다시 시작해도 똑같이 끝날 것이고, 그래서 답이 PROVEN_ERR_AGAIN이 아니다. (v0.35.0 전에는 그랬다.) 마침 그 순간 재시작 중이던 서버도 같은 답을 받는다: 그 서버가 HTTP/2를 말한다는 것을 안다면 요청을 다시 시작하라.

    HTTP/1.1 요청은 결코 그러지 않았지만 요청은 기다릴 수 있다: 연결이 만들어지는 동안 그 연결을, 스트림을 몇 개 허락하는지 말해 주는 서버의 첫 마디를 - 그보다 앞서 보내는 것이 없으므로 그 때문에 거절되는 것도 없다 - 그리고 서버의 한도에 닿았을 때 빈 스트림을. 기다리는 요청은 시작할 때 받은 것의 사본을 쥔다. 연결 하나에 많아야 max_waiting_requests(1,000)개가 기다리고, 그다음 start는 PROVEN_ERR_BUSY다. 그리고 max_connections를 설정했고 모든 연결이 쓰이는 중이면, 연결이 없는 origin으로 가는 요청은 클라이언트에 연결 하나를 더 둘 자리가 날 때까지 기다린다 - 어느 연결 위도 아닌 곳에서, 많아야 그만큼 더, 길어야 connect_timeout_ms(15장).

    on_done이 말하는 것은 전과 같되 답이 둘 늘었다. PROVEN_ERR_AGAIN은 HTTP/2 서버가 처리하지 않은 요청이다 - 서버가 먼저 작별했거나, 스트림을 거절했거나, 요청을 보내기 전에 연결을 잃었다. 그런 요청은 메서드가 무엇이든 다시 시작해도 된다. 클라이언트가 알아서 그러지는 않는다 - retry_unsent로 몇 번까지 그래도 되는지 정해 주지 않는 한(아래). PROVEN_ERR_UNSUPPORTED는 평문에서 HTTP/2를 말하지 않는 것으로 드러난 서버로 간 요청이다(위의 http2_cleartext): 역시 처리되지 않았고, 다시 시작할 가치가 없다. PROVEN_ERR_RESET은 여전히 "처리되었을 수도 있다"는 뜻이다 - 다만 응답이 선언한 content-length의 바이트가 모두 도착한 뒤 스트림을 NO_ERROR로 리셋한 서버는 끝까지 답한 것이고, 그것은 본문 전체와 함께 PROVEN_OK다(어떤 리셋이 그런지는 5절이 말한다). TLS 위에서는 PROVEN_ERR_UNSUPPORTED가 없다: 핸드셰이크가 프로토콜을 정하고, HTTP/1.1에 동의한 서버와는 HTTP/1.1로 말한다.

    설정HTTP/2에서
    connect_timeout_ms오리진의 연결 만들기 - 핸드셰이크, 그리고 그것을 HTTP/2 연결로 만드는 서버의 SETTINGS까지 - 그것을 기다리던 요청은 모두 그와 함께 끝난다(PROVEN_ERR_TIMEOUT)
    response_timeout_ms, body_timeout_ms요청 각각의 것: 답을 받지 못한 요청은 끝나고, 연결과 다른 요청은 계속된다
    write_timeout_ms연결의 것: 서버가 출력을 하나도 받지 않으면 연결이 끝난다
    idle_timeout_ms (0: 60초)요청이 없는 연결을 다음 요청을 위해 이만큼 간직했다가 닫는다
    max_buffered_output그 연결의 요청들을 합쳐서
    decompress그대로다. 정지된 요청은 도착한 것을 압축된 채로 쥐었다가 재개할 때 푼다
    decompress_zstdzstd에 대해 같다: accept-encoding으로 요청하고, 스트림에서 푼다
    decompress_brotlibr에 대해 같다

    예제: 요청 셋, 연결 하나#

    #include <stdio.h>
#include <string.h>

/*
 * HTTP/2로 말하는 이벤트 구동 클라이언트: 요청 셋, 연결 하나.
 *
 * 여기서는 클라이언트와 서버가 한 루프 위에 있고 손으로 돌리므로 스레드가 필요 없다.
 * 클라이언트의 콜백은 HTTP/1.1 프로그램의 것과 같다. 다른 것은 그 아래다 - 클라이언트가
 * 오리진마다 연결 하나를 간직하고, 그 오리진으로 가는 모든 요청을 그 연결에 올린다.
 */

typedef struct { int answered, over_http2; char text[3][32]; bool done[3]; } ex_seen_t;
typedef struct { ex_seen_t *seen; int which; } ex_call_t;

static void serve(void *ctx, proven_http_stream_t *stream, const proven_http_request_t *head) {
    (void)ctx;
    (void)proven_http_stream_respond(stream, 200, NULL, 0, (proven_mem_view_t){ head->target.ptr, head->target.size });     /* 자기 경로를 그대로 돌려준다 */
}

static void on_response(void *ctx, proven_http_event_request_t *request, const proven_http_response_t *head) {
    ex_call_t *call = ctx;
    /* 여기서는 2다. 아직 연결을 기다리는 요청이나, 서버가 HTTP/1.1만 말하는 것으로 드러난
     * 요청은 1이다. */
    if (head->status == 200 && proven_http_event_request_protocol(request) == 2) call->seen->over_http2++;
}

static void on_body(void *ctx, proven_http_event_request_t *request, proven_mem_view_t piece, bool last) {
    (void)request; (void)last;
    ex_call_t *call = ctx;
    snprintf(call->seen->text[call->which], sizeof call->seen->text[0], "%.*s", (int)piece.size, (const char *)piece.ptr);
}

static void on_done(void *ctx, proven_http_event_request_t *request, proven_err_t why) {
    (void)request;
    ex_call_t *call = ctx;
    call->seen->done[call->which] = true;
    if (why == PROVEN_OK) call->seen->answered++;
}

int main(void) {
    proven_allocator_t heap = proven_heap_allocator();
    proven_loop_t *loop = NULL;
    EXAMPLE_REQUIRE(proven_loop_create(heap, &loop) == PROVEN_OK, "a loop");

    /* 두 프로토콜을 모두 말하는 서버(6절). */
    proven_http_event_server_config_t server_config = { .on = { .on_request = serve }, .http2 = true };
    proven_http_event_server_t *server = NULL;
    proven_net_addr_t at;
    EXAMPLE_REQUIRE(proven_http_event_server_create(loop, &server_config, &server) == PROVEN_OK &&
                    proven_http_event_server_listen(server, proven_net_addr_loopback(PROVEN_NET_FAMILY_IPV4, 0), &at) == PROVEN_OK, "a server");

    /* 평문에는 물어볼 핸드셰이크가 없으므로 클라이언트에게 알려 준다: 이 클라이언트의 모든
     * `http` 요청은 HTTP/2다. TLS에서는 대신 `http2`이고, "h2"를 내놓는 TLS 설정과 함께 쓰며,
     * 오리진마다 핸드셰이크가 정한다. */
    proven_http_event_client_config_t client_config = { .alloc = heap, .http2_cleartext = true };
    proven_http_event_client_t *client = NULL;
    EXAMPLE_REQUIRE(proven_http_event_client_create(loop, &client_config, &client) == PROVEN_OK, "a client");

    ex_seen_t seen = { 0 };
    ex_call_t calls[3] = { { &seen, 0 }, { &seen, 1 }, { &seen, 2 } };
    static const char *const paths[3] = { "/first", "/second", "/third" };
    for (int i = 0; i < 3; i++) {
        char url[64];
        snprintf(url, sizeof url, "http://127.0.0.1:%u%s", (unsigned)at.port, paths[i]);
        proven_http_event_request_options_t request = {
            .url = proven_u8str_view_from_cstr(url),
            .on = { .on_response = on_response, .on_body = on_body, .on_done = on_done }, .ctx = &calls[i],
        };
        /* 연결이 생기기 전에 한꺼번에 시작한다: 첫 요청이 연결을 만들고 나머지는 그것을
         * 기다리며, 서버가 무엇을 허락하는지 말한 뒤 셋이 함께 나간다. */
        EXAMPLE_REQUIRE(proven_http_event_client_start(client, &request, NULL) == PROVEN_OK, "a request is started");
    }
    EXAMPLE_REQUIRE(proven_http_event_client_requests(client) == 3, "three are under way");

    proven_net_deadline_t until = proven_net_deadline_in(5000);
    while (!(seen.done[0] && seen.done[1] && seen.done[2]) && proven_time_monotonic_now() < until)
        EXAMPLE_REQUIRE(proven_loop_poll(loop, proven_net_deadline_in(10)) == PROVEN_OK, "a round of the loop");

    for (int i = 0; i < 3; i++) printf("%s\n", seen.text[i]);
    EXAMPLE_REQUIRE(seen.answered == 3 && seen.over_http2 == 3, "all three were answered, over HTTP/2");
    EXAMPLE_REQUIRE(strcmp(seen.text[0], "/first") == 0 && strcmp(seen.text[1], "/second") == 0 && strcmp(seen.text[2], "/third") == 0, "each with its own answer");
    EXAMPLE_REQUIRE(proven_http_event_server_connections(server) == 1, "and the server saw one connection, not three");

    proven_http_event_client_destroy(client);
    proven_http_event_server_destroy(server);
    proven_loop_destroy(loop);
    return EXAMPLE_OK();
}

    주의사항, 그리고 무엇이 잘못되는가#

    • 요청의 객체는 여러분 손에서 바뀌지 않는다. 오리진을 모르는 동안 시작되었고 그 오리진이 HTTP/1.1로 말하는 것으로 드러난 요청도 여전히 start가 준 그 포인터다. 그때 proven_http_event_request_protocol은 1을 답한다.
    • 기다리는 요청은 보내지기 전에 타임아웃될 수 있다: connect_timeout_ms가 그것이 기다리는 연결을 덮는다. 빈 스트림을 기다리는 요청에게는 자기 시계가 없다 - 재어지는 것은 그 앞의 요청들이다.
    • 정지는 많아야 윈도 하나를 쥔다. 서버에서와 같다: 클라이언트가 서버에게 소비했다는 말을 멈추고, 서버는 보내기를 멈춘다.

    • PROVEN_ERR_AGAIN은 요청하지 않는 한 대신 재시도해 주지 않는다. retry_unsent는 횟수다: 그렇게 끝났을 요청 - 작별 뒤에 남은 것, 스트림이 거절된 것, 잃어버린 연결에서 기다리던 것 - 을 클라이언트가 스스로 서버에 몇 번까지 다시 보낼지를 정한다. 스트림 하나만 거절되고 연결이 계속되면 같은 연결로, 그렇지 않으면 같은 오리진의 다른 연결로 가며, 없으면 새로 만든다. 함께 옮겨지는 요청들은 순서를 유지한다. 실패한 시도에 대해서는 아무것도 알려 주지 않고, on_done은 마지막 시도의 결과로 한 번 온다. 기본값 0은 재시도하지 않는다는 뜻이다: 호출자가 정한다. 이 설정이 다루지 않는 것과 그 비용:

      • 본문을 조각으로 쓰는 요청은 아니다 - 클라이언트가 다시 보낼 조각을 갖고 있지 않다 - 그리고 on_response 뒤에도 아니다: 답이 시작되는 것을 이미 보았다.
      • PROVEN_ERR_UNSUPPORTED는 아니다. 다시 해도 똑같이 끝난다. PROVEN_ERR_RESET도 아니다. 서버가 처리했을 수 있다. 시간 제한도 아니다.
      • 지연 없이 곧바로 한다. 바빠서 스트림을 거절한 서버에게 같은 순간에 다시 묻는다. 작은 횟수는 몇 순간일 뿐이다. 시도 사이에 기다리고 싶은 프로그램은 설정을 0으로 두고 직접 다시 시작한다.
      • 시간 제한은 시도마다 따로다: 요청 하나가 시도 횟수만큼 connect_timeout_ms나 response_timeout_ms를 쓸 수 있다.
      • 메모리에 든 본문은 응답이 시작될 때까지 메모리에 남는다. 다 보낼 때까지만이 아니다.
      • 다른 이유로 실패한 시도는 그 이유로 요청을 끝낸다. 새 연결을 만들 수 없으면 on_done은 PROVEN_ERR_AGAIN이 아니라 PROVEN_ERR_REFUSED를 말한다.
    • 연결 하나는 실패 지점 하나다. 그것이 끝나면 그 위의 모든 요청이 함께 끝난다 - 아직 보내지 않은 것은 PROVEN_ERR_AGAIN, 나머지는 PROVEN_ERR_RESET(평문에서 한 번도 HTTP/2가 아니었던 연결이면 모두 PROVEN_ERR_UNSUPPORTED).

    8. 무엇을 받아들이고, 무엇이 없으며, 어떻게 시험했는가#

    디코더가 받아들이는 것은 RFC 7541이 정의한 HPACK이다. 블록 맨 앞의 테이블 크기 갱신은 몇 개든 (RFC는 많아야 둘이라고 약속한다), 정수는 연속 바이트 다섯 개까지, 리터럴의 허프만 패딩은 1 비트 일곱 개까지이고 그 밖의 것은 안 된다.

    인코더가 쓰는 것은 흔한 선택을 하는 유효한 HPACK이다: 테이블에 있으면 참조로, 허프만 코딩은 더 짧을 때만(길이가 같으면 하지 않는다), 새 필드는 비밀이거나 테이블보다 크지 않으면 테이블에 넣는다.

    연결이 받아들이는 것은 RFC 9113이다. RFC가 선택을 남겨 둔 곳에서는 이렇게 한다: 폐기된 우선순위 필드는 무시하되, 자기 자신에게 의존한다는 스트림은 RFC 7540이 그랬듯 그 스트림의 오류다. 이쪽이 리셋한 스트림으로 온 프레임은, 그 리셋이 기억하고 있는 마지막 max_concurrent_streams개의 종료 안에 있는 동안 말없이 버린다. 한도를 넘는 헤더 목록은 연결이 아니라 그 스트림의 오류다. 본문과 맞지 않는 content-length는 스트림의 오류다. HEAD에 대한 응답과 상태 204, 304인 응답은 싣지 않은 길이를 알릴 수 있다.

    여기에 없는 것:

    • 11장 블로킹 서버와 블로킹 클라이언트의 HTTP/2: 연결 하나에 스레드 하나는 한 번에 한 교환에 어울리고, 그것이 HTTP/1.1이다.
    • 지연을 둔 재시도, 그리고 서버가 처리하지 않은 것 말고 다른 것의 재시도: 이벤트 구동 클라이언트는 그런 요청을 알리고(PROVEN_ERR_AGAIN), retry_unsent가 정해져 있으면 그 횟수만큼 곧바로 다시 보낸다. 시도 사이에 기다리는 것과, 처리되었을 수도 있는 것을 다시 시도하는 것은 호출자의 몫이다.
    • 이벤트 구동 서버의 트레일러, 어느 프로토콜이든.
    • 확장 CONNECT(RFC 8441, HTTP/2 위의 WebSocket)와 거기에 필요한 SETTINGS.
    • 서버 푸시: PUSH_PROMISE는 거절할 수 있도록 알아보기만 한다.
    • 우선순위(RFC 9113이 폐기한 RFC 7540의 방식): 건너뛴다.
    • RFC 9113이 없앤 Upgrade: h2c. (HTTP/3은 9절과 10절.)
    • 디코딩된 필드의 never-indexed 표시: 프록시라면 그것을 전달하겠지만, 여기에는 그럴 것이 없다.

    어떻게 시험했는가. 정적 테이블과 허프만 코드는 손으로 입력한 것이 아니다: 비공개 프로그램이 RFC 7541의 공개된 본문에서 읽어 오며, 항목이 61개이고 코드 257개가 서로 접두사가 아니며 코드 공간을 정확히 채우지 않으면 멈춘다. 등록된 시험은 링크된 테이블에 대해 같은 것을 검사한다. 그 시험은 이어서 RFC 부록 C의 예제 열여섯 개를 모두 디코더에 통과시키며 단계마다 동적 테이블을 RFC의 것과 비교하고, 인코더가 같은 선택을 하는 예제를 바이트 단위로 재현하게 하고, 잘못된 블록 열세 종류를 거부하고, 각 한도를 지키고, RFC 블록의 모든 앞부분과 모든 한 비트 변경을 디코딩한다. 두 번째 시험은 프레임 종류마다의 규칙을 경계의 양쪽에서, 그리고 잘못된 요청 서른한 개를 시험한다. 등록된 시험 밖에서는: 이 디코더가 다른 구현 열네 개가 같은 헤더 목록에 대해 만든 블록 47,142개를 읽었고(nghttp2, Go, Node, Python, Haskell, Swift 인코더. 테이블 크기가 바뀌는 순서 포함), Node의 HTTP/2 서버 - nghttp2다 - 가 이 인코더가 공유 연결 위의 요청 1,290개에 대해 쓴 블록을 모두 디코딩했으며, 손상된 블록 오백만 개를 버퍼 밖의 읽기나 쓰기를 보고하는 도구 아래에서 디코딩했고 보고된 것은 없었다.

    연결에는 따로 등록된 시험이 있다. 연결 둘을 메모리에서 맞물려 아홉 가지 크기의 본문을 세 가지 윈도 크기로, 한 바이트씩 그리고 한꺼번에 실어 나르고, 스트림 쉰 개를 동시에 나르고, 프레임 셋으로 나가는 40,000바이트짜리 머리를 나른다. 대본 백한 개가 저마다 RFC 9113의 규칙 하나를 어기거나 바로 그 안쪽에 서고, 연결은 RFC가 정한 판정 - 무시, 코드가 붙은 스트림의 오류, 코드가 붙은 연결의 오류 - 을 지켜야 한다. 한 번은 바이트를 한 덩어리로, 한 번은 한 바이트씩 준다. 5절의 한계는 저마다 양쪽에서 그 경계까지 몬다. 녹음한 대화를 각 역할의 새 연결에 12,214번 다시 들려준다 - 앞쪽에서는 모든 지점에서, 그 뒤로는 간격을 두고 끊거나, 한 비트를 바꿔서. 그리고 대화의 모든 할당을 한 번씩 실패시킨다. 등록된 시험 밖에서는, 소켓을 연결에 통과시키는 비공개 프로그램을 통해: Node의 HTTP/2 클라이언트와 서버(nghttp2), 그리고 curl이 양쪽 역할로 요청, 5 MB까지의 본문, 20,000바이트짜리 머리, 트레일러, 중간 응답, 취소, 설정 변경을 열두 가지 설정 조합 아래에서 주고받았다 - 검사 7,896개, 실패 없음. 그리고 무작위로 행동하는 애플리케이션과 함께 연결 140,108개에 걸친 무작위 프레임 5,000,230개가 같은 도구 아래에서 연결의 불변식을 하나도 깨지 못했다.

    6절의 서버에는 따로 등록된 시험이 있다: HTTP/1.1 서버의 처리기를 그대로 두고, 이 라이브러리의 연결로 만든 클라이언트가 실제 소켓으로 - 평문, TLS 1.3, TLS 1.2로 - 말을 건다. 양방향 본문, 동시 스트림 예순 개, 압축, 일시 정지, 양쪽의 리셋, 보내는 쪽을 닫고도 답을 받는 클라이언트, 한계, 타임아웃 각각, 작별, 그리고 내내 같은 포트의 HTTP/1.1 클라이언트. 등록된 시험 밖에서는, 비공개 프로그램이 한 포트에서 두 프로토콜을 Node의 http2, http, https 클라이언트와 다섯 가지 방식의 curl에게 서비스했다: 검사 7,392개, 마지막에는 실패 없음. 처음에는 하나가 실패했다: TLS 위에서 Node에게 나란히 보내던 큰 응답 둘이 멈췄다. 서버가 처리기 자신의 쓰기 안에서 on_writable을 불렀고, 다시 들어온 처리기가 자기 위치를 잃었기 때문이다. 이 라이브러리 자체의 클라이언트는 그것을 일으키지 못했었다. 이제 등록된 시험이 스트림 둘을 경쟁시키며 처리기가 "결코 재진입되지 않음"을 지키게 한다.

    HTTP/2 서버의 적합성 시험 모음인 h2spec(버전 2.6.0, 사례 146개)을 그 서버에 돌렸다: TLS에서 146개 가운데 146개, 평문에서 146개 가운데 145개. 그 하나는 "잘못된 연결 서문은 연결을 끝내야 한다"이다: 평문에서 서문이 아닌 바이트는 여기서 HTTP/2가 아니라 HTTP/1.1이고, 그렇게 답한다. 첫 실행은 두 가지를 찾았다: 길이를 알리지 않은 본문이 온다는 것을 처리기가 알 길이 없었고(이제 Transfer-Encoding: chunked를 본다), 자기 자신에게 의존하는 스트림을 거부하지 않았다.

    7절의 클라이언트에는 6절의 서버를 한 루프에서 상대하는 등록된 시험이 있다 - 평문과 TLS로: 한 연결의 요청 마흔 개, 양방향 본문, 압축, 일시 정지, 중단, 서버의 스트림 한도, 타임아웃 각각, 놓아 주는 한가한 연결, 그리고 HTTP/1.1만 말하는 것으로 드러나는 오리진 - 기다리던 요청들은 호출자가 이미 쥐고 있던 객체 그대로 HTTP/1.1로 서비스된다. 등록된 시험 밖에서는, 비공개 프로그램이 그 클라이언트를 TLS와 평문의 Node HTTP/2 서버에 서버 설정 네 벌로, 그리고 HTTP/2가 없는 HTTPS 서버에 돌렸다: 검사 1,156개, 마지막에는 실패 없음. 처음에는 열다섯이 실패했다: 스트림 넷을 허락하는 서버를 상대로, 새 연결에 몰아 보낸 요청들이 서버가 그렇게 말하기 전에 나갔고, 넘친 것이 거절되어 돌아왔다. 이제 클라이언트는 서버의 설정보다 앞서 아무것도 보내지 않는다.

    등록된 시험이 찾지 못한 것, 한 번 더. 서버가 한 번의 읽기를 처리하는 동안 출력을 붙들어 두게 처음 만들었을 때(아래 표가 그것으로 얻은 것이다), 본문을 통째로 주는 응답이 몰리자 연결의 출력이 가득 찼고 그 뒤에 시작한 응답들은 자리가 없어 리셋되었다. 등록된 시험은 모두 통과했다. 비공개 검증의 Node 클라이언트는 7,392개 가운데 945개가 실패했다. 이제 붙들어 두기는 max_buffered_output의 4분의 1이 쌓이면 끝나고, 통째로 준 본문은 머리가 쓸 자리를 남기며, 등록된 시험 하나가 한 번의 쓰기로 요청 백 개를 그 머리들보다 한도가 작은 서버에 보낸다. 그 뒤 비공개 검증을 전부 다시 돌렸다 - Node와 curl을 상대로 7,896개, 7,392개, 1,156개, h2spec은 전과 같이 - 실패는 없었다.

    속도, 소켓 없이 한 번 잰 것: 3.5 GHz x86-64 프로세서의 코어 하나에서 메모리 안의 연결 둘, GCC -O2. 필드 열두 개짜리 요청 머리(리터럴로 299바이트)를 초당 680,000번, 204 MB/s로 허프만 디코딩한다. 초당 385,000개의 요청이 보내지고, 디코딩되고, 머리로 답을 받고, 다시 읽힌다(백 개가 동시에). 본문은 2.4 GB/s로 건넌다. 이것은 프로토콜만의 비용이다 - 소켓, TLS, 처리기는 모두 더 든다.

    소켓 위의 속도, 한 번 잰 것: 15장 14절의 부하를 같은 기계의 같은 서버에 HTTP/2로 다시 걸었다 - 테스트 스위트에 속하지 않는 부하 프로그램, 루프백 인터페이스 위의 두 프로세스인 클라이언트와 서버, 평문, 루프 하나, 2바이트를 답하는 처리기, 행마다 10초. 모든 연결은 요청 하나를 하고 열린 채 남는다. 그 뒤 그 가운데 일부가 요청 몇 개씩을 동시에 띄워 둔다. HTTP/1.1 행은 비교를 위해 같은 날 같은 서버 프로세스를 상대로 쟀다.

    표가 말하는 것. 한 번에 요청 하나씩이면 HTTP/2가 8분의 1쯤 느리다: 요청마다 여전히 읽기 한 번과 쓰기 한 번이고, 그 사이에 할 일이 더 많다. 요청이 함께 떠 있으면 몇 배 빠르다. 서버가 한 번의 읽기가 가져온 것을 모두 처리한 뒤에 쓰기 때문이다: 함께 도착한 요청 백 개는 한 번의 쓰기로 답을 받고, 서버의 10초 가운데 시스템의 몫이 7.3초에서 0.8초로 떨어진다. 왕복 시간은 동시에 뜬 수와 함께 늘어난다. 그럴 수밖에 없다: 요청 백 개가 루프 하나에서 차례를 기다린다. 어느 행에서도 연결이나 요청을 잃지 않았다. 서버에서, 요청 하나를 마친 한가한 HTTP/2 연결은 2,272바이트를 쥐었고 (http2_no_header_table이면 1,920), HTTP/1.1은 448바이트였다. 헤더 목록을 읽는 버퍼 82 KiB는 서버 전체에 하나다.

    같은 서버를 상대한 라이브러리 자신의 클라이언트(7절): 연결 하나에 백 개를 띄워 세 번 재어 초당 471,000~486,000개 - 거기서는 두 프로세스가 번갈아 일하는데 클라이언트 차례가 더 길고, 서버는 10초 가운데 4초쯤 바빴다 - 그리고 하나씩이면 초당 42,000개, 중앙값으로 하나에 21마이크로초. (백 개를 띄운 수치는 403,000이었다. 연결이 스트림을 테이블을 훑어 찾지 않고 번호로 찾게 되고, 클라이언트가 요청의 URL을 두 번이 아니라 한 번 읽게 되기 전의 값이다.) 같은 클라이언트의 HTTP/1.1은 요청마다 연결을 만들던 때 초당 22,500개였다. v0.36.0부터는 연결을 보관하고(15장 12절), 여섯 연결 위에 백 개를 띄워 초당 129,000개, 한 연결에서 하나씩이면 초당 44,000개다. 루프백은 네트워크가 아니며, 실제 일을 하는 처리기는 "ok"를 답하는 처리기보다 느리다.

    하지 않은 것: 커버리지 기반 퍼징 없음. 실제 네트워크 위, TLS, 부하 아래의 큰 본문에 대한 측정 없음. 브라우저가 이 서버와 말해 본 적 없음. 외부 검토 없음. 연결은 스트림을 번호에서 자리로 가는 지도로 한 걸음에 찾는다. 지도는 스트림 테이블의 자리마다 칸 둘을 가진다. 와 보니 제 칸이 이미 찬 스트림 - 이웃들보다 훨씬 오래 열려 있는 스트림이 그렇게 만든다 - 은 테이블을 훑어 찾으며, 상대가 일부러 그렇게 만들면 연결은 지도가 있기 전처럼 테이블을 훑게 되고, 그보다 나쁜 일은 없다.

    9. 이벤트 구동 서버의 HTTP/3#

    typedef struct {
    /* ... 15장이 설명하는 모든 것, 그리고 6절의 필드 ... */
    bool http3;
    bool http3_retry;
    proven_size_t http3_window_bytes;
} proven_http_event_server_config_t;

    HTTP/3(RFC 9114)는 QUIC(RFC 9000) 위의 HTTP다. QUIC은 UDP 위의 전송으로, 스트림, 흐름 제어, 손실 복구와 혼잡 제어를 스스로 하며 TLS 1.3을 아래가 아니라 안에 품는다. 헤더 압축은 HPACK의 후속인 QPACK(RFC 9204)이다. HTTP/2에 견주어 주는 것은 잃은 패킷이 제 스트림만 붙잡는다는 것, 그리고 전송과 TLS의 핸드셰이크가 함께 한 왕복이라는 것이다. 모두 이 라이브러리의 코드다.

    http3를 켜면 6절의 서버가 그것도 말한다. 처리기는 여전히 바뀌지 않는다: 6절의 표는 HTTP/2에 대해 쓴 그대로 HTTP/3에도 맞고, 클라이언트의 창이라고 한 곳이 QUIC의 흐름 제어이며, proven_http_stream_protocol은 3을 답한다. 다른 것은 아래에 있다:

    • listen마다 UDP 소켓도 연다. TCP 리스너와 같은 주소와 포트에. UDP 소켓을 얻지 못한 listen은 실패하고 TCP 리스너는 다시 닫힌다. 포트 0일 때 TCP가 받은 번호의 UDP 포트가 이미 쓰이고 있으면 실패가 아니라 다른 번호를 시도한다(모두 17개까지). HTTP/3은 TLS 위에서만: TLS 설정이 h3를(h2, http/1.1 곁에) 내야 하고, http3가 꺼져 있으면 내지 말아야 한다. QUIC에서 서버는 목록이 TCP에서 무엇을 어떤 순서로 내든 h3만 합의한다(RFC 9114 3.1절). h3를 내지 않는 QUIC 클라이언트는 no_application_protocol로 끝난다. 0.73.2 전에는 서버가 클라이언트가 낸 것 중 자기 첫 선택을 골랐으므로, 이 라이브러리의 클라이언트와 서버는 QUIC에서 h2를 합의하고 그 아래에서 HTTP/3을 말했다.
    • 클라이언트가 찾는 법. HTTP/1.1과 HTTP/2 응답에 Alt-Svc: h3=":PORT" - 연결이 들어온 포트 - 가 붙는다. 처리기가 제 Alt-Svc를 썼으면 그것이 대신 간다. 브라우저나 curl --alt-svc는 다음 요청에서 HTTP/3을 시도하고, curl --http3-only는 곧바로 그것을 청한다.
    • 소켓 하나, 연결 여럿. QUIC 연결은 소켓이 아니라 연결 ID로 가린다. 데이터그램은 그것이 실은 ID의 연결로 가고, 클라이언트의 첫 패킷이 연결을 만들며, 아무도 쥐지 않은 ID로 온 짧은 패킷에는 상태 없는 리셋으로 답한다.
    • 쓰기를 묶는 것은 max_buffered_output이 아니라 QUIC의 보내기 버퍼 - 보냈고 아직 확인되지 않은 데이터가 스트림당 256 KiB, 연결당 1 MiB, 또는 클라이언트가 허락한 범위 안에서 혼잡 창의 두 배, 16 MiB와 24 MiB까지 - 다. 거절된 쓰기는 다른 둘에서처럼 on_writable을 듣는다.
    • 멈춘 요청은 읽히지 않게 되고, QUIC의 흐름 제어가 클라이언트를 http3_window_bytes에서 멈춘다. 기본은 스트림당 256 KiB, 연결당 1 MiB에서 시작해, 본문을 오는 대로 읽는 동안 두 배씩 16 MiB와 24 MiB까지 자란다. 읽히지 않는 본문은 자람을 멈추므로 멈춘 요청은 가졌던 창보다 더 쥐지 않는다(v0.71.0). 보내기 버퍼는 상대가 허락한 범위 안에서 경로가 나르는 만큼(혼잡 창의 두 배) 같은 상한까지 자란다.
    설정HTTP/3에서
    max_connectionsTCP 연결과 함께 QUIC 연결을 센다. 한도에서는 클라이언트의 첫 패킷에 답하지 않는다
    max_concurrent_streams클라이언트가 한 연결에서 한꺼번에 열 수 있는 요청 스트림. 서버가 도는 동안 바꿀 수 있다(proven_http_event_server_set_max_streams, 6절). 클라이언트에게 이미 허락한 것은 거둘 수 없어서(RFC 9000 4.6), 낮춘 수는 요청이 충분히 끝난 뒤에 드러난다. 올린 수는 바로 준다
    max_head_bytes, max_headersQPACK이 세는 가장 큰 필드 구역으로, SETTINGS로 클라이언트에 알린다. max_headers보다 많은 필드는 431
    max_body_bytes요청마다: HTTP/2에서처럼 413
    http3_window_bytes (0: 스트림 256 KiB, 연결 1 MiB에서 본문을 읽는 동안 16 MiB와 24 MiB까지 자람)처리기가 가져가기 전에 클라이언트가 보낼 수 있는 요청 본문 바이트. 값을 주면 고정. 최대 2^31-1
    http3_retry클라이언트마다 첫 패킷에 Retry: 주의할 것을 보라
    head_timeout_ms연결의 첫 패킷부터 - 핸드셰이크를 포함해 - 첫 요청까지
    body_timeout_ms본문이 남은 요청 하나의 침묵: 그 스트림이 리셋되고, 나머지는 계속된다
    write_timeout_ms움직이지 않는 출력: 연결이 닫힌다
    idle_timeout_ms열린 요청이 없음: 서버가 작별하고 닫는다. 아무것도 오지 않는 연결 - 사라진 클라이언트 - 은 이것과 head_timeout_ms 중 큰 것보다 1초 뒤에 놓는다(QUIC의 유휴 시간 초과)

    작별은 한 왕복을 사이에 둔 GOAWAY 둘이다(RFC 9114 5.2절). 첫째는 클라이언트가 아직 보낼 수 있는 가장 큰 요청을 알려, 이미 오는 중인 요청은 거절되지 않고 답을 받는다. 둘째는 처리하지 않은 첫 요청을 알리고, 받은 것에 다 답하면 연결은 H3_NO_ERROR로 닫힌다. proven_http_event_server_stop_listening이 이렇게 한다. UDP 소켓은 연결이 쓰는 동안 열려 있고, 같은 포트에 다시 listen하면 그것을 이어 쓴다. proven_http_event_server_shutdown과 _destroy는 HTTP/2 연결을 끝내듯 HTTP/3 연결을 끝낸다.

    주의할 것, 그리고 잘못되는 것#

    • UDP는 핸드셰이크 전에 서버에 닿는다. 누구든 어떤 주소에서나 클라이언트의 첫 패킷을 보낼 수 있고, http3_retry가 없으면 하나하나가 연결을 만든다 - 핸드셰이크를 기다리는 동안 약 40 KiB, 답하지 않는 주소 천 곳에서 잰 값 - 그리고 head_timeout_ms가 그것을 놓을 때까지 간다. 그런 주소에는 그 주소가 보낸 것의 세 배보다 많이 보내지 않으므로(RFC 9000 8절) 서버를 남을 향한 범람에 쓸 수는 없지만, 범람은 max_connections만큼을 붙잡을 수 있다. http3_retry는 주소가 받는다는 것을 보일 때까지 아무것도 두지 않으며, 연결마다 한 왕복을 치른다.
    • Retry 토큰과 상태 없는 리셋의 키는 서버를 만들 때 뽑는다. 다시 시작한 서버는 클라이언트의 옛 연결을 리셋할 수 없고, 그 클라이언트는 유휴 시간 초과를 기다린다.
    • 타이머는 제 시각에 울린다(POSIX에서는 약 1 ms 안, Windows에서는 시스템 타이머 간격; v0.70.0): 조용한 연결의 QUIC 타이머 - 프로브, 늦춘 확인 - 는 더 이상 다음 16 ms 경계를 기다리지 않고, 바쁜 연결은 라운드마다 제 일을 한다.
    • HTTP/3이 얼마나 빠른지는 플랫폼에 달렸다. Linux에서는 한 라운드의 데이터그램이 커널에 함께 간다 - 1,452바이트 45개까지 호출 하나에(UDP_SEGMENT), 수신 하나가 여러 개를 돌려줄 수도 있다(UDP_GRO). Windows에서도 USO와 URO로 같다(UDP_SEND_MSG_SIZE, UDP_RECV_MAX_COALESCED_SIZE; v0.74.0). 다른 곳에서는 데이터그램 하나가 시스템 호출 하나다. 어느 쪽이든 하나하나 따로 암호화되고 보호된다. Windows 11 시험 VM에서 이 서버와 이 클라이언트를 한 프로세스에 두고 루프백으로 256 MiB: HTTP/3 2,545 Mbit/s, 데이터그램마다 호출 하나일 때 1,021, HTTP/2 1,919(x86-64. i686은 1,807, 845, 1,627). Linux 루프백에서 이 서버로부터 curl로 100 MiB 하나를 내려받는 데 HTTP/3은 369 MiB/s, HTTP/2는 382, HTTP/1.1은 499였다(모두 TLS 위; v0.68.0. v0.67.0에서는 데이터그램마다 호출 하나로 219, v0.65.0에서는 174).
    • 데이터그램은 1,200바이트에서 시작해 탐침으로 커진다(RFC 9000 14.3절). 경로와 상대가 실어 나르면 1,452까지: 1,452를 나르는 경로에서는 핸드셰이크 뒤 탐침 하나, 찾은 뒤에는 없음. 경로가 그 크기를 더 나르지 않으면 손실이나 탐침 타임아웃으로 알아채고, 크기를 1,200으로 되돌린 뒤 다시 찾는다. 설정할 것은 없다. 모든 데이터그램에 조각 금지 비트가 서고 이쪽에서는 아무것도 조각내지 않으므로(Linux IP_PMTUDISC_PROBE, Windows IP_DONTFRAGMENT; v0.69.0), 통과한 탐침은 통째로 통과한 것이다.
    • TLS 설정에 early_data가 있으면 0-RTT(14장 6절; v0.73.0). 재개하는 클라이언트는 첫 요청들을 첫 패킷에 실어 보낼 수 있고, 서버는 첫 응답에서 답한다: 왕복 둘이 하나가 된다. 그렇게 온 요청은 핸드셰이크가 끝나기 전에 핸들러에게 가며, 그 요청에서 proven_http_stream_early는 참이다: 공격자가 재전송한 사본일 수 있다. 핸들러에게 조기에 가는 것은 본문 없는 GET, HEAD, OPTIONS뿐이고, 그 밖의 것이 조기에 오면 서버가 스스로 425(Too Early)로 답한다. 사본에 따라 행동하면 안 되는 핸들러도 425로 답하면 된다 - 클라이언트는 핸드셰이크가 끝난 뒤 요청을 다시 보낸다. 기본은 꺼짐.

    • 클라이언트의 다음 연결은 주소 확인을 건너뛴다. 핸드셰이크마다 서버는 클라이언트에게 IP 주소에 묶이고 하루 동안 유효한 토큰(NEW_TOKEN, RFC 9000 8.1.3절)을 준다. 그 토큰을 가져온 연결은 곧바로 확인된 것으로 다뤄지므로

      • 보낸 양의 3배라는 한도도, http3_retry의 Retry도 없다 - 약 3.6 KB보다 큰 0-RTT 응답도 왕복 하나를 기다리지 않는다. 확인되지 않는 토큰은 없는 것으로 다룬다.
    • HTTP/3 위에서 없는 것: WebSocket(proven_ws_event_accept는 그 스트림을 거절한다), 트레일러, 서버 푸시, 이쪽 스스로의 이주(클라이언트의 새 주소는 검증한다), 1이 아닌 QUIC 버전. proven_http_event_server_adopt는 TCP 연결만 받으므로, 여러 루프가 UDP 포트 하나를 나눠 쓸 수 없다.
    • 이벤트 구동 클라이언트는 요청이 청하면 HTTP/3을 말한다(10절). 이 서버의 Alt-Svc를 스스로 따르지는 않는다.

    어떻게 시험했는가. 등록된 시험이 루프백 UDP 위에서 이 라이브러리의 QUIC과 HTTP/3 엔진으로 만든 클라이언트를 이 서버에 붙인다 - WebSocket이 아닌 HTTP/2 시험의 모든 경로, 한도, 각 시간 초과, 작별, Retry. 등록된 시험 밖에서: curl --http3-only(OpenSSL의 QUIC)와 aioquic의 클라이언트를 이 서버에, 모든 응답을 바이트 단위로 확인. h3spec 0.1.14, 77개 중 76개 통과 - 통과하지 않은 하나는 반복된 모르는 설정으로, RFC 9114가 서버에 받아도 된다고 하는 것이다. 답하지 않는 주소에서 클라이언트의 첫 패킷 천 개, 주소마다 보낸 것의 세 배 이하만 보냈고, 모두 head_timeout_ms 뒤에 놓았으며, http3_retry로는 하나도 두지 않았다.

    10. 이벤트 구동 클라이언트의 HTTP/3#

    typedef struct {
    /* ... 15장이 설명하는 모든 것, 그리고 7절의 필드 ... */
    bool http3;
    proven_size_t http3_window_bytes;
} proven_http_event_client_config_t;

typedef struct {
    /* ... */
    bool http3;            /* 이 요청을 HTTP/3으로 */
} proven_http_event_request_options_t;

    HTTP/2는 TLS 핸드셰이크가 고른다. HTTP/3은 그럴 수 없다 - UDP 위의 다른 전송이고, 첫 패킷 전에는 물을 것이 없다. 그래서 호출자가 고른다: http3를 켠 클라이언트는 옵션에 http3를 적은 요청을, 각각 https URL로, HTTP/3으로 보내고, 다른 요청은 전처럼 보낸다. 서버의 Alt-Svc를 스스로 따르지 않는다. 콜백과 요청 호출은 세 프로토콜에 같고, proven_http_event_request_protocol은 처음부터 3을 답한다.

    아래에서 일어나는 일은 QUIC 위의 7절이다: 오리진(스킴, 호스트, 포트, 주소)마다 연결 하나를 제 UDP 소켓에 두고 요청들이 나눠 쓴다. 서버의 스트림 한도를 넘는 요청은 그 위에서 기다린다. 쉬는 연결은 idle_timeout_ms 뒤에 작별하고 닫는다. max_connections는 TCP 연결과 함께 센다. retry_unsent는 서버가 처리하지 않고 거절한 요청(H3_REQUEST_REJECTED, 또는 GOAWAY 뒤)을 다시 보낸다. decompress는 다른 것에서처럼 푼다. 쓰기는 QUIC의 보내기 버퍼 - 스트림 256 KiB, 연결 1 MiB, 또는 서버가 허락한 범위 안에서 혼잡 창의 두 배, 16 MiB와 24 MiB까지 - 로 묶이고, 멈춘 응답은 읽히지 않아 서버는 가졌던 창에서 멈춘다. 오는 대로 읽으면 http3_window_bytes가 고정하지 않는 한 창이 스트림 16 MiB, 연결 24 MiB까지 자란다(v0.71.0).

    대체는 없다. HTTP/3으로 청한 요청의 서버가 UDP로 답하지 않으면 connect_timeout_ms가 지난 뒤 PROVEN_ERR_TIMEOUT으로 - 연결하지 않은 UDP 소켓은 거절을 듣지 못한다 - , h3를 거절하는 서버면 PROVEN_ERR_UNSUPPORTED로, 믿을 수 없는 서버면 PROVEN_ERR_UNTRUSTED로 끝난다. QUIC에서 클라이언트는 TLS 설정이 TCP에서 무엇을 내든 h3만 내고 그 밖의 것은 받지 않는다(0.73.2부터). TCP 연결은 시도하지 않는다: 그것을 원하는 호출자는 http3 없이 요청을 다시 시작한다.

    주의할 것, 그리고 잘못되는 것#

    • 그것을 말한다고 알려진 서버에만 청하라. 어느 서버가 그런지 여기서는 배우지 않는다. 서버의 Alt-Svc가 말해 주며, 그것을 읽는 것은 호출자의 몫이다.
    • 얼마나 빠른지는 서버처럼 플랫폼에 달렸다: Linux에서는 한 라운드의 데이터그램이 커널에 함께 가고 수신 하나가 여러 개를 돌려줄 수 있으며, 다른 곳에서는 하나에 시스템 호출 하나다. Linux 루프백에서 이 라이브러리의 서버로부터 이 클라이언트로 100 MiB 하나를 내려받는 데 HTTP/3은 393 MiB/s, HTTP/2는 340이었다(v0.68.0; v0.67.0의 HTTP/3은 233, v0.65.0은 171). 데이터그램은 서버처럼 탐침으로 1,200에서 1,452바이트까지 커진다.
    • TLS 세션은 출처마다 보관한다(15장; v0.72.0): 새 연결은 그것을 재개하고, 서버의 NEW_TOKEN 토큰을 다음 연결을 위해 보관하므로 다음 연결은 주소 확인을 건너뛴다.
    • TLS 설정에 early_data가 있으면 0-RTT(14장 6절; v0.73.0). 세션이 허용하는 새 연결에서는 본문 없는 GET, HEAD, OPTIONS 요청을 첫 패킷에 실어 보내 왕복 하나 먼저 답을 받는다. 그 밖의 요청은 핸드셰이크를 기다린다. 조기 데이터로 거절되거나 425를 받은 요청은 핸드셰이크 뒤 한 번 다시 보내며, 두 번째 답만 전달한다. 기본은 꺼짐.
    • 여기 없는 것: 이쪽 스스로의 연결 이주, HTTP/3 위 WebSocket.

    어떻게 시험했는가. 등록된 시험이 이 클라이언트를 루프백 UDP 위 이 라이브러리의 서버에 붙인다 - 서버가 답할 수 있는 7절 시험의 모든 사례, 클라이언트의 거절, 대체 없음, 믿을 수 없는 서버, 시간 초과. 등록된 시험 밖에서: aioquic의 서버(50 MB까지 바이트 단위 다운로드, 업로드, 트레일러, 건너뛴 중간 응답, 요청 400개)와 공개 서버 둘, cloudflare-quic.com과 www.google.com.
