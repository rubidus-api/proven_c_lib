## 1. 목적과 결정 사항

이 문서는 구현 명세이며, 라이브러리를 빠짐없이 검증했다는 주장이 아니다.
현재 소스에서 발견한 독립적으로 처리 가능한 경계 조건·보안 결함 4건과,
기존에 기록된 Windows 결함 2건을 종결하기 위한 구체적인 작업으로 RFC-0005를 확장한다.
이 RFC는 실제 제품 소스나 등록된 테스트를 변경하지 않는다. 현재 통과하는 테스트는
아래 재현 사례를 다루지 않는다. RFC-0005의 과거 통과 결과는 이 기준 커밋에서
새로 얻은 결과가 아니다.

H-002, H-001, H-004, H-003, 이후 네이티브 Windows 작업 H-005/H-006 순으로
각각 테스트부터 작성하는 변경을 승인한다. 할당자, 파서, 큐, 파일시스템 재설계를
하나의 패치에 합치지 않는다. 이 RFC에서 명시적으로 결정이 필요하다고 한 경우 외에는
공개 함수 시그니처를 유지하며, 해당 결정은 구현 전에 받는다.

### 심각도와 근거

- P1: 명시한 입력이나 환경에서 발생하는 긴급한 기밀성 또는 경계 위반.
  어느 항목도 모든 환경에 적용되는 P0 릴리스 비상 상황은 아니다.
- P2: 특정 경로, 카운터 경계 또는 대상 환경에서 발생하는 정확성 결함.
- E3: 집중적인 로컬 실행 프로그램으로 해당 현상을 재현함.
- E2: 소스 수준의 입증이며, 영향받는 대상 환경이나 전체 크기 시나리오는 실행하지 않음.
- Gap: 실패를 입증하지도, 대상 환경의 통과를 확인하지도 못함.

|---|---|---|---|---|
| H-001 | P1 | 크기 헬퍼 E3; 인코더 용량 검사 우회 E2 | 메모리 접근 전에 인코딩 산술 검사 | 신규 |

## 2. 감사 범위와 한계

이번 검토에서는 `arena.c`, `pool.c`, `array.c`, `buffer.c`, `ring.c`, `u8str.c`,
`u16str.c`, `map.c`, `mmap.c`, `encode.c`, `random.c`, `stream.c`, `job.c`, `fs.c`의
소유권, 산술, 오류 경로를 표본 검토했으며, 관련 공개 계약과 메모리·파일시스템·난수
PAL 경로도 함께 확인했다. 나열한 모든 모듈을 한 줄씩 입증한 것은 아니다.
부동소수점 변환, 포맷팅·스캐닝, 해시 알고리즘, 시간 및 나머지 플랫폼 분기는
기준 테스트 모음 실행이나 이전 RFC와의 비교만 수행했으며, 알고리즘 전체를 새로
철저히 감사한 것은 아니다.

새로 확보한 로컬 근거의 환경: GCC 14.2.0, Linux, 64비트 `size_t`.

| 실제 실행한 검사 | 결과 | 한계 |
|---|---|---|
| `cc nob.c -o nob` 후 `./nob build` | 통과; 캐시된 소스 객체 34개, 캐시된 테스트·예제 실행 파일 192개 실행 | 네이티브 디버그 테스트 모음이며, 클린 재빌드나 새로운 새니타이저 조합 검증은 아님 |
| 부록 A 관찰 프로그램 | 인코딩 헬퍼가 0 반환; 임시 파일 초기 권한 0644, 유지한 fd로 NEW 읽음; 역슬래시 경로의 내구성 쓰기가 NEW를 공개한 뒤 오류 반환 | 링커 가로채기를 적용한 실제 로컬 시스템 호출; 다른 사용자로 수행한 악용 테스트는 아님 |
| UBSan을 적용한 부록 B 큐 검사 | 예상대로 실패: `job.c:262`에서 부호 있는 뺄셈 오버플로 | 제어된 큐 상태이며, 수십억 회 제출이나 전체 테스트 모음의 UBSan 실행은 아님 |

이 문서 변경에 대해 `scripts/project-check.sh`가 통과했으며, 문서, 예제 동등성,
개인정보 및 공백 검사를 포함한다. 위 표만으로 Windows, macOS, 32비트, 임베디드,
ASan, TSAN 또는 새로 실행한 전체 UBSan 검증의 성공을 추론하지 않는다.

### 결함으로 보지 않는 사항과 보류 작업

- *다른* 정렬 값으로 arena/pool realloc을 호출하는 것은 유효한 회귀 사례가 아니다.
  `include/proven/allocator.h`는 원래 정렬 값을 요구한다. 호출자 계약 위반을 고치기
  위해 할당자 의미를 확장하지 않는다.
- 뒤쪽 내용을 이동시키는 별칭 참조 문자열 치환은 `include/proven/u8str.h`에서
  명시적으로 금지한다. 해당 입력의 거부를 새로운 결함으로 취급하지 않는다.
- 크기를 과장한 모의 뷰는 공격자가 실제 64비트 프로세스에서 그 뷰를 할당할 수 있다는
  증거가 아니다. H-001은 산술 입증과 실제 악용 가능성을 구분한다.
- RFC-0005 C-002/C-003, V-001/V-002/V-004..V-012 및 B-034..B-038은 별도의
  후속 작업으로 남는다. 종결을 주장하기 전에 소스와 대상 환경의 사용 가능 여부를 재확인한다.
- 파일 복사의 경로명 대상 동일성 경쟁, Windows 경로 변환 경쟁, 맵 엔트로피 대체 정책,
  장시간 실행 시 세마포어 허가 누적은 집중적인 후속 검토가 필요하지만, 이 RFC는
  해당 문제의 악용을 재현했다고 주장하지 않는다.
- 이번 작업에서 문서 워크플로 불일치를 확인했다. `docs/operations/README.md`는
  변경 이력의 `Unreleased` 절을 요구하지만, 이를 추가하면
  `test_docs_version_sync.c:176`이 실패한다. 시험 삼아 추가한 변경 이력은 제거했으며,
  이 RFC는 릴리스 이력을 바꾸지 않는다. 동작 변경을 반영하기 전에 최신 릴리스 버전
  검사에서 Unreleased를 건너뛰도록 검사와 변경 이력 정책을 맞추거나, 승인받은
  릴리스·버전 갱신을 함께 진행한다. 이 제안 RFC를 통과시키기 위한 목적으로만
  릴리스 버전을 올리지 않는다.
- 벤치마크로 뒷받침한 성능 변경은 제안하지 않는다. 최적화를 추측하지 말고
  RFC-0005의 측정 요구사항을 유지한다.

## 3. H-001: 인코딩 산술이 출력 크기를 실제보다 작게 계산할 수 있음

### 소스와 발생 조건

`src/proven/encode.c`의 `proven_hex_encoded_size`, `proven_hex_encode`,
`proven_base64_encoded_size`, `proven_base64_decoded_size`, `base64_encode_impl`이
대상이다. `include/proven/encode.h`의 공개 계약은 용량이 부족하면 일부만 쓰는 일 없이
거부한다고 보장한다.

M을 `SIZE_MAX`라고 하면 현재 헬퍼는 다음 입력에서 0을 반환한다.

- 16진수 인코딩 크기: `M / 2 + 1` (`n * 2`가 래핑됨).
- Base64 인코딩 크기: M (`n + 2`가 래핑됨).
- Base64 디코딩 크기 상한: M (`n + 3`이 래핑됨).

헬퍼만 고쳐서는 인코더 자체가 보호되지 않는다. 16진수 인코더는 `data.size * 2`를
다시 계산하고, Base64는 `full * 4`와 꼬리 부분 덧셈을 검사 없이 계산한다.
래핑된 `need`는 `need > out_cap` 검사를 통과할 수 있으며, 이후 실제 용량에 맞지 않는
출력 쓰기가 발생한다. 인코딩 경로는 입력이나 출력에 접근하기 전에 표현 불가능한
출력을 거부해야 한다. 표현 가능한 실제 입력에서는 경계 위반이며, 큰 유효 입력은
64비트보다 32비트 대상에서 더 현실적이다. 헬퍼 실패 자체는 입력 할당 없이 완전히 재현된다.

### 제안하는 구현

1. `PROVEN_CKD_MUL`과 `PROVEN_CKD_ADD`로 정확한 크기를 검사하며 계산하는 내부
   기능을 도입한다. 16진수는 `n * 2`를 검사한다. Base64는 `(n / 3) * 4`를 검사한 뒤
   나머지와 패딩 모드에 따라 0/2/3/4를 더한다.
2. 두 인코더 모두 바이트에 접근하기 전에 정확한 크기를 계산하고 검증한다.
   표현 불가능한 크기는 `PROVEN_ERR_OVERFLOW`를 반환하고, 표현 가능하지만 용량을
   초과하는 크기는 기존 `PROVEN_ERR_OUT_OF_BOUNDS`를 유지한다. 두 오류 모두
   `written_out == 0`을 유지하고 출력을 건드리지 않는다.
3. 올림용 덧셈의 오버플로 없이 디코딩 상한을 계산한다.
   `(n / 4) * 3 + (n % 4 != 0 ? 3 : 0)`. 최댓값도 `size_t`에 들어간다.
4. 현재 공개 크기 헬퍼는 오류를 반환할 수 없다. 시그니처 호환성을 유지하는 정책으로,
   *인코딩 크기* 오버플로 시 `SIZE_MAX`를 반환하고 이 센티널 값을 문서화할 것을 제안한다.
   인코더는 해당 값을 용량으로 받더라도 독립적으로 오버플로를 거부해야 한다.
   유효한 16진수 및 패딩 있는 Base64 출력 크기는 `SIZE_MAX`가 될 수 없다.
   0은 빈 입력도 뜻하므로 센티널로 사용하지 않는다. 소유자 결정이 필요하다.
   이 정책을 수용하거나, 결과를 반환하는 검사형 헬퍼와 별칭·예제를 추가하면서
   문서화한 기존 래퍼를 유지한다.
5. 덧셈 자체가 래핑될 수 있는 `i + 3`, `i + 4` 대신 남은 길이나 완전한 그룹 수를
   반복 조건으로 사용한다. 이 산술 수정에서 Base64 문자 집합이나 패딩 허용 규칙은 바꾸지 않는다.

### 테스트와 완료 조건

기존 인코딩 단위 테스트부터 확장한다. 헬퍼만 검사하는 입력으로 0..6,
`M/2 - 1`, `M/2`, `M/2 + 1`, `M-3`부터 M까지, 패딩 유무별로 표현 가능한
최대 출력의 전환 경계를 사용한다. 기대 결과는 기존 식을 복사하지 말고 검사형 산술이나
나눗셈으로 도출한다. 인코더 세 가지 모두에 대해 정확한 용량과 1바이트 부족한 출력을
카나리 및 `written_out` 단언과 함께 추가한다.

불가능한 크기의 거부를 검사할 때 의도적으로 합성한 뷰는 초기 검증용 검사에만 사용할 수
있다. 그 용도를 표시하고 ASan 아래 격리하며 메모리 접근이 전혀 없도록 요구한다.
이를 유효하게 할당된 거대 객체라고 설명하지 않는다. 가짜 저장 공간 없이 경계 산술을
검사할 수 있도록 크기 검사 부분에 테스트용 접점을 두는 방식을 우선한다.

완료 조건: 네이티브 및 32비트 검증 환경에서 모든 크기 계산이 정확하고, 용량 판단에
래핑된 값을 사용하지 않으며, 거부 시 쓰기가 발생하지 않는다. 일반 테스트 벡터의
바이트 결과는 동일해야 한다. 공개 오류·센티널 의미를 헤더, 영문·한국어 매뉴얼,
추가한 경우 별칭, 변경 이력에 문서화한다.

## 4. H-002: 쓰기 전 chmod는 이미 열린 fd의 접근을 취소하지 못함

### 소스와 위협 모델

`src/proven/fs.c:internal_write_file_atomic`은 `proven_fs_open`을 통해 예측 가능한
`.pvtmpNN` 형제 파일을 연 뒤 chmod로 대상 파일의 모드를 적용한다. POSIX에서
`platform/proven_sys_fs.c:proven_sys_fs_open`은 umask를 적용한 `0666`으로 생성한다.
umask가 0022이면 임시 파일의 초기 모드는 0644다. 디렉터리를 탐색할 수 있는 다른
로컬 사용자는 chmod 전에 파일을 읽기 전용으로 열고 디스크립터를 유지할 수 있다.
나중에 0600으로 chmod해도 이미 열린 디스크립터는 무효화되지 않는다. 따라서 첫 데이터
쓰기 전에 파일 권한을 좁혀도, 이후 기록하는 비공개 내용을 그 디스크립터로 읽을 수 있다.
공격자에게 디렉터리 쓰기 권한은 필요하지 않다.

부록 A는 실제 임시 파일 생성을 가로채 모드 0644를 관찰하고, 읽기 디스크립터를 열어
유지한 뒤 라이브러리 실행을 재개하여 비공개 파일 덮어쓰기 성공 후 NEW를 읽는다.
이는 한 사용자로 실행한다. 사용자 간 접근 가능성의 근거는 관찰된 다른 사용자 읽기 권한과
일반적인 POSIX 열린 fd 의미이며, 두 번째 UID로 테스트한 결과가 아니다.

새 대상을 만드는 `proven_fs_copy`도 생성 후 chmod하는 같은 패턴을 따른다.
따라서 원자적 쓰기만 유일한 사용처라고 하지 말고 복사도 수정에 포함한다.
이미 읽을 수 있는 기존 대상에는 독자가 있을 수 있으며, 그 독자의 접근을 소급하여
취소하는 것은 이 라이브러리가 제공할 수 있는 보장이 아니다.

### 제안하는 구현

1. 생성 모드를 지정하는 비공개 PAL 열기 연산이나 명시적 내부 제한 생성 옵션을 추가한다.
   스테이징 파일의 *최초 생성 시스템 호출에* `O_CREAT | O_EXCL`과 함께 0600을 전달한다.
   프로세스 umask를 바꾸지 않는다. 이는 프로세스 전체가 공유하는 가변 상태다.
2. 공개 `proven_fs_open`의 기본값은 유지한다. 원자적·내구성 쓰기의 스테이징과
   새 복사 대상은 제한 생성 경로로 옮긴다. 새 헬퍼의 모든 호출 지점을 감사하며,
   공개 API의 새 파일 권한을 일괄 변경하지 않는다.
3. 최종 sync/rename 전에 열린 핸들을 통해 최종 권한을 적용한다(PAL 내부의 `fchmod`).
   chmod를 위해 스테이징 경로명을 다시 해석하지 않는다. 교체 시 대상 모드를 이어받는다.
   새 원자적 쓰기 대상은 동시성에 안전한 설계로 문서화된 기본 모드 동작을 유지하거나,
   제한적인 새 파일 기본값을 문서화하도록 승인받는다. umask를 잠시 0으로 설정하는 것을
   스레드 안전한 umask 조회라고 간주하지 않는다.
4. 필수 권한 작업이나 메타데이터 조회가 실패하면 비공개 데이터 쓰기를 진행하지 않는다.
   대상 부재와 메타데이터 조회 실패를 구분한다. 현재 불리언 stat 결과는 이 구분을
   잃는다. 필요하면 PAL 오류 정보를 추가하되 `src/proven/`에서 OS를 직접 호출하지 않는다.
5. 배타적 생성, 정리, 닫기 오류 전파, rename 전 실패 시 기존 대상 보존을 유지한다.
   Windows 권한 설계는 POSIX 모드 비트가 동등한 기밀성을 보장한다고 가정하지 말고
   ACL을 고려해야 한다. 네이티브 ACL 검증은 별도의 대상 환경 결과로 남긴다.

### 테스트와 완료 조건

관찰용 훅을, 실행을 계속하기 전에 초기 모드에 그룹·다른 사용자 접근 권한이 없는지
확인하는 회귀 테스트로 교체한다. 0600 대상의 원자적·내구성 교체, 0600 원본의 새 경로
복사, umask 0000/0022/0077, open/chmod/write/sync/close 실패, 임시 파일 이름 충돌을
다룬다. 확률적인 감시 루프 대신 시스템 호출 가로채기와 배리어를 사용한다.
다른 사용자로 수행하는 통합 테스트는 환경이 없으면 건너뛸 수 있으며, 그 사실을 보고한다.

초기 비공개 모드뿐 아니라 최종 공개 모드도 검증한다. 커밋 지점 전 실패는 기존 내용을
보존하고 자신이 소유한 임시 파일만 제거해야 한다. 악의적인 디렉터리 작성자, 이미 권한을
받은 독자, ACL 보존, 안전한 삭제에는 별도 보장이 필요함을 명시한다. 제한적인 생성만으로
모든 파일시스템 경쟁을 해결할 수는 없다. 완료 조건: chmod 전에 읽을 수 있는 스테이징
노출 구간과 전역 umask 변경이 없으며, 모든 호환성 결정을 문서화한다.

## 5. H-003: POSIX 내구성 쓰기가 역슬래시 경로에서 잘못된 부모를 동기화함

`src/proven/fs.c:internal_parent_dir`은 모든 플랫폼에서 슬래시와 역슬래시를 모두
구분자로 취급한다. POSIX는 파일명 안의 역슬래시를 허용한다.
`build/rfc-0006/a\b`에 대한 내구성 쓰기는 올바른 파일을 생성하고 rename하지만,
부모가 아닌 `build/rfc-0006/a`를 동기화하려 한다. 해당 경로가 없으면 NEW가 이미
보이는 *이후에* I/O 오류를 반환한다. 그 경로가 기존 디렉터리이면 잘못된 디렉터리를
동기화하고 내구성 확보를 거짓으로 보고할 수 있다. 부록 A는 첫 번째 경우를 재현한다.
같은 구현의 파일명 잘라내기 루프도 이 무조건적인 구분자 규칙을 사용한다.

수정: 플랫폼을 고려한 구분자·부모 선택을 한곳에 모은다. POSIX에서는 슬래시만 경로
구성요소를 구분한다. Windows에서는 지원하는 경로 계약에 따라 슬래시·역슬래시,
드라이브 루트, 드라이브 상대 경로, UNC 공유 및 확장 경로를 처리한다.
POSIX 파일명을 Windows 표기로 정규화하지 않는다. 부모 추출과 스테이징 이름의
파일명 판별에 같은 규칙을 적용한다. 플랫폼 연산은 PAL을 거치고 코어에 OS 헤더를 넣지 않는다.

테스트: 실제 역슬래시가 든 파일명, 일반 슬래시 경로, 구분자 없는 경로, 루트 부모,
역슬래시가 포함된 최대 길이 파일명, 잘못된 접두사와 일치하도록 만든 미끼 디렉터리.
PAL 동기화 관찰자는 실제 동기화한 부모를 기록해야 한다. PROVEN_OK만 확인하면 미끼
사례를 놓친다. 파일 sync -> rename -> 올바른 디렉터리 sync 순서를 기록한다.
실제 디렉터리 동기화 실패 테스트도 유지한다. 성공한 rename 이후의 오류는 rename을
되돌릴 수 없다. 모든 내구성 쓰기 오류에서 기존 바이트를 보존한다고 주장하지 말고
그 커밋 경계를 문서화한다. 완료 조건: 두 POSIX 사례에서 올바른 부모를 사용하고,
Windows 네이티브 루트 사례는 Linux에서 유추한 통과가 아닌 독립적인 결과를 갖는다.

## 6. H-004: 부호 있는 시퀀스 뺄셈이 부호 경계에서 오버플로함

`src/proven/job.c:proven_job_submit`은
`(proven_ptrdiff_t)seq - (proven_ptrdiff_t)pos`를 계산하며,
`proven_job_execute_one`도 `pos + 1`에 대해 같은 계산을 한다.
부호 있는 정수 범위의 전환 경계에서 두 캐스트 결과는 `PTRDIFF_MAX`와 `PTRDIFF_MIN`이
될 수 있다. 의도한 큐 거리는 -1에 불과해도 두 값을 빼면 부호 있는 정수 오버플로다.
이는 유효한 가득 찬 큐에서 도달 가능한 상태다. 용량 2, 삽입 위치 p = `PTRDIFF_MAX + 1`,
꺼내기 위치 p - 2, 셀 시퀀스 p - 1과 p인 경우다. 제출은 큐를 변경하지 않고 가득 찼다는
이유로 거부되어야 한다.

부록 B는 정확히 이 상태를 설정하며 UBSan은 부호 있는 정수 오버플로를 보고한다.
이것이 64비트에서 자연스럽게 실행 시간이 누적된 끝에 실패했음을 입증하는 것은 아니다.
32비트에서 2^31회 제출을 넘는 데 걸리는 시간은 훨씬 짧다. 이 산술 결함에 동시성 경쟁은
필요하지 않다.

수정: 부호 없는 큐 카운터 타입으로 시퀀스 거리를 계산한 뒤, 부호 있는 뺄셈 없이
0·앞·뒤를 분류한다. 모듈러 거리 규칙을 문서화하고 큐 용량을 카운터 범위의 절반보다
엄격히 작게 제한한다. 불가능한 용량은 초기화 시 할당 전에 거부한다.
부호 없는 값의 최상위 비트를 명시적으로 분류하면, 표현 범위 밖의 부호 없는 값을
부호 있는 타입으로 변환하는 동작에 의존하지 않아도 된다. 검토한 헬퍼 하나를 생산자와
소비자 양쪽에서 사용한다. 이 패치에서는 메모리 순서 지정, 제출 허용 제어, 깨우기 허가,
큐 비우기 동작을 바꾸지 않는다.

테스트: `PTRDIFF_MAX`, 부호 전환, `SIZE_MAX`, 부호 없는 값의 0으로의 래핑 주변에
빈 큐·가득 찬 큐·비어 있지 않은 큐 상태를 설정한다. 제출과 실행 경로를 모두 검사하며,
수락된 작업은 정확히 한 번 실행되고 가득 찬 큐의 거부는 셀을 덮어쓰지 않아야 한다.
접점은 테스트 전용으로 유지한다. 새로운 공개 변경 API보다 내부 거리 헬퍼와 큐 상태
하니스를 우선한다. 집중 UBSan, 가능한 경우 네이티브 32비트 검증, 기존 close/destroy
스트레스 및 TSAN 테스트를 실행한다. 완료 조건: 부호 있는 정수 오버플로 보고가 없고,
모듈러 비교가 정확하며 큐 종료 동작에 회귀가 없다.

## 7. 기존 Windows 결함: 구체적인 종결 작업

### H-005: 교체 연산 (RFC-0005 C-001)

`platform/proven_sys_fs.c:proven_sys_fs_rename`은 여전히 `MoveFileW`를 사용하며,
대상이 이미 존재하면 실패한다. 두 전체 파일 원자적 쓰기 함수가 모두 이 경로를 거친다.
따라서 Windows에서는 일반적인 두 번째 쓰기가 실패한다.

대상을 먼저 삭제하는 방식으로 고치지 않는다. 원자적 가시성을 잃고, 이후 실패하면
기존 파일을 잃을 수 있다. 명시적 계약을 가진 지원 교체 연산을 선택한다.
예를 들어 교체 플래그를 사용하는 `MoveFileExW`, 또는 대상이 없는 경우를 별도로 처리하는
`ReplaceFileW`가 있다. 동일 볼륨 의미를 유지하며, 조용히 복사·삭제로 대체하는 동작은
허용하지 않는다. 최종 연산을 선택하기 전에 읽기 전용 대상, ACL·메타데이터, 공유,
심볼릭 링크, 내구성 동작을 정의한다. 진단을 위해 원래 Windows 오류를 보존한다.

필수 네이티브 테스트: 최초 생성, 교체, 공유 허용 유무별 열린 독자, 읽기 전용 대상,
교체 실패, 유니코드·긴 경로, 이름 부재나 부분 내용 노출 구간 없음, 실패 시 기존 바이트
보존, 핸들·임시 파일 누수 없음. 소스 텍스트 테스트나 크로스 링크는 네이티브 원자성의
근거가 아니다. 중복 백로그 항목을 만들지 말고 B-033을 재사용한다.

### H-006: 엔트로피 요청 크기의 축소 변환 (RFC-0005 V-003)

`platform/proven_sys_random.c:proven_sys_random_bytes`는 `BCryptGenRandom`에
전달할 `size_t len`을 한 번 `ULONG`으로 캐스팅한다. 64비트 Windows에서
`len > ULONG_MAX`이면 조용히 축소된다. 앞부분만 요청하거나 0바이트를 요청할 수 있으며,
NTSTATUS 성공을 전체 버퍼의 성공으로 변환한다. 호출자는 변경되지 않은 바이트를 새로운
엔트로피로 취급할 수 있다. 일반적인 시드 초기화의 작은 요청은 이 결함을 검사하지 못한다.

수정: 최대 `ULONG_MAX`인 겹치지 않는 청크를 반복 처리하고 모든 BCrypt 호출을 검사한다.
성공한 뒤에만 포인터를 전진시키고 남은 수를 줄인다. 어느 청크든 실패하면 false를 반환하고
PRNG로 대체하지 않는다. 실패 시 앞부분이 채워져 있을 수 있음을 명시하여, 기존 불리언
API와 일치하게 호출자가 결과 전체를 버리도록 한다. 길이 0 요청의 true와 길이가 0이 아닌
null 요청의 false는 유지한다.

테스트: 기가바이트 단위 할당 없이 0, 1, limit-1, limit, limit+1, 2*limit+1을
검사할 수 있도록 비공개 청크 계획기·백엔드 접점을 분리한다. 합계, 오프셋, 빈틈·겹침 없음,
첫·중간·마지막 청크 실패를 검사한다. 작은 인위적 한도와 실제 작은 출력 버퍼로 포인터
이동을 검사한다. 산술 전용 대규모 테스트는 객체 밖 포인터를 만들면 안 된다.
네이티브 BCrypt 스모크 테스트는 따로 실행한다. 완료 조건: 성공은 요청한 모든 바이트가
성공한 OS 엔트로피 호출에 전달되었음을 뜻하며, 모의 백엔드와 네이티브 근거를 구분한다.

## 8. 구현 AI의 실행 계약

1. 현재 프로젝트 규칙과 관련 헤더 계약을 읽는다. 이 기준 커밋을 검증하거나 심볼을 기준으로
   현재 소스에 맞춰 발견 사항을 재확인한다. 변경 전에 status/diff를 검사한다.
   이 RFC는 소비 프로젝트의 벤더 복사본 수정을 승인하는 문서가 아니다.
2. 크기 헬퍼 오버플로 정책과 생성·기본 모드 정책에 대한 승인을 받는다.
   보안·동시성·API 구현에는 프로젝트의 T3 계획 요구사항을 따른다.
   제안 단계인 이 RFC를 승인된 새 API로 오해하지 않는다.
3. H-ID 하나에 대해 실패하는 회귀 테스트를 반영하고 예상한 실패를 보인 뒤 최소한의 수정을
   적용한다. 검사를 통과시키기 위해 단언을 약화하지 않는다. 적절하면 기존 테스트 실행
   파일을 확장한다. 테스트 소스를 추가하면 `build_tests.inc`에 등록하고 기존 문서 검사가
   요구하는 목록·개수 문서를 갱신한다. 편집 전에 현재 트리의 목록 파일명을 확인한다.

   별도의 명시적 결정이 필요하다.

## 부록 A. 기준 버전의 세 가지 관찰 결과 재현

저장소 루트에서 실행하고 프로젝트 소유의 폐기 가능한 테스트 디렉터리를 사용한다.
이 관찰 프로그램은 `build/rfc-0006` 아래에 합성한 OLD/NEW 테스트 데이터만 쓴다.
비공개 데이터를 사용하지 않는다. 잘못된 부모 사례를 실행하기 전에
`build/rfc-0006/a`가 없는지 확인한다. `mkdir -p build/rfc-0006` 실행 후 다음 코드를
`build/rfc-0006/probe.c`로 저장한다. 훅은 실제 POSIX open을 호출한다.
의도적으로 실행 타이밍을 바꾸지만 접근 모드는 바꾸지 않는다.

```c
#define _POSIX_C_SOURCE 200809L
#include "proven.h"
#include <stdio.h>
#include <stdint.h>
#include <string.h>
#include <stdarg.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <unistd.h>
#include <assert.h>
static int held = -1;
static mode_t initial_mode;
int __real_open(const char *, int, ...);
int __wrap_open(const char *p, int flags, ...) {
    mode_t mode = 0;
    if (flags & O_CREAT) {
        va_list ap; va_start(ap, flags); mode = va_arg(ap, mode_t); va_end(ap);
    }
    int fd = __real_open(p, flags, mode);
    if (fd >= 0 && (flags & O_CREAT) && strstr(p, ".pvtmp")) {
        struct stat st;
        assert(fstat(fd, &st) == 0);
        initial_mode = st.st_mode & 0777;
        held = __real_open(p, O_RDONLY);
        assert(held >= 0);
    }
    return fd;
}
int main(void) {
    printf("sizes hex=%zu b64enc=%zu b64dec=%zu\n",
      proven_hex_encoded_size(SIZE_MAX / 2 + 1),
      proven_base64_encoded_size(SIZE_MAX),
      proven_base64_decoded_size(SIZE_MAX));
    proven_allocator_t a = proven_heap_allocator();
    proven_u8str_view_t path = PROVEN_LIT("build/rfc-0006/private-data");
    umask(0022);
    assert(proven_fs_write_file(a, path, (proven_mem_view_t){(const proven_byte_t *)"OLD",3}) == PROVEN_OK);
    assert(proven_fs_chmod(a, path, 0600) == PROVEN_OK);
    proven_err_t e = proven_fs_write_file_atomic(a, path, (proven_mem_view_t){(const proven_byte_t *)"NEW",3});
    char b[4] = {0};
    assert(held >= 0 && read(held,b,3) == 3);
    printf("temp initial_mode=%03o atomic_ok=%d held_fd_payload=%s\n", (unsigned)initial_mode, e == PROVEN_OK, b);
    close(held);
    path = PROVEN_LIT("build/rfc-0006/a\\b");
    e = proven_fs_write_file_durable(a, path, (proven_mem_view_t){(const proven_byte_t *)"NEW",3});
    int fd = __real_open("build/rfc-0006/a\\b", O_RDONLY);
    memset(b,0,sizeof b);
    assert(fd >= 0 && read(fd,b,3) == 3);
    printf("backslash durable_ok=%d payload=%s\n", e == PROVEN_OK, b);
    close(fd);
    return 0;
}
```

방금 `./nob build`에서 사용한 디버그 객체에 링크하여 컴파일한다. D는 그 명령이 보고한
빌드 디렉터리로 설정하며, 이전 새니타이저·프로파일 디렉터리를 사용하지 않는다.
아래 예시는 감사 기준 버전에서 보고된 경로다.

```sh
D=build/gcc-debug-c3625330
cc -std=c2x -Iinclude build/rfc-0006/probe.c \
  $(find "$D/src" "$D/platform" -name '*.o') \
  -pthread -lm -Wl,--wrap=open -o build/rfc-0006/probe
build/rfc-0006/probe
```

관찰 결과(관찰 프로그램 종료 상태 0은 근거 수집을 뜻하며, 수정 통과를 뜻하지 **않는다**):

```text
sizes hex=0 b64enc=0 b64dec=0
temp initial_mode=644 atomic_ok=1 held_fd_payload=NEW
backslash durable_ok=0 payload=NEW
```

이는 의도적으로 수정 전 상태를 관찰하는 프로그램이다. 특히 같은 사용자로 유지한 fd의
읽기는 제한적으로 생성하도록 수정한 뒤에도 성공할 수 있다. 수정 후 보안 테스트는
제한적인 *초기 권한*을 단언하거나, 별도로 승인받은 다른 사용자 검증 환경을 사용해야 한다.
결함 수정 후에도 관찰 출력이 위와 정확히 같아야 한다고 요구하지 않는다.

## 부록 B. 장시간 부하 없이 큐 산술의 정의되지 않은 동작 재현

`build/rfc-0006/job-wrap.c`로 저장한다. 구현 파일을 포함하는 것은 테스트 전용 접점이다.
배포하거나, 이 실행 파일에 `job.o`를 추가로 링크하여 구현을 중복 포함하지 않는다.

```c
#include "../../src/proven/job.c"
#include <stdint.h>
int main(void) {
    proven_job_cell_t cells[2] = {0};
    proven_job_sys_t sys = {0};
    sys.queue.buffer = cells;
    sys.queue.buffer_mask = 1;
    atomic_init(&sys.admission_state, 0);
    proven_size_t p = (proven_size_t)PTRDIFF_MAX + 1;
    atomic_init(&sys.queue.enqueue_pos, p);
    atomic_init(&sys.queue.dequeue_pos, p - 2);
    atomic_init(&cells[0].sequence, p - 1);
    atomic_init(&cells[1].sequence, p);
    return proven_job_submit(&sys, NULL, NULL) ? 1 : 0;
}
```

```sh
D=build/gcc-debug-c3625330
cc -std=c2x -fsanitize=undefined -fno-sanitize-recover=undefined -Iinclude \
  build/rfc-0006/job-wrap.c \
  $(find "$D/src" "$D/platform" -name '*.o' ! -name job.o) \
  -pthread -lm -o build/rfc-0006/job-wrap
build/rfc-0006/job-wrap
```

관찰 결과: `proven_job_submit`에서 9223372036854775807로부터
-9223372036854775808을 빼는 부호 있는 정수 오버플로와 함께 종료 상태 1을 반환한다.
포함한 job 구현과 이 검사 프로그램에만 UBSan 계측이 적용되며, 링크한 디버그 PAL 객체에는
적용되지 않는다. 수정 후 이 가득 찬 큐 검사는 진단 없이 종료 상태 0을 반환해야 한다.
이 경계값 하나만 유지하지 말고, H-004의 소비자 및 래핑 사례까지 등록된 회귀 테스트를 확장한다.
